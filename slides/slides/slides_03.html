docker run --rm -it python:3.14-slim bash
pip install cowsay
python -c "import cowsay"      # works
exit

# 2. open the same image again

What happens in step 2?

ModuleNotFoundError: No module named 'cowsay'

Ask the class to guess before revealing. Run it live if there is time (tested: step 2 prints ModuleNotFoundError: No module named 'cowsay').

Back to the classroom container from last lecture: the image is the blueprint, a container is one room built from it. Installing cowsay changed the room, not the blueprint. --rm demolished the room. The next docker run builds a fresh room from the same blueprint, without cowsay.

So: if we want cowsay in every room, we have to change the blueprint. That is today.

Change the blueprint, not the room

  • A Dockerfile is a plain text file with the instructions to build an image
  • docker build follows it, line by line, and saves the result as an image
  • Everyone who builds it, or downloads the image, gets the same rooms

Today we walk through Individual Assignment 2 together, step by step.

A Dockerfile is the written list of instructions the builders follow, so anyone can rebuild the same blueprint. Building an image by hand and saving it (docker commit) also exists, but nobody can see what you did. The Dockerfile is transparent: it is in Git, people can read it and review it.

Step 1: the uv project

Some data science conventions

  • Folder and file names: snake_case (lowercase + underscore), no spaces
  • Documentation (README.md): Markdown. Need a review? Markdown tutorial
  • Settings and configuration: YAML (.yml or .yaml), not for documentation
    • Structure comes from indentation with spaces, never tabs
    • # starts a comment
    • JSON is a subset of YAML: a YAML reader can read a JSON file

Today we write two YAML files: the GitHub Actions workflow and docker-compose.yml. A tab instead of spaces is the most common reason they break.

Repository and image names are the exception to snake_case: GitHub and Docker Hub names usually use hyphens, like dsci522-dockerfile-practice, and Docker Hub names must be lowercase.

Step 2: the Dockerfile

How to write a Dockerfile without pain

  1. Pick a base image from Docker Hub, write FROM <base image>
  2. Open a container from it: docker run --rm -it <base image> bash
  3. Try your install commands by hand until they work
  4. Copy the ones that worked into the Dockerfile
  5. docker build after every 2 or 3 new lines
  6. Works on your laptop? Only then move to GitHub Actions

From the textbook chapter “Customizing and building containers”. Debugging a build on GitHub Actions takes minutes per try. Debugging in a container on your laptop takes seconds.

Live, step 2 and 3 (short):

  1. docker run --rm -it ubuntu:24.04 bash
  2. cat /etc/os-release → Ubuntu 24.04.
  3. python3 --version → command not found. Ubuntu has no Python at all. Good: uv installs the Python version we pinned, so we get exactly 3.14.
  4. exit

Writing the Dockerfile:

Live: nano Dockerfile (or code . and make a new file named Dockerfile, no extension), paste the uv version from the IA2 page, save. Then click through the highlights:

  1. FROM: the base image. Ubuntu Linux, no Python. Exact tag, never latest.
  2. COPY --from: copy the uv program out of the image uv publishes. The tag 0.13.7 pins uv’s own version.
  3. WORKDIR: like cd, for the rest of the build and for containers from this image. It creates the folder.
  4. ENV UV_PROJECT_ENVIRONMENT: put the environment in /opt/venv, not in /workspace/.venv. Why: later you mount your project folder over /workspace with -v, and a mount hides whatever was there. Worse, uv would find your laptop’s .venv and replace it with a Linux one.
  5. COPY: only the three files that list the packages. Not your code, not .venv/. Ask: why not just copy .venv/? Because on a Mac, file .venv/bin/python3 says Mach-O 64-bit executable arm64, a program that does not run on Linux. And uv.lock is enough to rebuild the same versions inside the image. Same as last lecture: the shopping list and the receipt travel, the electronics are bought again where you land.
  6. RUN uv sync --locked: runs during the build. Installs Python 3.14 and exactly the versions in uv.lock.

Build and test:

Terminal, step by step:

  1. docker build --tag dsci522-test . → point at the dot: “build from this folder” (the build context, where COPY finds the files). --tag names the image. Point at the steps [1/5] to [5/5], one per line of the Dockerfile. It takes about 7 seconds.
  2. docker images dsci522-test → about 386 MB.
  3. The test command from the slide → a cow says “numpy says 1 + 2 + 3 = 6”. If a package were missing, it would be a ModuleNotFoundError instead.
  4. Look around: docker run --rm -it dsci522-test bash
    • ls -a → only .python-version, pyproject.toml, uv.lock. No .venv.
    • python3 --version → still command not found: Python is not on the PATH.
    • uv run which python → /opt/venv/bin/python. uv knows where the environment is.
    • exit
  5. docker history dsci522-test | head -7 → one row per line of the Dockerfile, newest on top. RUN uv sync is about 147 MB, ENV is 0B. These rows are the layers: next slide.

Each line is a layer, and layers are reused

  • Docker saves the result of each line as a layer
  • Rebuild: a line whose input did not change says CACHED and is reused
  • Change one line, and that line and every line below it run again
  • So: things that change rarely go at the top, things that change often at the bottom

Live: add a CMD line at the bottom of the Dockerfile:

CMD ["uv", "run", "python", "-c", "import cowsay; cowsay.cow('Moo from my image')"]
  1. docker build --tag dsci522-test . → steps 2 to 5 all say CACHED, the build takes about a second.
  2. docker run --rm dsci522-test → no command after the image name, so the CMD runs: “Moo from my image”.
  3. CMD is the default command. A command after the image name replaces it (like bash did earlier).

Remove the CMD line again afterwards, so the Dockerfile matches the assignment (the CMD is not wrong, just not needed).

This is why we copy only the three uv files, not the whole folder: editing a script does not reinstall the packages.

Ask: a teammate runs uv add pandas, then docker build. Which steps run again? The COPY of the uv files and RUN uv sync: Docker checks the files a COPY reads, not only the text of the Dockerfile. The image does not update itself, so build again after every change to uv.lock.

What --locked protects you from

Someone types "pandas==3.1.1" into pyproject.toml by hand, without uv add:

 => ERROR [stage-0 5/5] RUN uv sync --locked
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
hint: To update the lockfile, run `uv lock`.
  • Without --locked, uv would quietly make a new lock file inside the image
  • The image would no longer match the uv.lock in your repository
  • Fix: uv lock, then commit pyproject.toml and uv.lock together

Live (tested, the error above is copied from the test):

  1. nano pyproject.toml, add "pandas==3.1.1", to dependencies, save.
  2. docker build --tag dsci522-test . → the error on the slide.
  3. Undo it: git checkout pyproject.toml.
  4. docker build --tag dsci522-test . → works again.

A failing build is good news here: it fails on your laptop, loudly, instead of shipping an image that differs from your repository.

Step 3: publish with GitHub Actions

The image works on my laptop. Now what?

  • Your teammate could build it too, but every build takes time, and could differ
  • Docker Hub stores images, the way GitHub stores code
  • We could docker push from our laptop… but it would be built from whatever is on our laptop
  • GitHub Actions builds it on a fresh computer, from the files in the repository

Ask first: “how does your teammate get this image?” Let them answer before showing the bullets.

Why not push from my laptop: maybe I have changes I never committed, or an old uv.lock. Nobody can check what went into that image. When GitHub Actions builds it, the image comes from the commit, and the log shows every step. Anyone can check it.

Docker Compose: one short command

We don’t like manual work!

docker run --rm \
    -v "/$(pwd)":/workspace \
    <your_dockerhub_username>/dsci522-dockerfile-practice:sha-xxxxxxx \
    uv run python hello.py

Source: Minions movie

Ask: do you want to type this every day? And get every flag, quote and slash right, on every teammate’s laptop? A typo in the image tag and you run a different image without noticing.

Version 1: run one command

Write the settings once, in docker-compose.yml in your repository:

services:
  analysis-env:
    image: <your_dockerhub_username>/dsci522-dockerfile-practice:sha-xxxxxxx
    volumes:
      - .:/workspace

Then everyone types the same short command:

docker compose run --rm analysis-env uv run python hello.py

Click through the highlights:

  1. services: the containers this file manages. We have one.
  2. analysis-env: a name we choose for it, the service name. Commands use it to say which container.
  3. image: the image we just published, with the sha- tag, not latest. sha- never moves, so everyone gets exactly the same image, even after someone pushes a new one.
  4. volumes: the same as -v. . is the folder this file is in (the project), shown as /workspace in the container, the WORKDIR from our Dockerfile.

Map it back to the long command: -v became volumes, the image name became image. Only the command we want to run stays on the command line.

The file goes in Git, so the whole team shares the same settings.

Version 2: a container that keeps running

Add a server: here, Python’s built in web server, showing our project folder.

services:
  analysis-env:
    image: <your_dockerhub_username>/dsci522-dockerfile-practice:sha-xxxxxxx
    volumes:
      - .:/workspace
    ports:
      - "8000:8000"
    command: uv run python -m http.server 8000

Last lecture’s RStudio and Ollama, and your Milestone 2 ssh server, work the same way.

Click through the highlights:

  1. ports: the same as -p. Port 8000 on my laptop goes to port 8000 in the container (lecture 2: the door number).
  2. command: what the container runs when it starts, in place of the image’s default (Ubuntu’s bash). A web server waits for visitors forever, so the container keeps running.

No new image needed: Python’s http.server comes with Python, and our image has Python.

In Milestone 2, the image’s own CMD starts the ssh server, so your docker-compose.yml has ports but no command line.

Start it, check it, stop it

Command What it does
docker compose up Start the containers, show their output here (Ctrl + C stops them)
docker compose up -d Start them in the background, give me my terminal back
docker compose ps List the containers this file started
docker compose logs Show their output so far
docker compose stop / start Pause them / start them again, nothing deleted
docker compose down Stop and remove them
docker compose pull Download the image named in the file
docker compose run --rm <service> <command> One command in a new container (version 1)

Terminal and browser, step by step (tested):

  1. nano docker-compose.yml, add the ports and command lines from version 2. Save. cat docker-compose.yml.
  2. docker compose up → the output shows up here. Browser: http://localhost:8000 → a list of my project files: hello.py, pyproject.toml, docker-compose.yml… Back in the terminal, a new log line per page view ("GET / HTTP/1.1" 200). Ctrl + C to stop.
  3. docker compose up -d → Started, and I get my terminal back.
  4. docker compose ps → analysis-env, STATUS Up, PORTS 0.0.0.0:8000->8000/tcp.
  5. Refresh the browser, then docker compose logs → the visits.
  6. docker compose stop → stopped, not deleted: docker compose ps -a still lists it (Exited). docker compose start → running again.
  7. docker compose down → removes the container and the network compose made. docker compose ps -a → empty. The browser page no longer loads.

Every command reads docker-compose.yml in the current folder, so run them from the project folder.

Rule of thumb: up -d in the morning, down when you finish. run --rm when you just need one command.

Command What it does
