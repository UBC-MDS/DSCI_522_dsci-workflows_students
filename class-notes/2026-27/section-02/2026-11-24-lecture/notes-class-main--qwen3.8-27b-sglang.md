## Key takeaways

- `docker build --tag <name> .` builds an image from the `Dockerfile` in the current directory; the trailing `.` means "here," and `docker run`'s `-it` (interactive terminal) and `--rm` (delete on exit) are the core flags.
- `CMD` sets the default command a container runs; a command after the image name in `docker run` overrides it (e.g., `... image bash`).
- For an analysis project, pin packages with `==` in `pyproject.toml` and set `add-bounds = "exact"` so `uv add` writes exact versions; `uv.lock` records the locked set.
- Copy only `pyproject.toml`, `uv.lock`, and `.python-version` into the image and run `uv sync --locked`, so packages install at build time and the build fails if the two files drift out of sync.
- Set `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` so the container keeps its Linux-built environment in `/opt/venv` instead of a `.venv` that a mounted folder would hide or overwrite.
- Mount the live project folder with `-v "$(pwd):/workspace"` to separate source code (the mount) from the compute environment (the image), rather than copying code into the image.
- Use a `docker-compose.yml` to record the build and run flags (build, image, volumes, ports) so the launch is version controlled instead of a long copy-pasted `docker run`.

### 5. Running the image: `docker run`, `--rm`, `-it`, and overriding `CMD` ([Using and running containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-running.html))

*00:16:40–00:20:05*

- **`docker run --rm -it <image>`**: `--rm` makes the container ephemeral — when you exit, it is deleted and any changes inside are undone. `-it` gives you an interactive terminal (Docker captures what you type and passes it to the container).
- **Default vs overridden command**: with `docker run --rm -it 2026-11-24-docker`, R started by default (because of `CMD ["R"]`). Adding `bash` after the image name overrides the default and gives you a normal shell.

- **Ephemeral = safe to experiment**: because `--rm` discards everything on exit, the instructor compared it to "another version of Git that automatically resets all of your changes" — a good place to try a risky install (he used "install PyTorch" as the example) and just restart the container if it goes wrong.

### 7. Setting up the uv project locally: `pyproject.toml`, pinning, and `uv.lock` ([uv: pinning exact versions](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/virtual-environments-python-uv-exact-pins.html))

*00:27:40–00:34:45*

- **Creating the project**: `uv init --bare` creates a minimal `pyproject.toml` (a name, a version, and `requires-python = ">=3.14"`). `uv add cowsay` installs `cowsay` (6.1) and records it as a dependency; `uv sync` builds the `.venv` and installs from `uv.lock`.
- **What `uv add` writes by default**: by default `uv add` writes a lower bound, `cowsay>=6.1`. The exact version is recorded only in `uv.lock`, so the project *declares* a range and *locks* one version.
- **Why pin with `==`**: the instructor flagged that a lower bound is a liability for a long-running project — if `cowsay` released 7.0 (a backwards-incompatible change), a rebuild could pull it and break the analysis. Pinning `cowsay==6.1` keeps the declared and locked versions identical, and a version only moves when someone edits the pin (which then shows up in a diff).
- **`add-bounds = "exact"`**: adding a `[tool.uv]` table with `add-bounds = "exact"` makes every future `uv add` write `==` instead of `>=`; the setting lives in `pyproject.toml`, so the whole team gets the same behaviour.
- **`pyproject.toml` vs `uv.lock`**: `pyproject.toml` holds the explicit versions you care about; `uv.lock` pins everything (including downstream dependencies) but is generated from the `toml`. The instructor noted that even with a package like pandas pinned, a far-downstream dependency can still update and break things, so you may pin extra packages; you do not have to specify everything, only what matters.
- **Running it locally**: `hello.py` (`import cowsay; cowsay.cow("hello, moo.")`), then `uv sync` and `uv run hello.py`, which prints the ASCII cow.

> [!WARNING]
>
> A `>=` lower bound can silently break a long-running project: if the package's major version bumps (e.g., 6.x to 7.0), that is usually a backwards-incompatible change and a rebuild can pull it. Pin the packages that matter with `==` in `pyproject.toml`.

### 8. The uv `Dockerfile`: the three files and `uv sync --locked` ([Python packages with uv in an image](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-uv.html))

*00:35:00–00:39:25*

- **The three files**: to install Python and its packages in the image you copy three files into it — `pyproject.toml` (which packages and which versions), `uv.lock` (the locked, exact set), and `.python-version` (which Python). These are "the files that list the packages," not the code.
- **`.python-version`**: this file tells `uv` which Python to install (the example holds `3.14`). The instructor stressed pinning the Python version too: the Python version determines which package versions are installable, and `PyTorch` is "almost never compatible with the latest version of Python," so you often must pin a Python version. It is also how a package author tests against an upcoming Python release.
- **`COPY pyproject.toml uv.lock .python-version ./`**: these land in `/workspace` because `WORKDIR` was already set.
- **`RUN uv sync --locked`**: this installs Python and the packages at build time, exactly as you would run `uv sync` on your machine. The new `--locked` flag makes the step fail if `uv.lock` and `pyproject.toml` are out of sync — the instructor called these "little placeholders" so the build errors out when you want it to, instead of quietly updating the lockfile inside the image. The `[tool.uv]` block comes from the book's [docker-uv-renv](https://github.com/chendaniely/docker-uv-renv) example.

### 9. Building the image, layer caching, and publishing ([Layer caching](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html#layer-caching))

*00:39:25–00:44:30*

- **Building and inspecting**: `docker build --tag 2026-11-24-docker .` now runs the `COPY` and `RUN uv sync --locked` steps; the build visibly stalled at the `uv sync` step because that is where it installs the environment. `docker run --rm -it 2026-11-24-docker bash` lands in `/workspace`, and `ls -a` shows the copied files plus the `.venv`.
- **Layer caching**: each step in the `Dockerfile` becomes a cached layer; if a layer and everything above it are unchanged, Docker reuses the cache. That is why people minimize steps (fewer layers, less disk), but nothing is wrong with having more lines.
- **Order matters**: any change to a layer forces Docker to rerun that layer and everything below it. So the convention is to put the slow, rarely-changing steps (installing packages) near the top and the frequently-changing steps (copying code) near the bottom — the instructor's example was that the tidyverse can take ~15 minutes to install, and you do not want to wait that out for a typo in a script. He demonstrated this by copying `hello.py` last, so a later rebuild was fast because `uv sync` was already cached.
- **Publishing**: once built, you can either hand someone the `Dockerfile` to build, or publish the image and have them `docker pull` it so they skip the build entirely.

### 10. The problem with copying code into the image ([Python packages with uv in an image](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-uv.html))

*00:49:36–00:52:15*

- **The problem**: for an actively developed project (milestones, fast-changing EDA files), copying all the code into the image and rebuilding snapshots the code at one moment. Then you have to worry about who copied what and when, and keep remembering to commit/push *and* re-copy *and* rebuild so the image matches.
- **Why it does not scale**: the instructor called this "not a very scalable way of dealing with work that is actively being developed."
- **A valid but inferior alternative**: you *could* install `git` inside the container and clone the repository at startup; the instructor said that is totally valid and that he has done it (for example, to mimic a student's terminal), but there is a better approach.
- **The goal — separate compute from source**: keep the container holding only the installed software (the packages), and bring the code in some other way. So the `COPY hello.py` line is removed from the `Dockerfile` (you still keep the three package-listing files, because without them the image cannot build).

### 11. Mounting volumes with `-v` ([Mounting volumes to containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-running.html#mounting-volumes-to-containers))

*00:52:15–00:59:35*

- **`-v` mounts a volume**: `-v` (volume) tells Docker to "mount" a folder from your computer into the container when it runs, so the container sees your live files. `-v "$(pwd):/workspace"` takes the current directory (`$(pwd)` prints it) and places it at `/workspace` inside the container; using `$(pwd)` rather than a hard-coded path keeps the same command working on different machines.
- **It is a live shared drive**: changes you make on your computer appear in the container and vice-versa; it is the same folder, not a synced copy like Google Drive. The instructor proved it by creating `my_secrets.txt` on his machine, seeing it in the container, editing it on the machine ("i eat baby food"), and watching the change appear live in the container.
- **Why not install `git`**: with the mount, you do not need `git` (or an SSH key / personal access token) inside the container — a problem that would otherwise resurface every time the image is rebuilt with a new key. You are "just you working by yourself" on the same file, so there is no risk of clobbering a teammate's work.
- **`run` vs `build`**: you do the mounting in the `run` process, not the `build` process — at build time Docker can only `COPY` (a snapshot), but at run time it can mount a live folder.
- **Windows note**: on Windows you may need an extra leading slash in the path (the textbook shows the per-OS forms); in Bash, the `$` in `$(pwd)` pulls in the command's output.
- **Editor note**: the instructor tried `nano` and `vi` in the container and neither exists (`command not found`); Positron sometimes needs you to refresh to notice a file changed on disk.
- **The payoff**: you can now verify code in the container (`uv run hello.py`, or `uv run quarto render` for your project) with the live files, so you have a test that it works locally and a test that it works in the container.

> [!WARNING]
>
> Pay attention to the terminal prompt so you know which machine you are typing on — the instructor was jumping between his local machine and the container, and mixing them up means editing the wrong environment.

### 12. The `.venv` problem across platforms and `UV_PROJECT_ENVIRONMENT` ([Why the packages go in `/opt/venv`](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-uv.html#why-the-packages-go-in-optvenv))

*00:59:35–01:07:00*

- **The `.venv` is not portable**: the `.venv` folder holds the actual Python binary and the installed packages, all built for *your* machine's operating system and CPU. A team spans different operating systems (Windows, Mac, Linux) and CPU architectures (amd64 vs arm64) — the instructor counted four to six "different computers" to think about. A `.venv` built on a Mac will not run on Windows ("you can't just take my Excel file on my Mac, go to Windows, double click it, and expect it to run"). This is the [Building images for several platforms](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-platforms.html) idea: one image is built for one kind of processor.
- **What the mount broke**: when the project folder (including its local `.venv`) was mounted over `/workspace`, it hid/overwrote the image's Linux-built `.venv`; running `uv run` in the container then warned that the existing `.venv` was "linked to non-existent Python interpreter" (a macOS aarch64 Python), removed `.venv`, and recreated it.
- **The `uv.lock` already knows all platforms**: `uv.lock` records the package locations/hashes for the other operating systems too — `uv sync` just did not install them for you locally because you do not need them on your machine. The image build, however, is on Linux and must install the Linux set.
- **The fix — `ENV UV_PROJECT_ENVIRONMENT=/opt/venv`**: set this environment variable in the build (it must be set before `uv sync`) to tell `uv` to put the project's virtual environment in `/opt/venv` instead of `.venv` inside the project folder. Then the container ignores the mounted local `.venv` and uses the Linux environment it built, making the image portable across the team's machines.
- **Verification**: after rebuilding, `uv run which python` inside the container returns `/opt/venv/bin/python`, confirming the container uses `/opt/venv` and not the mounted `.venv`.

> [!WARNING]
>
> A local `.venv` is tied to one operating system and CPU architecture. Mounting your project folder over the image's `/workspace` can make `uv` in the container discard your Mac/Windows `.venv` and build a Linux one in its place, which then no longer works on your machine. Keep the container's environment in `/opt/venv` with `UV_PROJECT_ENVIRONMENT`.

### 13. Docker Compose ([Containers: Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*01:07:00–01:14:05*

- **Why Compose**: as the `docker run` command accumulates flags (`-v`, and `-p` for ports when using JupyterLab or RStudio on port `8787`), it becomes long and painful to edit (you cannot click into the middle of a pasted command to fix it). A `docker-compose.yml` file records all of the run parameters, and a file is nicer than a command because it can be version controlled and tracked.
- **What the file holds**: a `docker-compose.yml` is a YAML file (like `pyproject.toml`) that lists, under `services:`, each container and how to launch it — for this project one service, `analysis-env`, with `build: .` (build from the current `Dockerfile`), `image: 2026-11-24-docker` (the tag to build into), `volumes:` (`.:/workspace`), and optionally `ports:`.
- **Multiple containers**: the instructor noted that one service is "a little bit overkill" here but still useful; compose is really for running several containers at once (microservices, for example a dashboard plus its database) where you want separation between the pieces.
- **The commands**: `docker compose build` reads the file and builds the image; `docker compose up` starts the container (named after the folder and service, e.g., `2026-11-24-docker-analysis-env-1`); `docker compose up --detach` (`up -d`) starts it in the background so the prompt returns.
- **It did not work live**: in this session `docker compose up` created the container but it immediately exited with code 0, and the follow-on `exec` calls failed ("service not running"); the instructor said he would fix the demo next class. The point of the file is that it is reading all of those `docker run` flags and applying them.

### Creating the uv project on the local machine

```bash
uv init --bare        # minimal pyproject.toml (no app code)
uv add cowsay         # add cowsay==6.1 and create uv.lock
uv sync               # create .venv and install from uv.lock
uv run hello.py       # run the script in the project environment (prints the cow)
```

### Building the uv image and mounting the project folder

```bash
docker build --tag 2026-11-24-docker .                            # now runs uv sync --locked inside
docker run --rm -it 2026-11-24-docker bash                       # lands in /workspace
docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash # mount current dir at /workspace
# inside the container:
uv tree                  # show the dependency tree (cowsay v6.1)
uv run which python      # -> /opt/venv/bin/python (after ENV UV_PROJECT_ENVIRONMENT=/opt/venv)
```

`-v "$(pwd):/workspace"` mounts your live project folder, and `$(pwd)` keeps the path portable across machines; the `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` line in the `Dockerfile` keeps the container's Linux environment out of the mounted folder.

### Docker Compose

```bash
docker compose build               # build the image described in docker-compose.yml
docker compose up                  # create and start the container (exited immediately; see "what went wrong")
docker compose up --detach         # start in the background (the flag is --detach, not --detatch)
docker compose ps                  # list the project's running containers
docker compose exec analysis-env bash   # run a command in the running service
```

The compose file records `build: .`, `image: 2026-11-24-docker`, and `volumes: - .:/workspace` for the `analysis-env` service, replacing the long `docker run` command.

### What went wrong live

- **`docker compose up --detatch`**: a typo of the flag; Docker returned `unknown flag: --detatch`. The correct flag is `--detach` (or `up -d`).
- **`docker compose up` exited**: the container `analysis-env-1` was created but immediately `exited with code 0`, so `docker compose exec ...` then failed with `service "analysis-env" is not running`. The instructor said he would fix the compose demo next class.
- **`uv which python`**: `error: unrecognized subcommand 'which'`; the working form is `uv run which python`, which returned `/opt/venv/bin/python`.
- **No editor in the container**: `nano my_secrets.txt` and `vi my_secrets.txt` both gave `command not found` — the image has no text editor, which is why the homework mentions you may add one.
- **`ls 0alh`**: a `0` typed instead of `-`; `ls: cannot access '0alh'`. Re-run as `ls -alh`.
