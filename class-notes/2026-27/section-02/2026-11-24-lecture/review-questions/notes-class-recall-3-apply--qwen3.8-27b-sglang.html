1. Warm-up setup and Docker Desktop

00:00:00–00:07:15

  • Q: You run docker images on a Windows or Mac laptop and the command does not reach the Docker engine. What check should you make before running more Docker commands?
    • A: Make sure Docker Desktop is actually running. If the Docker program is not started, Docker commands cannot communicate with the daemon. Start it deliberately rather than relying on a prompt to start the program. (00:07:04)
  • Q: You are starting a Windows or Mac computer, then locating the repository, then building the image. Put these three actions in the order required: start Docker Desktop, locate the folder containing the Dockerfile, and run docker build --tag 2026-11-24-docker ..
    • A: Start Docker Desktop first, then locate the folder that contains the Dockerfile, and then run the build command from that folder. Docker commands need the running daemon before the build can use or pull the base image. The build uses the current directory, so the folder location must be correct before the trailing dot is interpreted. (00:07:00)
  • Q: You create the repository folder and run docker build --tag 2026-11-24-docker ., but Docker cannot find an image definition. What file did you forget to create, and what line must it contain?
    • A: You forgot the Dockerfile, which must contain a base image line such as FROM rocker/r-ver:4.6.2. docker build . looks for that default file in the current directory. Adding the Dockerfile gives the build an image definition to use. (00:04:19)

2. Creating the repository with a coding agent

00:07:15–00:11:00

  • Q: You are writing a prompt for a coding agent to recreate the warm-up repository. What two specific details do you need to give it instead of saying “make a Docker thing”?
    • A: Tell it to create a Dockerfile and name the exact base image, such as rocker/r-ver:4.6.2. Those details let the agent create the intended file instead of guessing what Docker object you want. The demo prompt pointed toward the actual image for that reason. (00:08:06)
  • Q: The agent says it created the repository in a temporary folder and ran shell commands such as ls, mkdir, and docker. Before you run docker build, what do you inspect, and why?
    • A: Locate the folder it actually created and inspect the files, especially the Dockerfile, to confirm the base image and default command. The agent may also write extra files such as README.md and Makefile, so you need to confirm the contents before building. This keeps you from building from the wrong location or the wrong file. (00:09:26)
  • Q: The agent adds a Makefile and a README.md to the repository in addition to the Dockerfile. For the minimal warm-up requirement, which file must be present and what are the other files?
    • A: The Dockerfile is the essential file for the warm-up. The Makefile and README.md are optional extras generated from the usual templates. They do not satisfy the Docker image requirement by themselves. (00:11:34)

3. The CMD default in the warm-up R image (29.2.1 CMD or ENTRYPOINT?)

00:11:00–00:12:45

  • Q: You build the first-commit 2026-11-24-docker image and run docker run --rm -it 2026-11-24-docker. What do you expect to start, and which instruction in the Dockerfile causes that behavior?
    • A: R starts because the warm-up Dockerfile contains CMD ["R"]. That instruction sets the default command used when no command follows the image name in docker run. It is the reason the container opens R automatically. (00:12:25)
  • Q: You want the warm-up image to start R automatically for a teammate, but you also want that default to be replaceable when debugging. Which instruction do you put in the Dockerfile, and what command later replaces it?
    • A: Use CMD ["R"] in the Dockerfile so R is the default startup command. Later, run docker run --rm -it 2026-11-24-docker bash to replace the default with a shell. This works because a command after the image name overrides CMD. (00:17:45)
  • Q: You edit the warm-up Dockerfile so it has the base image but no default command. After rebuilding, what changes when you run the container with no extra command, and what do you do if you want a shell?
    • A: R no longer starts automatically from the project’s CMD ["R"] line. To get a shell, explicitly pass bash after the image name. The default startup is no longer controlled by that CMD line. (00:17:26)

4. Building the image with docker build and the current-directory dot (29 Customizing and building containers)

00:12:45–00:16:40

  • Q: You are in the root folder of the 2026-11-24-docker repository and need to rebuild the warm-up R image with the same tag. Complete the command and explain the trailing dot.
    • A: Run docker build --tag 2026-11-24-docker .. The tag names the local image, and the trailing dot means the current directory. It tells Docker to look for the default Dockerfile in the folder where you are standing. (00:14:57)
  • Q: You are in a subfolder of the repository that contains hello.py but not a Dockerfile. You run docker build --tag 2026-11-24-docker . there. What happens, and how do you fix it?
    • A: Docker looks for the default Dockerfile in that subfolder, so it does not use the repository’s Dockerfile. Move to the folder that contains the Dockerfile and run the build command there. The dot means the current location, not the project root. (00:14:57)
  • Q: You change FROM rocker/r-ver:4.6.2 in the Dockerfile to an R version that is not already on your computer. What should you expect during docker build --tag 2026-11-24-docker .?
    • A: Docker pulls the new base image before it runs the remaining build steps. That pull can take seconds or minutes depending on the connection speed. If the base image was already local, the build can finish much faster. (00:15:54)

5. Running the image with --rm, -it, and an overridden command (28 Using and running containers)

00:16:40–00:20:05

  • Q: You run docker run --rm -it 2026-11-24-docker, see the R prompt, then exit. Predict whether a stopped container from that run remains available, and what happens to changes made inside.
    • A: --rm makes the container ephemeral, so exiting removes it. Any changes made inside are no longer available because the container was deleted. This is the reset-like behavior that makes it safe to discard the session. (00:19:29)
  • Q: You want to test a risky install, such as PyTorch, without harming your laptop. Which run pattern do you choose and why is it safe?
    • A: Start a disposable container with docker run --rm -it <image> bash, perform the install, then exit. --rm deletes the container on exit, so the install and any side effects are discarded. It is safe to start a new container if something goes wrong. (00:19:50)
  • Q: You type docker run --rm 2026-11-24-docker bash and expect to type commands interactively. What flag combination is missing, and what does it provide?
    • A: The command is missing -it. -it gives the container terminal access and passes your typed input into it. Without that flag, the run is not set up as an interactive shell. (00:16:53)

6. Choosing ubuntu:24.04 and installing uv (30 Python packages with uv in an image)

00:20:05–00:27:40

  • Q: You need to switch the warm-up R base to a Python-friendly base for the project. Which base image do you choose from the demo, and why did the demo prefer it over the R base?
    • A: Use FROM ubuntu:24.04. It is a smaller Linux base than the R image because it does not carry the R packages. The project can then install uv and let uv manage the Python version and packages. (00:23:46)
  • Q: You need uv inside the Ubuntu image, but you do not want to build it from source. Which Dockerfile instruction did the demo use, and what does --from specify?
    • A: Use COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/. --from names another published image as the source for the copy. This copies the uv and uvx programs into the new image while pinning the uv version by tag. (00:24:53)
  • Q: After writing WORKDIR /workspace in the Dockerfile, you build the image and start a container with bash. What starting directory do you expect, and what does WORKDIR do if the folder does not exist?
    • A: You should start in /workspace. WORKDIR sets the working directory for later build steps and for the running container. It creates the folder if it does not already exist, so you do not start at the filesystem root. (00:27:15)

7. Setting up the local uv project and exact pins (22 uv: pinning exact versions)

00:27:40–00:34:45

  • Q: You create a minimal uv project in the demo folder and need to add cowsay. In order, what commands do you run to create the project metadata, add the package, create the local environment, and run hello.py?
    • A: Run uv init --bare, then uv add cowsay, then uv sync, and finally uv run hello.py. uv add records the dependency and updates uv.lock; uv sync builds or updates .venv from the lock; uv run executes the script in that environment. This is the local workflow shown before building the image. (00:34:15)
  • Q: After uv add cowsay, you notice pyproject.toml declares cowsay>=6.1 instead of an exact version. For a long-running analysis project, what change should you make and why?
    • A: Change the dependency to cowsay==6.1 so the declared version matches the version the analysis was tested with. A >= lower bound can later pull a breaking major release, such as 7.0, when the project is rebuilt or relocked. Pinning the important package keeps the version from moving silently. (00:31:06)
  • Q: You want every future uv add in this project to write exact pins automatically. What setting do you add to pyproject.toml, and where does that setting belong?
    • A: Add a [tool.uv] table with add-bounds = "exact". This makes uv add write == versions for new dependencies instead of lower bounds. Because the setting is in pyproject.toml, all people working on the project get the same behavior. (00:32:02)

8. The uv Dockerfile: package-listing files and uv sync --locked (30 Python packages with uv in an image)

00:35:00–00:39:25

  • Q: You are writing the Dockerfile for the Python compute environment. Which three project files must be copied into the image before uv sync --locked, and why are analysis code files not required there?
    • A: Copy pyproject.toml, uv.lock, and .python-version into the image. These files list the packages, the locked dependency set, and the required Python version. The analysis code can be mounted later, so copying it into the image would create a stale snapshot. (00:37:44)
  • Q: You manually add a package line to pyproject.toml but forget to update uv.lock, then run docker build --tag 2026-11-24-docker .. What do you expect at the RUN uv sync --locked step, and what command fixes it locally?
    • A: The build fails because --locked requires uv.lock to match pyproject.toml. Run uv lock locally to regenerate the lockfile, then rebuild the image. This makes the intended mismatch error out instead of silently updating the lockfile inside the image. (00:38:55)
  • Q: You need the image to use Python 3.14 rather than whatever Python a user’s computer might have. Which file controls that, and what does it contain in the demo?
    • A: Use .python-version, which in the demo contains 3.14. It tells uv which Python version to install or use for the project environment. Pinning the Python version matters because package compatibility can depend on the Python version. (00:36:38)

9. Layer caching and build order (29.1.3 Layer caching)

00:39:25–00:44:30

  • Q: You add COPY hello.py ./ after RUN uv sync --locked in the Dockerfile, then only edit hello.py and rebuild. What do you expect about the uv sync --locked step, and why?
    • A: The uv sync --locked layer should be cached because the package-listing files above it did not change. Docker only reruns the changed layer and the layers below it in the file, so copying the edited script is fast. This is why frequently changing code copies are placed after slow package installs. (00:43:49)
  • Q: You move COPY hello.py ./ above RUN uv sync --locked and then change hello.py often. What problem does that create during builds?
    • A: The COPY layer changes whenever the script changes, so Docker reruns uv sync --locked and every later layer for each small edit. That can make builds wait for package installation or environment setup that did not need to change. The better order is slow, stable steps first and changing code copies later. (00:42:33)
  • Q: You have finished building the 2026-11-24-docker image and want a teammate to skip building from the Dockerfile entirely. What are the two ways described for giving them the environment?
    • A: You can hand them the Dockerfile and have them run docker build, or you can publish the image to a registry and have them use docker pull to download it. The second way gives them the already built image without needing the build steps. This is the sharing goal after a successful build. (00:44:16)

10. Separating code from the compute environment (30 Python packages with uv in an image)

00:49:36–00:52:15

  • Q: Your group is doing EDA and edits scripts many times a day. If you keep a COPY instruction that puts all analysis code into the image, what maintenance problem do you predict?
    • A: The image snapshots the code at build time, so you must remember to rebuild after copying new code to match the repository. Teammates may then run an old copy of the analysis unless they know who copied what and when. That is not scalable for actively developed work. (00:50:47)
  • Q: You decide the container should hold only the installed software while your project folder supplies the source code. What change do you make to the Dockerfile that copied hello.py?
    • A: Remove the COPY hello.py ./ line so the image no longer embeds the analysis script. Keep the copies of pyproject.toml, uv.lock, and .python-version because those are needed to build the environment. The script can then be provided at run time through a mounted folder. (00:52:14)
  • Q: You considered installing git in the container and cloning the repository when the container starts, but you want the simpler approach for this project. Which approach separates compute from source more directly?
    • A: Use a volume mount for the live project folder instead of installing Git and cloning inside the container. The mount keeps the container focused on the installed software and avoids needing SSH keys or tokens inside the image. You can still run the mounted code with uv run in the container. (00:51:21)

11. Mounting the live project folder with -v (28.1.2 Mounting volumes to containers)

00:52:15–00:59:35

  • Q: You want the container to see the current directory of the demo repository as /workspace while you run an interactive shell. What docker run command do you use?
    • A: Use docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash. $(pwd) expands to your current directory, and the -v flag mounts that folder at /workspace inside the container. This keeps the same command portable instead of hard-coding a local path. (00:57:13)
  • Q: You create my_secrets.txt in the mounted project folder on your computer, open the container, and edit the file there. What should you observe when you look at the file on your computer, and what does that show about -v?
    • A: The edit made inside the container appears on your computer because the mount is a live shared folder, not a one-time copy. It behaves like a shared drive between the container’s /workspace and your local project folder. This is how the mount was demonstrated with my_secrets.txt. (00:58:45)
  • Q: You are on Windows in Git Bash and need to mount the current directory at /workspace using the same volume idea. What path form does the textbook warn you to use, and why?
    • A: Use the doubled leading slash form, -v "/$(pwd):/workspace", in Git Bash. Git Bash can rewrite arguments that start with a single slash into Windows paths, so doubling the slash preserves the intended container path. The macOS/Linux form uses $(pwd) without the extra slash. (00:56:34)

12. Keeping the container’s Python environment in /opt/venv (30 Python packages with uv in an image)

00:59:35–01:07:00

  • Q: You mount your local project folder over /workspace, and your local folder contains a .venv built on your Mac. When you run uv run in the Linux container, what problem can the mount create?
    • A: The mount can hide or replace the image’s Linux .venv with your local .venv, which contains binaries for your machine’s operating system and architecture. uv may then complain that the existing virtual environment points to a nonexistent or incompatible Python interpreter and recreate .venv. This can leave your local environment broken if the container deletes or rewrites it. (01:02:40)
  • Q: You want the container to keep its Linux-built environment outside the mounted project folder. Which Dockerfile instruction do you add, and where must it be placed relative to uv sync?
    • A: Add ENV UV_PROJECT_ENVIRONMENT=/opt/venv before RUN uv sync --locked. This tells uv to create the project environment in /opt/venv instead of .venv inside /workspace. The environment variable must be set before the sync step so the build installs packages in the intended location. (01:04:13)
  • Q: After rebuilding with that environment variable, you want to confirm the container is using /opt/venv rather than the mounted .venv. Which command do you run inside the container, and what output did the demo show?
    • A: Run uv run which python inside the mounted container. The output was /opt/venv/bin/python, showing that uv is resolving Python from the container’s /opt/venv environment. That confirms the mounted local .venv is being ignored. (01:06:20)

13. Docker Compose for build and run parameters (33 Containers: Docker Compose)

01:07:00–01:14:05

  • Q: Your docker run command now includes the image tag, a volume mount, and possibly a port. What file do you create to store those launch parameters, and what top-level key does it start with?
    • A: Create docker-compose.yml and start the service definition under services:. For the demo, the service is analysis-env with build: ., image: 2026-11-24-docker, and volumes: - .:/workspace. The file records the same parameters that would otherwise be typed as flags on docker run. (01:10:34)
  • Q: You have written the compose file for the demo project and want to build the image it describes. Which command do you run from the project folder, and what does it read?
    • A: Run docker compose build. It reads docker-compose.yml and builds the image from the build: . and image: settings. This replaces manually typing docker build --tag 2026-11-24-docker . for that service. (01:11:09)
  • Q: You type docker compose up --detatch and Docker returns unknown flag: --detatch. What is the correct flag and what does it do?
    • A: The correct flag is --detach (or -d), so the command is docker compose up --detach or docker compose up -d. It starts the container in the background and returns your terminal prompt. The misspelled flag is not a valid Docker Compose option. (01:12:47)
  • Q: You run docker compose up for the demo, the container is created, and then docker compose exec analysis-env bash says the service is not running. What did the live output show, and what does that tell you to check?
    • A: The container analysis-env-1 exited immediately with code 0, so there was no running service to exec into. Check the container’s default command and whether it has a long-running process to keep the container alive. The compose demo was flagged as needing a fix. (01:13:50)

14. The milestone Dockerfile as a compute environment (30 Python packages with uv in an image)

01:14:05–01:17:00

  • Q: You are preparing the milestone Dockerfile for your analysis. What must the resulting container be able to do for the grader to run your analysis successfully?
    • A: The grader builds the container from your repository and runs the analysis inside it. Your Dockerfile must therefore create a reproducible compute environment with the needed Python packages installed. You should be able to mount the project folder and run the analysis in the container. (01:15:01)
  • Q: Your project is a Quarto report that already runs on your laptop. In the container, what command pattern do you use to render it with the uv-managed environment?
    • A: Mount the project folder at the container’s working directory and run uv run quarto render inside the container. uv run uses the environment that was built into the image, so the report renders with the locked packages. This is the specific goal stated for the milestone. (01:14:37)
  • Q: You discover the container lacks a text editor or a system tool your package needs. What kind of Dockerfile change is allowed, and what condition must you be able to satisfy?
    • A: Add extra RUN commands to install the missing editor or system tool, for example an editor or OS dependencies for a package. You must know why each extra item is needed for the analysis environment. The core requirement remains that the Dockerfile builds the compute environment and the report renders. (01:15:37)

15. Using other tools’ docker-compose.yml files (33 Containers: Docker Compose)

01:17:00–01:20:10

  • Q: You download an open-source application such as Actual Budget that ships with a docker-compose.yml defining a service with an image, ports, environment variables, and volumes. What command do you run to start it in the background, and what does it do?
    • A: Run docker compose up -d from the folder containing the compose file. Docker downloads any needed image, starts the service, and maps the configured port so you can reach the app in a browser. You do not need to learn that app’s normal installation steps. (01:18:29)
  • Q: You see a compose file with one service that exposes a web-app port. After docker compose up, where do you connect to the app?
    • A: You connect to the mapped port on your computer, just as you would for RStudio or JupyterLab. The compose file’s port mapping tells you which local port corresponds to the service inside its container. The app then appears in a browser on that local port. (01:19:21)
  • Q: You want to run one of the examples, such as Jellyfin or N8N, on an old laptop instead of your main computer. What does the compose-file approach require from that machine?
    • A: It needs a machine with Docker and enough resources to run the container, plus access to the compose file and image. Once Docker is available, the same docker compose up command starts the service and exposes its configured port. The choice of laptop versus cloud machine is separate from the Docker workflow.
