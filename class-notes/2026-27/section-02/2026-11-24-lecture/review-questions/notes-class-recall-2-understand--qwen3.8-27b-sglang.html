Building a reproducible Docker + uv compute environment: review questions, tier 2 — Understand

Instructor: Daniel Chen

Tier 2 of 5: Understand. Explain each answer in your own words before you read it; tier 1 (Remember) covers the facts, tiers 3 to 5 put them to use.

1. Warm-up exercise and course logistics

00:00:00–00:07:15

  • Q: Why did the course website’s colours and layout change?
    • A: Because the other instructor had the materials from her own class folded into the student repository. She teaches out of slide decks rather than summary notes, so the site now hosts her slide decks and the summary notes directly, meaning you no longer have to look in the UBC student repository for the notes. (00:04:44)
  • Q: Why are the per-lecture review notes written at different levels of Bloom’s taxonomy?
    • A: To test different levels of understanding. Some questions are basic factual ones, while others are more complicated and require you to actually know what is going on under the hood, so a lecture can be broken down into question-and-answer topics at each level. (00:05:48)
  • Q: Why does the instructor stress that everyone make sure Docker Desktop is actually running before running Docker commands?
    • A: Because if it is not running, any docker command will not reach the daemon — Docker usually prompts “do you mean to turn on Docker?” but you should not rely on that prompt and instead start it deliberately. It is flagged especially because one student in the class is on a Linux machine (which does not use Docker Desktop) while the rest are on Windows or Mac. (00:07:04)

2. Creating the repository with a coding agent

00:07:15–00:11:00

  • Q: Why did specifying the exact image name and the word Dockerfile in the prompt matter for the coding agent?
    • A: Because the information you feed into the prompt is what steers the result toward the correct answer; the instructor contrasted this with a vague “go make a thing” prompt from someone who has never heard of Docker, which would fail. Knowing the tooling vocabulary lets you point the agent at the right image and file. (00:08:38)
  • Q: What shell commands did the coding agent run before writing the files, and why?
    • A: It ran ordinary shell commands — ls, mkdir, and docker — to check its environment: whether docker and the gh command exist, and what type of computer it was on. This is the kind of setup an agent performs before writing the Dockerfile. (00:09:20)
  • Q: Why did the agent create a Makefile and a README.md even though the warm-up only asked for a Dockerfile?
    • A: Because those are things the instructor typically asks for, and his machine is set up with defaults learned in DSCI 522, so the agent reproduces those defaults; a student with their own templates can do the same. (00:11:24)

3. Reviewing the Dockerfile: the CMD command (29.2.1 CMD or ENTRYPOINT?)

00:11:00–00:12:45

  • Q: In the instructor’s “double-click a file” analogy, what does the CMD ["R"] line answer?
    • A: It answers “what opens by default” when you start the container with no other input; here, R opens. CMD is the line that sets that default command for the container. (00:12:28)
  • Q: Why did the warm-up Dockerfile need only the FROM rocker/r-ver:4.6.2 line to meet the requirement, yet Claude still added CMD ["R"]?
    • A: The base-image line was enough to fulfill the task, but Claude recognized the base was an R container and inferred you would want to do R things with it, so it set R as the default command. (00:11:44)
  • Q: If the container’s CMD is ["R"], why is CMD a default rather than a hard requirement?
    • A: Because you can always give the container other parameters or commands when you run it to start something that is not R; CMD only controls what happens when you provide no other input. (00:12:19)

4. Building the image: docker build and the . (29 Customizing and building containers)

00:12:45–00:16:40

  • Q: Why does docker build --tag 2026-11-24-docker . end with a dot .?
    • A: The dot comes from DSCI 521 week 1, where . meant “your current location.” docker build looks for a file called Dockerfile (capital D) by default and must be given a location to look; the dot says that default file is where you currently are. It is like a function that needs an input, so you cannot leave it empty. (00:14:46)
  • Q: Why did rebuilding the R image build so quickly this time?
    • A: Because the base rocker/r-ver:4.6.2 image was already available locally, so the build just ran through the steps fast. Had you pointed at an R version you had not downloaded, the pull step would have taken a couple of seconds to minutes depending on your internet speed. (00:15:45)
  • Q: What does the --tag (or -t) flag do, and why can the tag be anything?
    • A: It names the image you are building. The tag can be any name you choose — the instructor joked you could call it “pizza” — it simply labels the image locally. (00:14:13)

5. Running the image: docker run, --rm, -it (28 Using and running containers)

00:16:40–00:20:05

  • Q: What do the --rm and -it flags each do in docker run --rm -it 2026-11-24-docker?
    • A: --rm makes the container ephemeral: when you exit (or Ctrl-C), it is deleted and any changes inside are undone. -it gives you an interactive terminal, meaning Docker captures what you type and passes it along to the container. (00:16:53)
  • Q: Why is a container run with --rm a good place to try a risky install such as PyTorch?
    • A: Because exiting deletes the container and undoes all of your changes — the instructor compared it to “another version of Git that automatically resets all of your changes.” If the install goes wrong, you just restart it and nothing bad has happened. (00:19:50)
  • Q: Why do you start at the root of the filesystem inside the container, and why is there no dedicated user?
    • A: Because a lot of Docker containers are set up with stuff just thrown in, so you end up seeing the operating-system files from the system level. For this class the container is a self-contained analysis setup, not a public service, so ownership is not a concern and commands start at the root. (00:18:24)
  • Q: Why does adding bash after the image name in docker run --rm -it 2026-11-24-docker bash give you a normal shell instead of starting R?
    • A: Because a command after the image name overwrites the container’s default CMD of R; you then have normal terminal access, just like Git Bash on Windows or your terminal on a Mac, with the same type of access to that machine. (00:17:26)

6. Choosing a base image and installing uv (30 Python packages with uv in an image)

00:20:05–00:27:40

  • Q: Why did the class choose ubuntu:24.04 as the base image instead of keeping the R image?
    • A: Because the R image has a lot of R-specific stuff installed, and the instructor wanted something smaller to be respectful of other people’s disk space — he noted disk is “very expensive now because of the AI boom.” Alpine is even smaller but may need more manual installs, so Ubuntu is a good general starting point. (00:23:55)
  • Q: What is the COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/ line doing, and why copy from that registry image?
    • A: It copies the uv and uvx programs out of the image that uv publishes — “copy from one image to another image” — into the new container’s /usr/local/bin. The ghcr.io/... name is a registry path (a username, a repository, a version), and the version is pinned by tag the way a lockfile pins a package; this line comes straight from uv’s Docker guide. (00:25:14)
  • Q: What does WORKDIR /workspace do, and why set it?
    • A: It changes the working directory of the container (creating the folder if it does not exist), so when you start the container you land in /workspace instead of the root. The working-directory idea comes from DSCI 521 and from R/Python, where commands always need a starting point. (00:26:42)
  • Q: If most of the class is on Windows or Mac, why does a container run on Linux?
    • A: Because Docker containers work on top of some version of Linux; as soon as you are inside a container you are in the Linux world, most likely some version of Ubuntu. (00:23:33)

7. Pinning exact versions with pyproject.toml (22 uv: pinning exact versions)

00:27:40–00:34:45

  • Q: Why pin cowsay==6.1 with == rather than the cowsay>=6.1 that uv add writes by default?
    • A: Because a lower bound is a liability for a long-running project: if cowsay released 7.0 and you rebuilt the container, you would pull it, and when a package’s first number changes it is typically a backwards-compatibility-breaking change that can break the analysis. Pinning with == keeps the declared and locked versions identical, so a version only moves when someone edits the pin. (00:30:51)
  • Q: What does add-bounds = "exact" in the [tool.uv] table of pyproject.toml change?
    • A: It makes every future uv add write an exact version (==) instead of a lower bound (>=). Because the setting lives in pyproject.toml, everyone on the project gets the same behaviour from uv add. (00:31:06)
  • Q: What is the difference between pyproject.toml and uv.lock?
    • A: pyproject.toml is a general Python metadata file that holds the explicit versions you care about, while uv.lock pins the whole set (including downstream dependencies) to specific versions and is generated from the toml. You specify what matters in the toml and let the resolver handle the rest, though you may pin extra downstream packages if one updates and breaks things. (00:33:35)

8. The uv Dockerfile: three files and uv sync --locked (30 Python packages with uv in an image)

00:35:00–00:39:25

  • Q: What is the .python-version file for, and how does it differ from uv.lock?
    • A: It tells uv what version of Python to install; it is a separate file that says, if you were to install again, which Python version to use, because you do not always want the latest. uv.lock, by contrast, only locks the packages and their dependencies, not the Python version. (00:36:38)
  • Q: Why does the class pin the Python version at all?
    • A: Because the version of Python determines which dependency versions of a package are installable — not everything is compatible with the latest Python. His biggest example is PyTorch, which is almost never compatible with the latest Python, so you often have to pin a version; it also lets a package author test against an upcoming Python release. (00:35:59)
  • Q: What does RUN uv sync --locked do at build time, and what does the --locked flag add?
    • A: It installs the Python and the packages at build time, exactly as you would run uv sync on your machine. The --locked flag makes the step error out if uv.lock and pyproject.toml are out of sync — the instructor called these “little placeholders” so the build fails when you want it to, instead of quietly updating the lockfile inside the image. (00:39:14)

9. Layer caching and ordering (29.1.3 Layer caching)

00:39:25–00:44:30

  • Q: How does Docker’s layer caching work, and what does it mean for rebuild speed?
    • A: Docker saves each step’s result as a layer, and reuses a layer when that step and the steps above it have not changed; if a layer is unchanged it just uses the cached version. That is why a build can finish very quickly. (00:41:35)
  • Q: Why put the slow, rarely-changing steps near the top of the Dockerfile and the frequently-changing steps near the bottom?
    • A: Because any change to a layer forces Docker to rerun that layer and everything below it. If uv sync takes a long time and you copied your code before it, a typo in a script would make you wait through the slow install again — his example was that the tidyverse can take around fifteen minutes — so copying code last avoids that. (00:42:40)
  • Q: Why did copying hello.py at the end make the next rebuild fast?
    • A: Because copying a file is super fast, and the earlier uv sync layer was already cached, so only the copy step had to run. (00:43:54)
  • Q: What are the two ways to hand someone a working copy of your analysis once the image is built?
    • A: You can give them the Dockerfile and have them build it, or you can publish the image to a registry and have them docker pull it so the image is already there and they skip the build entirely. (00:44:16)

10. Separating compute from source code (30 Python packages with uv in an image)

00:49:36–00:52:15

  • Q: Why is copying all of your code into the image and rebuilding a poor way to work on an actively developed project?
    • A: Because it snapshots the code at one moment, so you then have to worry about who copied what and when, and remember to commit/push and re-copy and rebuild so the image matches. The instructor called this not a very scalable way to deal with work that is actively being developed. (00:50:27)
  • Q: Why is installing Git inside the container and cloning the repository a valid but inferior alternative?
    • A: Because the goal is to separate compute (the installed software/packages) from source code; installing Git just re-introduces the code into the container. The instructor said it is totally valid and he has done it (for example, to mimic a student’s terminal), but there is always a better way. (00:51:40)
  • Q: Why remove the COPY hello.py line from the Dockerfile while keeping the pyproject.toml, uv.lock, and .python-version copies?
    • A: Because the three package-listing files are required for the build — without them the container could not build — whereas the actual code is brought in another way (mounted) so the container holds only the installed software. (00:52:30)

11. Mounting volumes with -v (28.1.2 Mounting volumes to containers)

00:52:15–00:59:35

  • Q: What does the -v flag in docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash do?
    • A: It “mounts” a volume: it takes a folder from your computer and makes it available in the container when it runs, so the container sees your live files. It is like a shared drive — changes you make on your computer appear in the container and vice-versa, because it is the same folder, not a synced copy. (00:54:30)
  • Q: Why use $(pwd) in the -v flag instead of a hard-coded path?
    • A: The $ in $(pwd) is a Bash way to pull in a command’s output, and pwd prints your current working directory, so the flag takes your current directory as the folder to share. That keeps you from hard-coding a local path. (00:56:59)
  • Q: Why is the mounting done in the docker run process rather than the docker build process?
    • A: Because at build time Docker can only COPY a snapshot of the files, but at run time it can mount a live folder and keep it in sync at that location. (00:56:06)
  • Q: Why don’t you need to install Git (with SSH keys or a personal access token) inside the container when you use the mount?
    • A: Because the shared drive means you are not doing git push/pull in the container; otherwise every rebuild would create a new SSH key you would have to re-register, which makes Git a big problem. You are just working by yourself on the same file, so there is no risk of clobbering a teammate’s work. (00:54:52)
  • Q: Why did the instructor warn to pay attention to the terminal prompt?
    • A: Because he was jumping between his local machine and the container, and mixing them up means you might edit or run commands in the wrong environment. (00:52:53)

12. Keeping the environment in /opt/venv (30.5 Why the packages go in /opt/venv)

00:59:35–01:07:00

  • Q: Why is a local .venv folder not portable across a team’s different machines?
    • A: Because the .venv holds the actual Python binary and the installed packages, all built for your machine’s operating system and CPU architecture. A team spans Windows/Mac/Linux and two CPU architectures (amd64 and arm64), so a .venv built on a Mac will not run on Windows — like you cannot double-click a Mac Excel file on Windows and expect it to work. (01:00:45)
  • Q: What went wrong when the project folder (with its local .venv) was mounted over /workspace?
    • A: The mount overwrote the image’s Linux-built .venv; running uv run in the container then found your local .venv, warned that it was “linked to non-existent Python interpreter,” removed it, and created a Linux one in its place. The result is that your Mac .venv is gone and the new one does not work on your machine. (01:02:40)
  • Q: Why set ENV UV_PROJECT_ENVIRONMENT=/opt/venv in the Dockerfile?
    • A: It tells uv to put the project’s virtual environment in /opt/venv instead of .venv inside the mounted project folder, and it must be set before uv sync runs. Then the container ignores the mounted local .venv and uses the Linux environment the image built, which makes the image portable across the team’s machines. (01:04:35)
  • Q: Why does uv.lock already contain the package information for other operating systems even though uv sync only installed your local one?
    • A: Because the lock file records the hashes, locations, and dependencies for all the other operating systems; uv sync simply did not install them locally because you do not need them on your machine. When the container builds on Linux, it is those Linux entries in the lock file that are used. (01:01:22)
  • Q: How did the instructor verify that the container now uses /opt/venv?
    • A: By running uv run which python inside the container, which returned /opt/venv/bin/python, confirming uv was no longer looking in .venv. (01:06:27)

13. Docker Compose (33 Containers: Docker Compose)

01:07:00–01:14:05

  • Q: Why use a docker-compose.yml file instead of a long docker run command?
    • A: Because as the docker run command accumulates flags (-v, and -p for ports when using JupyterLab or RStudio on port 8787) it becomes long and painful to edit — you cannot click into the middle of a pasted command to fix it. A file is nicer because it can be version controlled and tracked, and you rely on simple commands to run. (01:11:28)
  • Q: What are the parts of the docker-compose.yml the class wrote for the analysis-env service?
    • A: It is a YAML file that, under services:, lists one container: build: . (build the image from the current Dockerfile), image: 2026-11-24-docker (the tag to build into), volumes: with .:/workspace (mount the current directory at /workspace), and optionally ports:. (01:10:34)
  • Q: Why is Docker Compose useful beyond a single container?
    • A: Because it is really for running several containers at once — for example a dashboard plus its database in a microservices setup, where some people only care about the database and you want separation between the pieces. One service is a bit overkill here but still useful. (01:08:53)
  • Q: What does docker compose up --detach do compared with docker compose up?
    • A: --detach (or up -d) starts the container in the background so the prompt returns, whereas a plain up attaches. In this session up created the container but it exited with code 0 immediately, and the instructor said he would fix the demo next class. (01:12:14)

14. The homework: a Dockerfile as compute environment (30 Python packages with uv in an image)

01:14:05–01:17:00

  • Q: Why might the Dockerfile need extra system tools beyond the Python packages installed by uv?
    • A: Because some packages need system tools to actually function — the instructor’s example was geospatial analysis, which needs many system tools and the underlying libraries those Python packages are built on. The requirement is that you understand why you are installing each thing. (01:16:16)
  • Q: How is this week’s Dockerfile milestone graded, and what does that grading check?
    • A: The TA takes your repository, builds a container from it, and runs the analysis inside that container. It checks that you have a reproducible compute environment — hand someone the Dockerfile or an image and the analysis is fully contained. (01:15:09)
  • Q: Why must the container mount your project folder and render with uv run quarto render?
    • A: Because the homework requires that you mount the folders that need to be mounted and that uv run quarto render renders your report inside the container, so the analysis is verified to run in the container and not just on your machine. (01:14:44)

15. Docker Compose outside the class (33 Containers: Docker Compose)

01:17:00–01:20:10

  • Q: Why can you stand up whole applications with just docker compose up if you know your way around Docker?
    • A: Because many open-source tools ship a docker-compose.yml that defines the service(s), image, ports, and environment variables; docker compose up then downloads the image, runs the software, and exposes the port, so you do not have to learn each tool’s install steps. (01:19:44)
  • Q: What did the Actual Budget compose file define, and what does docker compose up -d do for it?
    • A: It defines one service (actual-server) with an image, some ports, the environment variables it needs, some volumes, and a health check. docker compose up -d downloads the image, runs the software, and exposes the port, giving you your own personal-finance app in a browser. (01:18:19)
  • Q: Why do tools like Jellyfin, N8N, and the recipe app “run like RStudio”?
    • A: Because they all run on a port in a browser; the only thing you have to arrange is a machine to run them on, whether an old laptop or a machine you pay for in the cloud. (01:19:21)
  • Q: Explain how the compose-file skill used for the class’s compute environment applies to deploying these open-source apps.
    • A: It is the same skill: read the docker-compose.yml and run docker compose up, so Docker is not only for reproducible analysis — the same mechanism stands up whole applications. (01:19:56)
