## 2. Building a Python Container with `uv` ([30 Python packages with uv in an image](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-uv.html))

*00:13:56–00:33:35*

- **Q:** Why did the instructor switch from using an R-specific image to `ubuntu:24.04` as the base image for the Python container?
    - **A:** The R container comes preloaded with R-specific software and dependencies, making it unnecessarily large. Starting from `ubuntu:24.04` provides a leaner, more generic Linux environment that is smaller in size and saves disk space while still allowing `uv` to install Python. *(00:23:42)*

- **Q:** What is the difference between how `uv` handles package versions in `pyproject.toml` versus `uv.lock`, and why is it important to pin exact versions in `pyproject.toml` for a data analysis project?
    - **A:** `uv.lock` records the exact versions resolved, but `pyproject.toml` declares the ranges or versions. If `pyproject.toml` only uses lower bounds (e.g., `>=3.1.1`), a regenerated lockfile could install newer versions that break the analysis. Declaring exact versions (`==`) ensures that anyone reading the file or installing it elsewhere knows exactly what version the analysis was run with. *(00:30:01)*

- **Q:** Why does the `Dockerfile` include the `--locked` flag in the `RUN uv sync --locked` command instead of just `RUN uv sync`?
    - **A:** The `--locked` flag ensures that the build fails if `uv.lock` does not perfectly match `pyproject.toml`. Without it, `uv sync` might quietly update the lockfile inside the container, causing the built image to no longer match the version-controlled `uv.lock` in the repository. *(00:38:55)*

- **Q:** What role does the `.python-version` file play in the container build process, and why is it useful for package authors or long-term projects?
    - **A:** The file explicitly tells `uv` which Python version to install if it needs to set up the environment from scratch. It is useful for package authors who want to ensure their code works with upcoming or specific Python releases, rather than relying on whatever the latest version happens to be. *(00:36:30)*

## 3. Layer Caching and `Dockerfile` Optimization ([29 Customizing and building containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html))

*00:33:35–00:51:21*

- **Q:** Why does Docker cache layers, and why is it recommended to place long-running setup steps at the top of a `Dockerfile`?
    - **A:** Docker caches each step's result as a layer and reuses it if the command and its inputs have not changed since the last build. Placing long, static steps like installing software at the top means that if you only edit application code later, Docker will skip the slow installation steps and reuse the cached layers. *(00:41:35)*

- **Q:** Why does changing a single instruction early in a `Dockerfile` force Docker to rebuild all the layers below it, and how does this affect development time?
    - **A:** Docker caches each instruction as a distinct layer. If you change an early step, the cache for that layer is invalidated, meaning Docker must re-execute that step and every subsequent step to construct the new image. This forces you to wait through slow installation steps again instead of just building the changed part. *(00:42:23)*

- **Q:** Why is it counterproductive to copy your entire application code (like `hello.py`) into the `Dockerfile` during the build process for an actively developing project?
    - **A:** Copying code into the image snapshots a static version of the files at build time. If you edit the code on your host machine while working, the container still contains the old version, forcing you to rebuild the entire image to see your changes, which is inefficient for rapid iteration. *(00:50:14)*

## 4. Volume Mounting and Cross-Platform Environments ([28 Using and running containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-running.html))

*00:51:21–01:06:55*

- **Q:** Why did the instructor introduce the `-v "$(pwd):/workspace"` flag when running the container, instead of copying the code into the image?
    - **A:** The `-v` flag mounts the host's current directory directly into the container, creating a live, bidirectional sync. This allows you to edit files on your computer and immediately see the changes reflected inside the container without needing to rebuild the image. *(00:54:18)*

- **Q:** Why does mounting the local `.venv` folder into the container cause problems, and how does setting `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` solve this issue?
    - **A:** Mounting the local `.venv` overwrites the container's packages with binaries compiled for the host operating system (e.g., macOS), which will fail inside the Linux container. Setting the environment variable forces `uv` to install the virtual environment in an isolated directory like `/opt/venv`, so the container ignores the mounted `.venv` and uses its own Linux-compiled packages. *(01:00:45)*

- **Q:** Why might a team of developers working on the same project need to solve the cross-platform `.venv` problem, even if it works fine on one person's laptop?
    - **A:** Team members often use different operating systems (macOS, Windows, Linux) and different CPU architectures (ARM, Intel/AMD). A virtual environment created on one system contains architecture-specific binaries that will not run on another system, breaking the environment if shared or mounted directly. *(01:01:12)*

## 5. Docker Compose and Milestone Assignment ([33 Containers: Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*01:06:55–01:20:07*

- **Q:** Why is it beneficial to replace long, manual `docker run` commands with a `docker-compose.yml` file?
    - **A:** `docker-compose.yml` consolidates all the parameters (like volumes, ports, and build contexts) into a readable, version-controlled YAML file. This prevents errors from typos, makes it easier to document and modify the setup, and allows anyone to run the exact same configuration using simple compose commands. *(01:11:28)*

- **Q:** How does the structure of a `docker-compose.yml` file map to the `docker build` and `docker run` commands the instructor demonstrated manually?
    - **A:** The `build: .` line tells Compose to build the image from the current directory's `Dockerfile`, equivalent to `docker build`. The `volumes:` section replaces the `-v` flag, mapping the local directory to a path inside the container. Together, they combine the setup and execution steps into one declarative file. *(01:10:25)*

- **Q:** Why might a `docker-compose.yml` file be useful for deploying applications like personal finance or media servers in real-world settings?
    - **A:** In industry, complex applications often require multiple coordinated containers, such as a web app communicating with a database. A compose file allows you to define all these services, their ports, and their shared volumes in one place, making deployment and scaling much easier than managing individual commands. *(01:08:35)*
