Building a Docker + uv compute environment: review questions, tier 5 — Evaluate

Date: 2026-11-24

Generated by qwen3.8-27b-sglang, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Tier 5 of 5: Evaluate. Decide and justify your verdict before you read the answer; the criteria are the ones given in class.

1. Docker Desktop must be running

00:00:00–00:07:15

  • Q: A student plans to run docker build on a Mac or Windows machine without checking whether Docker Desktop is running, relying on Docker’s prompt to start it for them. Would you approve that plan?
    • A: No. The instructor warned that Docker Desktop must actually be running before a docker command is issued; otherwise the command will not reach the Docker daemon. Relying on Docker to prompt and start it is not the standard the class set. (00:07:04)

2. Prompting a coding agent for a Docker project

00:07:15–00:11:00

  • Q: A team asks a coding agent to “make a thing” for their container setup without naming the Dockerfile or the specific base image. Is that an acceptable way to set up the repository?
    • A: No. The instructor’s criterion is that the agent needs the actual tooling vocabulary, so the prompt should name the Dockerfile and the specific base image. A vague “go make a thing” prompt from someone who does not know the Docker words is the mistake he contrasted with the working demo. (00:08:38)

3. The default CMD in the R image (29.2.1 CMD or ENTRYPOINT?)

00:11:00–00:12:45

  • Q: A teammate argues that because the warm-up Dockerfile contains CMD ["R"], running docker run --rm -it 2026-11-24-docker bash is not possible. Is that argument sound?
    • A: No, that is not a sound argument. CMD ["R"] only sets the default command for the 2026-11-24-docker image; the instructor said you can still pass another command, such as bash, when running the container. So CMD is not a hard lock on R. (00:12:19)

4. docker build and the required . (29 Customizing and building containers)

00:12:45–00:16:40

  • Q: A pull request changes docker build --tag 2026-11-24-docker . to docker build --tag 2026-11-24-docker, arguing that the tag is enough. Would you approve it?
    • A: No, I would not approve it. The trailing . is not punctuation; it is the required location argument telling docker build that the default Dockerfile is in the current directory. Since the build command needs an input location, omitting the dot leaves that input empty. (00:15:31)

5. Using --rm for risky experiments (28 Using and running containers)

00:16:40–00:20:05

  • Q: A student wants to test installing PyTorch directly on their own laptop because they are worried about breaking their environment. Is that the recommended approach?
    • A: No, not for a risky experiment. The class standard is to use a container run with --rm, because exiting removes the container and undoes the changes, like a Git reset. That makes a failed PyTorch test harmless: restart the container and nothing on the laptop is damaged. (00:19:58)

6. Choosing the base image for the Python/uv image (29.3 Choosing a base image for your Dockerfile)

00:20:05–00:27:40

  • Q: For the class’s Python/uv compute environment, one Dockerfile uses rocker/r-ver:4.6.2 and another uses ubuntu:24.04. Which would you approve, and why?
    • A: Approve the ubuntu:24.04 Dockerfile. The class switched from the R base to a Python-compatible base because the rocker/r-ver image carries unnecessary R software for this Python/uv project. The criterion was to keep the image smaller and be respectful of other people’s disk space, with Ubuntu as a good starting point. (00:23:55)

7. Pinning package versions in pyproject.toml (22 uv: pinning exact versions)

00:27:40–00:34:45

  • Q: A milestone project’s pyproject.toml declares cowsay>=6.1 and relies on uv.lock to keep version 6.1. Is that acceptable for a long-running analysis?
    • A: No, not for a long-running analysis. A >= lower bound can let a later major version, such as cowsay 7.0, be pulled during a rebuild, and a major version change is typically backwards incompatible. The class solution is to pin the packages that matter with == in pyproject.toml and set add-bounds = "exact" so uv add keeps writing exact pins. (00:31:06)

8. Copying the uv project files and enforcing the lockfile (30 Python packages with uv in an image)

00:35:00–00:39:25

  • Q: A Dockerfile copies pyproject.toml and uv.lock but omits .python-version, and the team says it is fine to use whatever latest Python is available. Is that acceptable?
    • A: No. The instructor said the Python version itself should be pinned because the Python version determines which package versions can be installed. He singled out PyTorch as almost never compatible with the latest Python, so relying on whatever latest Python is available does not meet the class standard. (00:35:59)
  • Q: A team removes --locked from RUN uv sync --locked to avoid build failures when pyproject.toml and uv.lock drift apart. Would you approve that change?
    • A: No. uv sync --locked is the check that pyproject.toml and uv.lock are in sync; if they are not, the build should error. Removing --locked would let the build quietly update the lockfile inside the image, so the image could stop matching the repository’s uv.lock. (00:39:14)

9. Dockerfile layer order and caching (29.1.3 Layer caching)

00:39:25–00:44:30

  • Q: A Dockerfile copies hello.py before RUN uv sync --locked. Would you approve that order for a project where scripts change often?
    • A: No, I would not approve that order for frequently changing code. Docker reuses cached layers, but a change to an earlier layer reruns that layer and everything below it. The class ordering puts the slow uv sync --locked environment install before the code copy, so editing hello.py does not force a long package install again. (00:43:10)

10. Not copying live analysis code into the image (30 Python packages with uv in an image)

00:49:36–00:52:15

  • Q: For a milestone with fast-changing EDA scripts, a teammate proposes COPY-ing all analysis scripts into the image and rebuilding after each edit. Is that acceptable?
    • A: No, that is not the scalable approach for active milestone work. COPY-ing all code into the image snapshots it at one moment and forces the team to track who copied what, plus commit, push, copy, and rebuild each time. The class goal was to separate compute from source code by keeping only the installed software in the image. (00:51:16)

11. Mounting the project folder instead of installing Git (28.1.2 Mounting volumes to containers)

00:52:15–00:59:35

  • Q: To get code into the container, a teammate proposes installing git inside the image and cloning the repository when the container starts. Would you recommend that for the course’s live-analysis workflow?
    • A: No, I would not recommend it as the preferred approach. Installing git in the container and cloning is valid only if the goal is to mimic a terminal, but the class preferred a mounted volume because it is a live shared drive. The mount avoids putting SSH keys or tokens in the container and avoids the problem of generating and updating a new key whenever the image is rebuilt. (00:55:24)

12. Keeping the container environment out of the mounted .venv (30.5 Why the packages go in /opt/venv)

00:59:35–01:07:00

  • Q: A team mounts the whole project folder, including the local .venv, over /workspace and lets the container use that .venv. Is that acceptable for a group project with different operating systems and CPU architectures?
    • A: No, that is not acceptable for a group project. A .venv contains the actual Python binary and packages for one operating system and CPU architecture, so it is not portable across the team’s different machines. The class standard is ENV UV_PROJECT_ENVIRONMENT=/opt/venv, so the container keeps its Linux-built environment and ignores the mounted local .venv. (01:05:01)

13. Using a docker-compose.yml instead of a long docker run command (33 Containers: Docker Compose)

01:07:00–01:14:05

  • Q: A team records how to launch the container only as a long docker run command in a README, rather than in a docker-compose.yml. Would you recommend that?
    • A: No, I would recommend the docker-compose.yml instead. The class criterion is that a file records the build and run flags, can be version controlled, and makes changes trackable. A long copy-pasted docker run command is the fragile approach they contrasted with the compose file. (01:11:46)

14. The milestone Dockerfile standard

01:14:05–01:17:00

  • Q: A milestone submission builds a container but does not mount the project folder or render the report with uv run quarto render. Does it meet the standard the class set for this week?
    • A: No, it does not meet the standard. The class said the TA grades by taking the repository, building the container, and then running the analysis in that container. For this week, the container must be able to mount the needed folders and uv run quarto render must render the report inside it. (01:15:09)

15. Docker Compose as a general skill (33 Containers: Docker Compose)

01:17:00–01:20:10

  • Q: A teammate says Docker Compose is only for this class’s analysis environment and cannot be used to run open-source software like Actual Budget. Is that a fair judgment?
    • A: No, that judgment is not fair. The class showed that many open-source tools already ship a docker-compose.yml, and knowing Docker lets you start them with docker compose up. Compose was presented as a general skill for running applications, not only as a tool for this class’s analysis environment. (01:19:56)
