## 7. Pinning exact versions with `pyproject.toml` ([22 uv: pinning exact versions](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/virtual-environments-python-uv-exact-pins.html))

*00:27:40–00:34:45*

- **Q:** Why pin `cowsay==6.1` with `==` rather than the `cowsay>=6.1` that `uv add` writes by default?
    - **A:** Because a lower bound is a liability for a long-running project: if cowsay released 7.0 and you rebuilt the container, you would pull it, and when a package's first number changes it is typically a backwards-compatibility-breaking change that can break the analysis. Pinning with `==` keeps the declared and locked versions identical, so a version only moves when someone edits the pin. *(00:30:51)*

- **Q:** What does `add-bounds = "exact"` in the `[tool.uv]` table of `pyproject.toml` change?
    - **A:** It makes every future `uv add` write an exact version (`==`) instead of a lower bound (`>=`). Because the setting lives in `pyproject.toml`, everyone on the project gets the same behaviour from `uv add`. *(00:31:06)*

- **Q:** What is the difference between `pyproject.toml` and `uv.lock`?
    - **A:** `pyproject.toml` is a general Python metadata file that holds the explicit versions you care about, while `uv.lock` pins the whole set (including downstream dependencies) to specific versions and is generated from the `toml`. You specify what matters in the `toml` and let the resolver handle the rest, though you may pin extra downstream packages if one updates and breaks things. *(00:33:35)*

## 9. Layer caching and ordering ([29.1.3 Layer caching](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html#layer-caching))

*00:39:25–00:44:30*

- **Q:** How does Docker's layer caching work, and what does it mean for rebuild speed?
    - **A:** Docker saves each step's result as a layer, and reuses a layer when that step and the steps above it have not changed; if a layer is unchanged it just uses the cached version. That is why a build can finish very quickly. *(00:41:35)*

- **Q:** Why put the slow, rarely-changing steps near the top of the `Dockerfile` and the frequently-changing steps near the bottom?
    - **A:** Because any change to a layer forces Docker to rerun that layer and everything below it. If `uv sync` takes a long time and you copied your code before it, a typo in a script would make you wait through the slow install again — his example was that the tidyverse can take around fifteen minutes — so copying code last avoids that. *(00:42:40)*

- **Q:** Why did copying `hello.py` at the end make the next rebuild fast?
    - **A:** Because copying a file is super fast, and the earlier `uv sync` layer was already cached, so only the copy step had to run. *(00:43:54)*

- **Q:** What are the two ways to hand someone a working copy of your analysis once the image is built?
    - **A:** You can give them the `Dockerfile` and have them build it, or you can publish the image to a registry and have them `docker pull` it so the image is already there and they skip the build entirely. *(00:44:16)*

## 11. Mounting volumes with `-v` ([28.1.2 Mounting volumes to containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-running.html#mounting-volumes-to-containers))

*00:52:15–00:59:35*

- **Q:** What does the `-v` flag in `docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash` do?
    - **A:** It "mounts" a volume: it takes a folder from your computer and makes it available in the container when it runs, so the container sees your live files. It is like a shared drive — changes you make on your computer appear in the container and vice-versa, because it is the same folder, not a synced copy. *(00:54:30)*

- **Q:** Why use `$(pwd)` in the `-v` flag instead of a hard-coded path?
    - **A:** The `$` in `$(pwd)` is a Bash way to pull in a command's output, and `pwd` prints your current working directory, so the flag takes your current directory as the folder to share. That keeps you from hard-coding a local path. *(00:56:59)*

- **Q:** Why is the mounting done in the `docker run` process rather than the `docker build` process?
    - **A:** Because at build time Docker can only `COPY` a snapshot of the files, but at run time it can mount a live folder and keep it in sync at that location. *(00:56:06)*

- **Q:** Why don't you need to install Git (with SSH keys or a personal access token) inside the container when you use the mount?
    - **A:** Because the shared drive means you are not doing `git push`/`pull` in the container; otherwise every rebuild would create a new SSH key you would have to re-register, which makes Git a big problem. You are just working by yourself on the same file, so there is no risk of clobbering a teammate's work. *(00:54:52)*

- **Q:** Why did the instructor warn to pay attention to the terminal prompt?
    - **A:** Because he was jumping between his local machine and the container, and mixing them up means you might edit or run commands in the wrong environment. *(00:52:53)*

## 12. Keeping the environment in `/opt/venv` ([30.5 Why the packages go in `/opt/venv`](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-uv.html#why-the-packages-go-in-optvenv))

    - **A:** Because the `.venv` holds the actual Python binary and the installed packages, all built for your machine's operating system and CPU architecture. - **Q:** What went wrong when the project folder (with its local `.venv`) was mounted over `/workspace`?
    - **A:** The mount overwrote the image's Linux-built `.venv`; running `uv run` in the container then found your local `.venv`, warned that it was "linked to non-existent Python interpreter," removed it, and created a Linux one in its place. - **Q:** Why set `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` in the `Dockerfile`?
    - **A:** It tells uv to put the project's virtual environment in `/opt/venv` instead of `.venv` inside the mounted project folder, and it must be set before `uv sync` runs. - **Q:** Why does `uv.lock` already contain the package information for other operating systems even though `uv sync` only installed your local one?
    - **A:** Because the lock file records the hashes, locations, and dependencies for all the other operating systems; `uv sync` simply did not install them locally because you do not need them on your machine. When the container builds on Linux, it is those Linux entries in the lock file that are used. *(01:01:22)*

- **Q:** How did the instructor verify that the container now uses `/opt/venv`?
    - **A:** By running `uv run which python` inside the container, which returned `/opt/venv/bin/python`, confirming uv was no longer looking in `.venv`. *(01:06:27)*
