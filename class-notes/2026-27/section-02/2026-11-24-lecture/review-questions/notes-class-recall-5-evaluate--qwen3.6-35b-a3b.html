Dockerfile Optimization and Volume Mounting: review questions, tier 5 — Evaluate

1. Layer Caching and Code Snapshotting (29.1.3 Layer caching)

00:33:35–00:51:21

  • Q: A teammate proposes writing COPY . . at the very top of the Dockerfile to ensure the latest code is always included, then running RUN uv sync --locked afterward. Would you approve this structure for an active project, and why?
    • A: I would reject this plan. The class criterion for efficient builds is that Docker discards cached layers and rebuilds every step below any changed instruction, so placing a frequently updated COPY command at the top forces a full rebuild of all preceding steps like uv sync for even minor code changes. Optimal Dockerfile design places long-running, static setup steps at the top and application code at the bottom to maximize layer caching. (00:40:45)
  • Q: Another teammate suggests copying the entire project directory into the image during the docker build step so the analysis runs entirely inside the container. How do you assess this approach for exploratory data analysis?
    • A: This approach is not acceptable for active development. The instructor warned that snapshotting code into the image during the build process is not scalable because it requires manually remembering to copy files and rebuild the image every time you iterate on your code. Separating compute from source code by using volume mounts is the standard for live, iterative development. (00:50:14)

2. Base Image Selection and Dependency Pinning (29.3 Choosing a base image for your Dockerfile)

00:13:56–00:33:35

  • Q: A teammate argues we should use rocker/r-ver as the base image to save setup time, since it comes pre-installed with R and many packages. Critique this proposal for a pure Python analysis project.
    • A: This proposal should be rejected. The class criterion for choosing a base image is to be respectful of disk space and download times by using the smallest appropriate image; R-specific images carry heavy pre-installed software that a Python project does not need. Using a lightweight OS like ubuntu:24.04 and installing only uv and the required packages keeps the image lean and reproducible. (00:23:55)
  • Q: A colleague wants to keep default lower bounds (>=) in pyproject.toml instead of configuring add-bounds = "exact", arguing that it allows the environment to automatically update to the latest package versions. Would you defend or critique this practice for a long-term data analysis project?
    • A: I would critique this practice. The class criterion states that analysis projects must declare exact versions because long-term ranges like >= risk breaking changes when major versions update, and the lockfile can be regenerated or ignored by other tools. Exact pins in pyproject.toml ensure that the declared dependencies always match what was actually run and allow reviewers to see exact version changes in the diff. (00:30:01)

3. Volume Mounting and Cross-Platform Compatibility (28.1.2 Mounting volumes to containers)

00:51:21–01:06:55

  • Q: A teammate mounts the project folder with -v "$(pwd):/workspace" but leaves uv’s default virtual environment path, relying on the local .venv folder inside the container. Judge whether this setup will work across the team.
    • A: This setup will fail and should not be approved. The class criterion is that a mounted local .venv overwrites the container’s built-in packages and injects host-machine binaries into a Linux environment, causing silent runtime crashes. The Dockerfile must set ENV UV_PROJECT_ENVIRONMENT=/opt/venv to force uv to install packages in an isolated directory that ignores the mounted local environment. (00:59:45)

4. Docker Compose for Reproducible Launches (33 Containers: Docker Compose)

01:06:55–01:20:07

  • Q: A teammate prefers typing out long docker run commands with multiple flags directly in the terminal rather than creating a docker-compose.yml file. How would you justify adopting a compose file for the group project?
    • A: I would recommend adopting a docker-compose.yml file. The class criterion emphasizes that compose files improve reproducibility and maintainability by replacing error-prone, hard-to-edit terminal commands with a version-controlled YAML configuration. Files allow the project to document launch parameters, track changes over time, and standardize how the container is built and run across different machines. (01:11:46)
