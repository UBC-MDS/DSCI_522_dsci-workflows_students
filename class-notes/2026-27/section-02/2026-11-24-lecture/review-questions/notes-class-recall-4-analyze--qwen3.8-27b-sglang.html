  • Q: Break down the first Dockerfile in the 2026-11-24-docker repository and the two docker run forms shown for it: what does CMD ["R"] set, what runs when the image is started with no extra command, and what changes when bash is placed after the image name?
    • A: FROM rocker/r-ver:4.6.2 gives the R base, and CMD ["R"] sets the default command for a container from that image. 4. docker build and the trailing . (29 Customizing and building containers)

00:12:45–00:16:40

  • Q: Separate the important pieces of docker build --tag 2026-11-24-docker . and the first R-image build output: what does --tag name, what does the final . point to, and what part of the terminal output shows that the base layer was already available?

5. --rm, -it, and the default command (28.2.2 Docker run commands)

00:16:40–00:20:05

  • Q: Set the two runs docker run --rm -it 2026-11-24-docker and docker run --rm -it 2026-11-24-docker bash side by side: where each one starts inside the container, which flag makes the terminal interactive, and what happens to changes after you exit?
    • A: Both commands start a container from the same image, but the first uses the image’s CMD ["R"] and starts at the R prompt, while the second replaces that default with bash and starts at the container’s root directory, /. -it gives an interactive terminal, so keystrokes are passed into the container and output is returned to your screen. --rm deletes the container when it exits, so files or changes made inside are discarded and the next run starts from the image again. (00:19:29)

6. Base image and installing uv (30 Python packages with uv in an image)

00:20:05–00:27:40

  • Q: Examine the first three lines of the new Python Dockerfile for the compute environment — FROM ubuntu:24.04, COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/, and WORKDIR /workspace — and say what each contributes to the image before the uv project files are copied.
    • A: FROM ubuntu:24.04 starts from a small Linux base without the R software that the previous image carried. The COPY --from=... line brings in the uv and uvx executables from the pinned ghcr.io/astral-sh/uv:0.13.7 image, so the new machine can manage Python projects. 7. uv project files and exact pins (22 uv: pinning exact versions)

00:27:40–00:34:45

  • Q: Follow cowsay from uv add cowsay to the local hello.py run: which files record the package, which file holds the exact locked version, and why did the instructor want add-bounds = "exact" in pyproject.toml for a long-running analysis?
    • A: uv add cowsay installs the package into the local .venv and writes the dependency into pyproject.toml, while uv.lock records the exact resolved version, cowsay==6.1. By default uv add can write a lower bound such as >=, so a later rebuild or relock might pull a newer major version and break the analysis. add-bounds = "exact" makes future uv add commands write == pins, so pyproject.toml and uv.lock show the same exact version and changes are visible when the pin is edited. (00:32:39)

8. Three package-listing files and uv sync --locked (30 Python packages with uv in an image)

00:35:00–00:39:25

  • Q: Break down the Dockerfile lines COPY pyproject.toml uv.lock .python-version ./ and RUN uv sync --locked: what is each copied file for, where do they land, and what failure does --locked make possible?
    • A: pyproject.toml declares the project’s explicit dependency pin, uv.lock holds the locked package set, and .python-version tells uv which Python version to use. Because WORKDIR /workspace was set, COPY ... ./ places them in /workspace. RUN uv sync --locked installs the Python environment at build time and stops the build if uv.lock no longer matches pyproject.toml, instead of silently updating the lockfile inside the image. (00:39:14)

9. Layer caching and build order (29.1.3 Layer caching)

00:39:25–00:44:30

  • Q: Trace the rebuild after the class added COPY hello.py ./ to the 2026-11-24-docker Dockerfile: which steps in the docker build output are cached, which step is new, and what does that imply about where slow install steps should sit relative to frequently changing files?
    • A: The output shows CACHED for FROM, the uv COPY, WORKDIR, the COPY pyproject.toml uv.lock .python-version ./ step, and RUN uv sync --locked. Only the new COPY hello.py ./ step actually runs, because Docker reuses layers when a layer and the steps above it are unchanged. This is why the class put the slow uv sync --locked step before copying code: editing hello.py should not force the package install to run again. (00:42:40)

10. Copying code into the image versus Git inside the container (30 Python packages with uv in an image)

00:49:36–00:52:15

  • Q: Set two pre-mount approaches for getting actively changing code into the container side by side — copying the code into the image with COPY and rebuilding, versus installing git inside the container and cloning the repository — and say what each approach snapshots or requires.
    • A: Copying code into the image snapshots the files at build time, so every edit requires remembering to update the repository, change the Dockerfile or copied files, and rebuild the image. Installing git inside the container could clone the repository at start, but it introduces credentials such as an SSH key or token and the problem of rebuilding or regenerating keys. Both mix source code into the compute environment, which is why the instructor said the goal is to keep the container to installed software and bring code in separately. (00:52:14)

11. Volume mounts and live files (28.1.2 Mounting volumes to containers)

00:52:15–00:59:35

  • Q: Follow my_secrets.txt through the volume mount demo: which command mounts the local project folder, what changes become visible in the container, and how does that differ from a COPY instruction in the Dockerfile?
    • A: docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash mounts the current local directory at /workspace inside the container. Creating or editing my_secrets.txt on the local machine is immediately visible in the container because the mount is the same live folder, not a copy. A COPY step instead copies files into the image at build time, so later local edits would require rebuilding the image to appear inside it. (00:58:45)

00:59:35–01:07:00

  • Q: Trace the .venv problem in the mounted-container demo: why did uv run hello.py warn about a non-existent macOS Python and recreate .venv, and how does ENV UV_PROJECT_ENVIRONMENT=/opt/venv change what uv run which python reports after the rebuild?
    • A: The local project folder mounted over /workspace exposed the Mac-built .venv, whose Python interpreter did not exist inside the Linux container. uv therefore reported the linked interpreter missing, removed that .venv, and created a Linux one in its place. After adding ENV UV_PROJECT_ENVIRONMENT=/opt/venv before uv sync --locked, uv uses the Linux environment installed at build time in /opt/venv, so uv run which python points to /opt/venv/bin/python and the mounted .venv is left alone.
