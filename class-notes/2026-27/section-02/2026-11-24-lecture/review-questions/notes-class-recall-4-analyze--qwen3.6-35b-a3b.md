## 3. Layer Caching and `Dockerfile` Optimization ([29.1.3 Layer caching](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html#2913-layer-caching))

*00:33:35–00:51:21*

- **Q:** Examine how Docker's layer caching affects build times when modifying a `Dockerfile`. How should you order instructions that install slow dependencies versus instructions that copy frequently changing code, and what is the structural consequence of changing an early instruction?
    - **A:** Docker saves each instruction as a read-only layer and only reruns a step if that step or anything above it has changed since the last build. Because installing packages and running `uv sync` takes significant time, these long, static setup steps should be placed at the top of the `Dockerfile`. Frequently changing code should be copied at the bottom so that editing a script only invalidates the final layer, allowing Docker to reuse all the cached installation layers and rebuild almost instantly. *(00:42:33)*

## 4. Volume Mounting and Cross-Platform Environments ([28.1.2 Mounting volumes to containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-running.html#2812-mounting-volumes-to-containers))

*00:51:21–01:06:55*

- **Q:** Differentiate between copying code into an image and mounting a local volume with `docker run -v`. How does volume mounting solve the problem of active development, and what cross-platform risk does it introduce regarding the `.venv` folder?
    - **A:** Copying code snapshots a static version into the image, requiring a full rebuild for every edit and complicating team collaboration on active scripts. Mounting a local volume with `-v "$(pwd):/workspace"` creates a live, bidirectional sync, allowing edits on the host to appear instantly inside the container without rebuilding. However, this introduces a cross-platform risk because the mounted local `.venv` folder contains macOS binaries that overwrite the container's Linux environment, causing the container to crash or run incompatible executables. *(00:59:52)*

## 5. Docker Compose and Milestone Assignment ([33 Containers: Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*01:06:55–01:20:07*

- **Q:** Set up the components of `docker-compose.yml` side by side with a typical long `docker run` command. How does the compose file reorganize these parameters, and what specific YAML keys replace the `--tag`, `-v`, and interactive shell flags?
    - **A:** A standard `docker run` command bundles the image name, volume mounts, port mappings, and interactive flags into a single long string that is difficult to edit, read, or version control. The `docker-compose.yml` file separates these into a structured YAML layout using keys like `build:` (replacing `--tag` and pointing to the Dockerfile), `volumes:` (replacing `-v` to map host directories), and `ports:` (replacing `-p`). This structure allows developers to launch the container with a single command like `docker compose up` while keeping the configuration readable, auditable, and easily shared with teammates. *(01:11:28)*
