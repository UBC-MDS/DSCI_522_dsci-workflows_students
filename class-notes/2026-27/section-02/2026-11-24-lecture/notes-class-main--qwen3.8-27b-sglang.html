Building a reproducible Docker + uv compute environment

Date: 2026-11-24

Generated by qwen3.8-27b-sglang, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Summary

The session continued the Docker unit from the previous class, opening with a warm-up exercise (re-creating, with a coding agent, the small R-image repository built last time) and a round of course logistics: the course website now hosts the slide decks and summary notes (previously in the UBC student repository), along with per-lecture command histories and question-and-answer topics written at different levels of Bloom’s taxonomy. The instructor also reminded everyone to make sure Docker Desktop is actually running before touching Docker.

The main goal was to build a reproducible compute environment: a Docker image that already contains uv and the project’s Python packages, so someone else can pull it and run the analysis without setting anything up. The instructor constructed this step by step — choosing a small ubuntu:24.04 base, copying uv in from ghcr.io/astral-sh/uv:0.13.7, setting WORKDIR /workspace, copying in pyproject.toml, uv.lock, and .python-version, and installing packages at build time with RUN uv sync --locked. Along the way he covered why analysis projects pin exact versions (==, with add-bounds = "exact"), and why --locked makes the build fail when the lockfile and pyproject.toml drift apart.

The key difficulty was that mounting the live project folder over /workspace hides or overwrites the image’s .venv, and a .venv built on one operating system or CPU architecture is not portable across a team’s machines. The fix is ENV UV_PROJECT_ENVIRONMENT=/opt/venv, which keeps the container’s Linux-built environment in /opt/venv and separates compute (the image) from source code (the mounted folder).

Finally, the instructor introduced docker-compose.yml as a version-controlled file that records the build and run flags (build, image, volumes, ports) instead of a long, hard-to-edit docker run command; the compose demo did not fully work and will be fixed next class. The homework is to produce the Dockerfile that serves as the compute environment for the student’s own analysis, in which uv run quarto render must render the report.

Key takeaways

  • docker build --tag <name> . builds an image from the Dockerfile in the current directory; the trailing . means “here,” and docker run’s -it (interactive terminal) and --rm (delete on exit) are the core flags.
  • CMD sets the default command a container runs; a command after the image name in docker run overrides it (e.g., ... image bash).
  • For an analysis project, pin packages with == in pyproject.toml and set add-bounds = "exact" so uv add writes exact versions; uv.lock records the locked set.
  • Copy only pyproject.toml, uv.lock, and .python-version into the image and run uv sync --locked, so packages install at build time and the build fails if the two files drift out of sync.
  • Set ENV UV_PROJECT_ENVIRONMENT=/opt/venv so the container keeps its Linux-built environment in /opt/venv instead of a .venv that a mounted folder would hide or overwrite.
  • Mount the live project folder with -v "$(pwd):/workspace" to separate source code (the mount) from the compute environment (the image), rather than copying code into the image.
  • Use a docker-compose.yml to record the build and run flags (build, image, volumes, ports) so the launch is version controlled instead of a long copy-pasted docker run.

Knowledge Points

1. Warm-up exercise and course logistics

00:00:00–00:07:15

  • Warm-up exercise: the day opened with a review from last class — create a GitHub repository whose Dockerfile uses the image built in the previous session. Students were told to consult last class’s notes while they tried it, and the instructor would do the same thing with a coding agent (Claude) to show what the agent produced.
  • Course website update: the other instructor (Sky) folded her class’s materials into the course, so the website’s colours and layout changed. Her slide decks are posted in the repo, and the summary notes now live on the course website rather than the UBC student repository; the full transcript and links remain on the private side.
  • Note resources: the repo also holds a per-lecture command-history page and question-and-answer topics written at different levels of Bloom’s taxonomy (from basic factual questions to ones that require knowing what is happening “under the hood”), generated with different language models so students can compare them. The instructor framed all of this as optional and as a template for taking notes in other classes — nothing was required.
  • Docker Desktop: with one student on a Linux machine, the instructor stressed that everyone else must make sure Docker Desktop is actually running before running any Docker command, or the commands will not reach the daemon.

[!WARNING]

Make sure Docker Desktop is actually running before you run any docker command; otherwise the command cannot run. Docker now usually prompts to start the program, but do not rely on that prompt — start it deliberately.

2. Creating the repository with a coding agent

00:07:15–00:11:00

  • The prompt and the result: the instructor asked Claude to create a repository named 2026-11-24-docker with a Dockerfile based on the image from last class. Claude created the folder (in a temp directory on his machine), wrote a Dockerfile, a README.md, and a Makefile, and committed the file (co-authored), for a cost of about fifty cents. The work was committed to the demo repository, whose history has two commits: the warm-up R image and “files from class.”
  • Why the jargon matters: because he named the specific image and the term Dockerfile, the agent did the right thing. The instructor contrasted this with a vague “go make a thing” prompt from someone who has never heard of Docker, which would fail — knowing the tooling vocabulary lets you feed the agent the right information.
  • What the agent ran: the agent ran ordinary shell commands — ls, mkdir, docker — and checked whether docker and the gh command exist and what kind of machine it was on before writing files; the instructor walked through these as the shell commands the agent executes.
  • The default files: Claude wrote the Makefile and README.md on its own because the instructor’s templates usually ask for them. The Dockerfile itself only needed the base-image line to satisfy the exercise, and Claude added CMD ["R"] because it recognized an R container.
  • Templates: because the instructor’s machine is set up with defaults learned in DSCI 522, the agent reproduces those defaults; students with their own templates can start using them with a coding agent as well.

3. Reviewing the Dockerfile: the CMD command (CMD or ENTRYPOINT?)

00:11:00–00:12:45

  • The minimal Dockerfile: to fulfil the warm-up, the Dockerfile only needs the base-image line; for the R image that is FROM rocker/r-ver:4.6.2.
  • CMD ["R"]: Claude added CMD ["R"], which sets the default command. The instructor’s analogy: it is like double-clicking a file and asking “what opens?” — here, R opens by default when you run the container with no other input.
  • Overriding the default: you can always pass a different command when you run the container, so CMD is a default, not a hard requirement.
  • The textbook distinction: this is the CMD vs ENTRYPOINT difference in the book — CMD holds the default that a command after the image name in docker run replaces.

4. Building the image: docker build and the . (Customizing and building containers)

00:12:45–00:16:40

  • docker build --tag <name> .: build the image by giving it a tag (--tag / -t) and the location of the Dockerfile. The tag here was 2026-11-24-docker; the tag can be anything (the instructor joked “you can call it pizza”).
  • The . means “here”: the trailing dot comes from DSCI 521 week 1, where . was “your current location.” docker build looks for a file called Dockerfile (capital D) by default; the dot tells it that default file is in the current directory. It is a required input, like a function argument — you cannot leave it empty.
  • What the build does: running it executes the steps in the Dockerfile. Because the R image was already pulled, the build was fast; if you pointed at a new R version you did not have, the pull step would take seconds to minutes depending on your connection.
  • You need this image for the milestone: the instructor noted the class needs some version of this R image for the week’s milestone.
  • Listing images: docker images shows the images on your machine; the book’s Introduction to containerization covers the image-vs-container distinction and container registries.

5. Running the image: docker run, --rm, -it, and overriding CMD (Using and running containers)

00:16:40–00:20:05

  • docker run --rm -it <image>: --rm makes the container ephemeral — when you exit, it is deleted and any changes inside are undone. -it gives you an interactive terminal (Docker captures what you type and passes it to the container).
  • Default vs overridden command: with docker run --rm -it 2026-11-24-docker, R started by default (because of CMD ["R"]). Adding bash after the image name overrides the default and gives you a normal shell.
  • Starting at the root: inside the container you start at the root of the filesystem and see the operating-system files; there is no dedicated user. For this class the container is a self-contained analysis setup, not a public service, so ownership is not a concern.
  • Ephemeral = safe to experiment: because --rm discards everything on exit, the instructor compared it to “another version of Git that automatically resets all of your changes” — a good place to try a risky install (he used “install PyTorch” as the example) and just restart the container if it goes wrong.

6. Choosing a base image: ubuntu:24.04 and installing uv (Python packages with uv in an image)

00:20:05–00:27:40

  • Switching to a Python base: since no one was working on an R project, the goal was to swap the R base for a Python one and bundle the project’s packages so someone could pull the container and run it with everything already installed. The textbook also provides an image with both R and Python for mixed-language projects (the book’s Python and R in one image chapter); the class demoed the Python path only.
  • ubuntu:24.04 as the base: Docker containers run on some version of Linux; even on a Windows or Mac you are in the Linux world inside a container. ubuntu:24.04 was chosen over the R image mainly because it is smaller — the instructor urged being respectful of others’ disk space (“it is very expensive now because of the AI boom”), noting Alpine is even smaller but needs more manual installs, and that ubuntu is a good general starting point (see Choosing a base image for your Dockerfile).
  • Copying uv in: the COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/ line copies the uv and uvx programs out of the image uv publishes, taken from uv’s Docker guide, pinning uv’s version by tag the way a lockfile pins a package. The ghcr.io/... name is a registry path: think of it as a username, a repository, and a version number.
  • WORKDIR /workspace: this sets the container’s working directory (creating the folder if it does not exist). The working-directory idea comes from DSCI 521 and from R/Python file-loading — commands always need a starting point. After this, a container built from the image lands in /workspace instead of the root.

7. Setting up the uv project locally: pyproject.toml, pinning, and uv.lock (uv: pinning exact versions)

00:27:40–00:34:45

  • Creating the project: uv init --bare creates a minimal pyproject.toml (a name, a version, and requires-python = ">=3.14"). uv add cowsay installs cowsay (6.1) and records it as a dependency; uv sync builds the .venv and installs from uv.lock.
  • What uv add writes by default: by default uv add writes a lower bound, cowsay>=6.1. The exact version is recorded only in uv.lock, so the project declares a range and locks one version.
  • Why pin with ==: the instructor flagged that a lower bound is a liability for a long-running project — if cowsay released 7.0 (a backwards-incompatible change), a rebuild could pull it and break the analysis. Pinning cowsay==6.1 keeps the declared and locked versions identical, and a version only moves when someone edits the pin (which then shows up in a diff).
  • add-bounds = "exact": adding a [tool.uv] table with add-bounds = "exact" makes every future uv add write == instead of >=; the setting lives in pyproject.toml, so the whole team gets the same behaviour.
  • pyproject.toml vs uv.lock: pyproject.toml holds the explicit versions you care about; uv.lock pins everything (including downstream dependencies) but is generated from the toml. The instructor noted that even with a package like pandas pinned, a far-downstream dependency can still update and break things, so you may pin extra packages; you do not have to specify everything, only what matters.
  • Running it locally: hello.py (import cowsay; cowsay.cow("hello, moo.")), then uv sync and uv run hello.py, which prints the ASCII cow.

[!WARNING]

A >= lower bound can silently break a long-running project: if the package’s major version bumps (e.g., 6.x to 7.0), that is usually a backwards-incompatible change and a rebuild can pull it. Pin the packages that matter with == in pyproject.toml.

8. The uv Dockerfile: the three files and uv sync --locked (Python packages with uv in an image)

00:35:00–00:39:25

  • The three files: to install Python and its packages in the image you copy three files into it — pyproject.toml (which packages and which versions), uv.lock (the locked, exact set), and .python-version (which Python). These are “the files that list the packages,” not the code.
  • .python-version: this file tells uv which Python to install (the example holds 3.14). The instructor stressed pinning the Python version too: the Python version determines which package versions are installable, and PyTorch is “almost never compatible with the latest version of Python,” so you often must pin a Python version. It is also how a package author tests against an upcoming Python release.
  • COPY pyproject.toml uv.lock .python-version ./: these land in /workspace because WORKDIR was already set.
  • RUN uv sync --locked: this installs Python and the packages at build time, exactly as you would run uv sync on your machine. The new --locked flag makes the step fail if uv.lock and pyproject.toml are out of sync — the instructor called these “little placeholders” so the build errors out when you want it to, instead of quietly updating the lockfile inside the image. The [tool.uv] block comes from the book’s docker-uv-renv example.

9. Building the image, layer caching, and publishing (Layer caching)

00:39:25–00:44:30

  • Building and inspecting: docker build --tag 2026-11-24-docker . now runs the COPY and RUN uv sync --locked steps; the build visibly stalled at the uv sync step because that is where it installs the environment. docker run --rm -it 2026-11-24-docker bash lands in /workspace, and ls -a shows the copied files plus the .venv.
  • Layer caching: each step in the Dockerfile becomes a cached layer; if a layer and everything above it are unchanged, Docker reuses the cache. That is why people minimize steps (fewer layers, less disk), but nothing is wrong with having more lines.
  • Order matters: any change to a layer forces Docker to rerun that layer and everything below it. So the convention is to put the slow, rarely-changing steps (installing packages) near the top and the frequently-changing steps (copying code) near the bottom — the instructor’s example was that the tidyverse can take ~15 minutes to install, and you do not want to wait that out for a typo in a script. He demonstrated this by copying hello.py last, so a later rebuild was fast because uv sync was already cached.
  • Publishing: once built, you can either hand someone the Dockerfile to build, or publish the image and have them docker pull it so they skip the build entirely.
  • Break: a five-minute break here, then the session continued.

10. The problem with copying code into the image (Python packages with uv in an image)

00:49:36–00:52:15

  • The problem: for an actively developed project (milestones, fast-changing EDA files), copying all the code into the image and rebuilding snapshots the code at one moment. Then you have to worry about who copied what and when, and keep remembering to commit/push and re-copy and rebuild so the image matches.
  • Why it does not scale: the instructor called this “not a very scalable way of dealing with work that is actively being developed.”
  • A valid but inferior alternative: you could install git inside the container and clone the repository at startup; the instructor said that is totally valid and that he has done it (for example, to mimic a student’s terminal), but there is a better approach.
  • The goal — separate compute from source: keep the container holding only the installed software (the packages), and bring the code in some other way. So the COPY hello.py line is removed from the Dockerfile (you still keep the three package-listing files, because without them the image cannot build).

11. Mounting volumes with -v (Mounting volumes to containers)

00:52:15–00:59:35

  • -v mounts a volume: -v (volume) tells Docker to “mount” a folder from your computer into the container when it runs, so the container sees your live files. -v "$(pwd):/workspace" takes the current directory ($(pwd) prints it) and places it at /workspace inside the container; using $(pwd) rather than a hard-coded path keeps the same command working on different machines.
  • It is a live shared drive: changes you make on your computer appear in the container and vice-versa; it is the same folder, not a synced copy like Google Drive. The instructor proved it by creating my_secrets.txt on his machine, seeing it in the container, editing it on the machine (“i eat baby food”), and watching the change appear live in the container.
  • Why not install git: with the mount, you do not need git (or an SSH key / personal access token) inside the container — a problem that would otherwise resurface every time the image is rebuilt with a new key. You are “just you working by yourself” on the same file, so there is no risk of clobbering a teammate’s work.
  • run vs build: you do the mounting in the run process, not the build process — at build time Docker can only COPY (a snapshot), but at run time it can mount a live folder.
  • Windows note: on Windows you may need an extra leading slash in the path (the textbook shows the per-OS forms); in Bash, the $ in $(pwd) pulls in the command’s output.
  • Editor note: the instructor tried nano and vi in the container and neither exists (command not found); Positron sometimes needs you to refresh to notice a file changed on disk.
  • The payoff: you can now verify code in the container (uv run hello.py, or uv run quarto render for your project) with the live files, so you have a test that it works locally and a test that it works in the container.

[!WARNING]

Pay attention to the terminal prompt so you know which machine you are typing on — the instructor was jumping between his local machine and the container, and mixing them up means editing the wrong environment.

12. The .venv problem across platforms and UV_PROJECT_ENVIRONMENT (Why the packages go in /opt/venv)

00:59:35–01:07:00

  • The .venv is not portable: the .venv folder holds the actual Python binary and the installed packages, all built for your machine’s operating system and CPU. A team spans different operating systems (Windows, Mac, Linux) and CPU architectures (amd64 vs arm64) — the instructor counted four to six “different computers” to think about. A .venv built on a Mac will not run on Windows (“you can’t just take my Excel file on my Mac, go to Windows, double click it, and expect it to run”). This is the Building images for several platforms idea: one image is built for one kind of processor.
  • What the mount broke: when the project folder (including its local .venv) was mounted over /workspace, it hid/overwrote the image’s Linux-built .venv; running uv run in the container then warned that the existing .venv was “linked to non-existent Python interpreter” (a macOS aarch64 Python), removed .venv, and recreated it.
  • The uv.lock already knows all platforms: uv.lock records the package locations/hashes for the other operating systems too — uv sync just did not install them for you locally because you do not need them on your machine. The image build, however, is on Linux and must install the Linux set.
  • The fix — ENV UV_PROJECT_ENVIRONMENT=/opt/venv: set this environment variable in the build (it must be set before uv sync) to tell uv to put the project’s virtual environment in /opt/venv instead of .venv inside the project folder. Then the container ignores the mounted local .venv and uses the Linux environment it built, making the image portable across the team’s machines.
  • Verification: after rebuilding, uv run which python inside the container returns /opt/venv/bin/python, confirming the container uses /opt/venv and not the mounted .venv.

[!WARNING]

A local .venv is tied to one operating system and CPU architecture. Mounting your project folder over the image’s /workspace can make uv in the container discard your Mac/Windows .venv and build a Linux one in its place, which then no longer works on your machine. Keep the container’s environment in /opt/venv with UV_PROJECT_ENVIRONMENT.

13. Docker Compose (Containers: Docker Compose)

01:07:00–01:14:05

  • Why Compose: as the docker run command accumulates flags (-v, and -p for ports when using JupyterLab or RStudio on port 8787), it becomes long and painful to edit (you cannot click into the middle of a pasted command to fix it). A docker-compose.yml file records all of the run parameters, and a file is nicer than a command because it can be version controlled and tracked.
  • What the file holds: a docker-compose.yml is a YAML file (like pyproject.toml) that lists, under services:, each container and how to launch it — for this project one service, analysis-env, with build: . (build from the current Dockerfile), image: 2026-11-24-docker (the tag to build into), volumes: (.:/workspace), and optionally ports:.
  • Multiple containers: the instructor noted that one service is “a little bit overkill” here but still useful; compose is really for running several containers at once (microservices, for example a dashboard plus its database) where you want separation between the pieces.
  • The commands: docker compose build reads the file and builds the image; docker compose up starts the container (named after the folder and service, e.g., 2026-11-24-docker-analysis-env-1); docker compose up --detach (up -d) starts it in the background so the prompt returns.
  • It did not work live: in this session docker compose up created the container but it immediately exited with code 0, and the follow-on exec calls failed (“service not running”); the instructor said he would fix the demo next class. The point of the file is that it is reading all of those docker run flags and applying them.

14. The homework assignment: a Dockerfile as compute environment

01:14:05–01:17:00

  • The task: this week’s homework is to create the Dockerfile that is the compute environment for your analysis — essentially a copy of the example built in class (see the demo repository). The container should replicate your compute environment, be able to mount the folders that need mounting, and run uv run quarto render so that your report renders inside the container.
  • What you already have: you already have the analysis running on your local machine and a pyproject.toml; the new part is making sure the container builds and the report renders in it.
  • How it is graded: the TA takes your repository, builds the container, and runs the analysis in it. The overarching goal is a reproducible compute environment: hand someone the Dockerfile (or an image) and the analysis is fully contained.
  • Optional extras: you may add other RUN commands for things the container lacks (the instructor noted it has no text editor, so you might add one to edit/inspect files), or the system tools some packages need (his example was geospatial analysis, which needs many system tools and the underlying libraries those Python packages are built on). The requirement is that you understand why you are installing each thing.
  • Main deliverable: the Dockerfile is the most important thing for this week; the instructor will get Compose working in a future class.

15. Docker Compose outside the class (Containers: Docker Compose)

01:17:00–01:20:10

  • Compose is a general skill: many open-source tools ship a docker-compose.yml, so if you know your way around Docker you can stand up whole applications with docker compose up — no need to learn each tool’s install steps.
  • Example — Actual Budget: a personal-finance app (similar to Firefly III) that you can run on your own computer or “a laptop in your closet.” Its compose file defines one service (actual-server), an image, ports, environment variables, volumes, and a health check; docker compose up -d downloads the image, runs the software, and exposes the port, giving you your own personal-finance app in a browser.
  • More examples: the instructor listed Jellyfin (serve movies/media), N8N (AI automation), and a recipe app, all of which “run like RStudio, just running on a port in a browser”; you just have to find a machine to run them on (an old laptop or a paid cloud machine).
  • Tie-back: the same compose-file skill used for the class’s compute environment is the skill used to deploy these apps; Docker is not only for reproducible analysis.

Building and running the R image

docker build --tag 2026-11-24-docker .          # build from the Dockerfile here; `.` = current directory
docker run --rm -it 2026-11-24-docker           # R starts by default (CMD ["R"])
docker run --rm -it 2026-11-24-docker bash      # pass `bash` to override CMD and get a shell

--rm removes the container on exit and discards any changes; -it gives an interactive terminal; a command after the image name replaces the image’s default CMD.

Creating the uv project on the local machine

uv init --bare        # minimal pyproject.toml (no app code)
uv add cowsay         # add cowsay==6.1 and create uv.lock
uv sync               # create .venv and install from uv.lock
uv run hello.py       # run the script in the project environment (prints the cow)

Building the uv image and mounting the project folder

docker build --tag 2026-11-24-docker .                            # now runs uv sync --locked inside
docker run --rm -it 2026-11-24-docker bash                       # lands in /workspace
docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash # mount current dir at /workspace
# inside the container:
uv tree                  # show the dependency tree (cowsay v6.1)
uv run which python      # -> /opt/venv/bin/python (after ENV UV_PROJECT_ENVIRONMENT=/opt/venv)

-v "$(pwd):/workspace" mounts your live project folder, and $(pwd) keeps the path portable across machines; the ENV UV_PROJECT_ENVIRONMENT=/opt/venv line in the Dockerfile keeps the container’s Linux environment out of the mounted folder.
