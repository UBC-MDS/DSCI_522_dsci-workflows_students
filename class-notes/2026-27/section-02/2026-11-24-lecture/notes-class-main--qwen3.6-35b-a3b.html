Docker Workflows with uv and Docker Compose

Date: 2026-11-24

Generated by qwen3.6-35b-a3b, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Summary

This session focused on building reproducible compute environments using Docker and the uv package manager. The instructor began by reviewing foundational Docker concepts, including building images and running containers interactively, after scaffolding a demo repository with an AI coding agent. The lecture then transitioned to constructing a Python-focused Dockerfile starting from a lightweight ubuntu:24.04 base image. Students learned how to install uv inside the image, manage dependency pins with pyproject.toml, and use the --locked flag to enforce reproducibility during the build process.

A significant portion of the class addressed live development workflows. The instructor demonstrated why copying code directly into an image is counterproductive for active projects and introduced volume mounting (-v) to sync the local filesystem with the container. This led to a critical cross-platform compatibility issue: mounting a local .venv folder overwrites the container’s environment and injects macOS binaries into a Linux system. The solution involved setting the UV_PROJECT_ENVIRONMENT environment variable to force uv to install packages in an isolated directory (/opt/venv). Finally, the session introduced docker-compose.yml to manage long docker run commands declaratively and outlined the requirements for the current week’s milestone assignment.

Key takeaways

  • Use lightweight base images like ubuntu:24.04 to keep container sizes small and reduce download times.
  • Configure add-bounds = "exact" in pyproject.toml so uv add writes exact version pins (==) instead of lower bounds (>=).
  • Always run uv sync --locked in a Dockerfile to fail the build immediately if uv.lock and pyproject.toml are out of sync.
  • Order Dockerfile instructions to place long, static setup steps at the top and copy application code last, maximizing Docker layer caching.
  • Use -v "$(pwd):/workspace" to mount your local code into a container for live editing without rebuilding the image.
  • Set ENV UV_PROJECT_ENVIRONMENT=/opt/venv to prevent mounted local virtual environments from breaking the container’s cross-platform Python binaries.
  • Replace lengthy docker run flags with a docker-compose.yml file to improve readability, documentation, and reproducibility.

Knowledge Points

1. Docker and AI-Assisted Setup Review (28 Using and running containers)

00:00:00–00:13:56

  • AI-assisted scaffolding: The instructor used Claude Code to generate a new GitHub repository containing a Dockerfile, Makefile, and README.md. The agent correctly inferred the need for a Docker-based setup and initialized it with the rocker/r-ver:4.6.2 image.
  • Reviewing local images: The docker images command lists all container images pulled or built on the machine. It displays the image name, ID, disk usage, and content size, which helps manage local storage.
  • Building the image: docker build --tag <name> . reads the Dockerfile in the current directory (.) and compiles the layers into a named image. The . argument is required because Docker needs a context to look for the default Dockerfile and build instructions.
  • Running containers interactively: docker run --rm -it <image> launches the container. The --rm flag ensures the container is automatically deleted when it exits, preventing orphaned processes. The -it flags allocate a terminal and capture input/output.
  • Overriding default commands: The initial Dockerfile contained CMD ["R"], which automatically starts the R interpreter. Appending bash to the docker run command overrides this default, providing a standard shell prompt for exploration.
  • Docker Desktop requirement: Students must ensure Docker Desktop is actively running before executing any Docker commands. If it is not, commands will silently fail or return unhelpful errors.

[!WARNING]

Always keep Docker Desktop running. If it is closed, the terminal will return vague errors when you attempt to pull, build, or run containers.

2. Building a Python Container with uv (30 Python packages with uv in an image)

00:13:56–00:33:35

  • Choosing a base image: The instructor switched from an R-specific image to ubuntu:24.04 to create a leaner, more generic Linux environment. Ubuntu is a standard starting point that balances size with package availability.
  • Installing uv inside the image: Rather than installing uv via system package managers, the Dockerfile uses a multi-stage copy: COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/. This pulls the exact uv binaries from Astral’s official registry and places them in the container’s PATH.
  • Setting the working directory: WORKDIR /workspace sets the default directory for all subsequent commands and interactive sessions. Starting inside a dedicated project folder avoids navigating the system root and keeps the environment organized.
  • Pinning dependencies: In pyproject.toml, the [tool.uv] table includes add-bounds = "exact". This configuration forces uv add to write strict version pins (e.g., "cowsay==6.1") rather than lower bounds (>=), ensuring long-term reproducibility for the analysis.
  • Lockfile verification: The Dockerfile includes RUN uv sync --locked. The --locked flag instructs uv to strictly compare the lockfile against pyproject.toml. If they are out of sync, the build halts with an error, preventing the image from being built with mismatched dependencies.
  • Verifying the environment: After building, running uv run hello.py inside the container confirms that uv successfully resolved the environment and executed the script using the image’s Python interpreter.

3. Layer Caching and Dockerfile Optimization (29.1.3 Layer caching)

00:33:35–00:51:21

  • How Docker layers work: Each instruction in a Dockerfile creates a new read-only layer. Docker caches these layers and reuses them if the instruction and its inputs have not changed since the last build.
  • The cost of rebuilding: If you modify a RUN command or add a COPY instruction early in the file, Docker must discard the cached layer and rebuild every subsequent layer. This can add significant time to the build process.
  • Optimizing instruction order: To minimize rebuild times, place long-running, static setup steps (installing system packages, running uv sync) at the top of the Dockerfile. Place frequently changing instructions (copying application code, hello.py) at the bottom.
  • The snapshot problem: Copying your code directly into the image during the build process snapshots a static version of your files. When you edit a script on your host machine, the container still contains the old version unless you rebuild the entire image. This defeats the purpose of rapid iteration during exploratory data analysis.

4. Volume Mounting and Cross-Platform Environments (30.5 Why the packages go in /opt/venv)

00:51:21–01:06:55

  • Mounting local volumes: Instead of copying code into the image, use the -v flag during docker run: docker run -v "$(pwd):/workspace" <image>. This mounts your local project directory directly into the container’s filesystem, creating a live, bidirectional sync.
  • Live code editing: Changes made to files on your host machine appear instantly inside the container. You can edit scripts, run tests, and debug without ever rebuilding the image.
  • Cross-platform binary incompatibility: By default, uv stores the virtual environment in a local .venv folder. When this folder is mounted into the container, it overwrites the container’s built-in packages. The Linux container then attempts to execute macOS-compiled binaries, leading to crashes and errors.
  • Isolating the container environment: To solve this, the Dockerfile sets ENV UV_PROJECT_ENVIRONMENT=/opt/venv. This forces uv to install packages in a completely separate directory outside the mounted workspace. The container ignores your local .venv and uses only the Linux-compiled packages it built during the image creation.
  • Verifying the fix: Running uv run which python inside the mounted container returns /opt/venv/bin/python, confirming that the environment variable successfully redirected uv to the correct, isolated virtual environment.

[!WARNING]

Never allow a mounted local .venv to overwrite the container’s environment. The container will attempt to run host-machine binaries (e.g., macOS/Windows) on Linux, causing silent failures or crashes. Always redirect the virtual environment to an unmounted path like /opt/venv.

5. Docker Compose and Milestone Assignment (33 Containers: Docker Compose)

01:06:55–01:20:07

  • Managing long commands: Typing out full docker run commands with multiple volume mounts, port forwards, and environment variables is error-prone and difficult to maintain. docker-compose.yml consolidates these parameters into a readable YAML file.
  • Compose file structure: The file begins with services:, under which each container is defined. Properties like build: . point to the Dockerfile, volumes: maps the local directory, and ports: handles network routing.
  • Essential Compose commands:
    • docker compose build: Reads the compose file and builds the image.
    • docker compose up: Starts the container according to the defined parameters.
    • docker compose exec <service> bash: Opens an interactive shell inside a running container without leaving the compose context.
  • Industry applications: Docker Compose is standard practice outside academia for deploying complex applications. It is used to spin up databases, web servers, and automation tools (like personal finance or media servers) with a single, version-controlled configuration file.
  • Milestone requirements: Students must create a Dockerfile that replicates their project’s compute environment. The container must use volume mounting for the code and successfully execute uv run quarto render to generate the final report. TAs will grade submissions by pulling the repository, building the image, and running the analysis inside the container.

Commands from class

Reviewing local Docker images

docker images                  # List all locally available container images
docker run --rm -it <image>    # Run a container interactively, deleting it on exit
docker run --rm -it <image> bash # Override default CMD to enter a bash shell

Setting up a Python environment with uv

uv init --bare                 # Initialize a bare Python project
uv add cowsay                  # Add a dependency; creates pyproject.toml and uv.lock
uv run hello.py                # Run a Python script using the local uv environment

Building and running a Python container

docker build --tag <name> .    # Build the image using the Dockerfile in the current directory
docker run --rm -it <image> bash # Enter the container to inspect files
uv run hello.py                # Execute the script inside the container

Mounting local volumes

docker run --rm -it -v "$(pwd):/workspace" <image> bash
                               # Mount the host's current directory into /workspace
uv run which python            # Verify the virtual environment path inside the container

Testing Docker Compose

docker compose build           # Build the image using parameters from docker-compose.yml
docker compose up              # Start the container in the foreground
docker compose exec <service> bash # Open a terminal inside a running compose service

What went wrong live

  • docker compose up exited immediately: The container had no long-running process attached to it (like an SSH server), so Docker shut it down right after starting. The instructor noted this demo requires a background process to keep the container alive and planned to fix it for the next class.
  • Typo in the detach flag: The instructor typed docker compose up --detatch, which Docker Compose rejected as an unknown flag. The correct spelling is --detach.
