Docker, uv, and Docker Compose for a Reproducible Analysis Environment

Date: 2026-11-24

Generated by qwen3.8-27b-sglang, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Summary

This lecture continued the Docker part of DSCI 522 by turning a project’s Python environment into a reproducible container. The session began with a warm-up in which a coding agent had created a new repository containing a Dockerfile based on rocker/r-ver:4.6.2. Daniel reviewed docker build and docker run, including the meaning of the trailing ., the --rm and -it flags, and how a command after the image name replaces the image’s default CMD.

The main part of the lecture built an Ubuntu-based image for a uv Python project. The class copied uv into the image, set WORKDIR /workspace, copied pyproject.toml, uv.lock, and .python-version, and ran uv sync --locked. The lecture then separated the code from the installed environment by mounting the project folder into /workspace with docker run -v "$(pwd):/workspace". A key warning was that the project’s .venv should not live inside the mounted folder, because the host’s virtual environment can hide, overwrite, or break the container’s Linux environment. The class fixed this by setting UV_PROJECT_ENVIRONMENT=/opt/venv in the Dockerfile.

The session finished with Docker Compose. Daniel introduced docker-compose.yml as a version-controlled replacement for long docker build and docker run commands. The class built and started a service with docker compose, but the live demo container exited immediately; Daniel said he would fix the demo next class. The assignment for the week is to create a Dockerfile that reproduces your analysis compute environment, mount the project folder, and run the analysis inside the container.

Knowledge Points

1. Course resources and session setup

  • Course website update: Daniel said the class course website now looks different because another instructor folded her slide decks and summary notes into the student repository. He described the summary notes as available but not required; the transcript and link remained in the private side.

  • Docker Desktop warning: On machines that use Docker Desktop, Docker Desktop must actually be running before Docker commands work. Daniel warned that if it is not running, Docker commands can fail or prompt you to start Docker.

  • Demo repository: The live class used the demo repository 2026-11-24-docker. Its first commit was the warm-up: a Dockerfile that started from rocker/r-ver:4.6.2:

    FROM rocker/r-ver:4.6.2

CMD ["R"]

    The coding agent also created a README.md and a Makefile.

  • Prompting coding agents: Daniel noted that giving the agent useful jargon matters. Saying “create a Dockerfile” without context may not be enough; saying the exact image, language, and desired default command makes the result more reliable.

2. Docker image and container review

  • Image vs container: An image is the buildable snapshot; a container is a running or stopped instance of that image. See the textbook’s 27.7 Image vs container?.
  • docker images: Lists local images and shows DISK USAGE and CONTENT SIZE. The live output included 2026-11-24-docker:latest, rocker/r-ver:4.6.2, ubuntu:24.04, and other images.
  • docker build: Builds an image from a Dockerfile.
    • docker build --tag 2026-11-24-docker .
    • --tag names the local image.
    • The final . is the build context, usually the current directory. Daniel stressed that it is not punctuation; it means “look for the Dockerfile here.”
  • docker run:

    • --rm removes the container when it exits, so changes inside are not preserved.

    • -it gives interactive terminal access.

    • A command after the image name replaces the image’s default CMD.

    • Example:

      docker run --rm -it 2026-11-24-docker
docker run --rm -it 2026-11-24-docker bash

      The first command ran the default CMD ["R"]; the second replaced it with bash.

  • Default command analogy: Daniel compared CMD ["R"] to double-clicking a file: it says what opens by default when the container is run with no other command.
  • Container starting point: Running bash in the warm-up R container started at /, the root of the container’s Linux filesystem. The home directory was empty.
  • Ephemeral containers: Because --rm deletes the container on exit, changes inside the container are discarded. Daniel compared this to an automatic reset and recommended containers for testing risky installs.

3. uv project files and exact version pins

  • uv init --bare: Creates a minimal uv project, including pyproject.toml.

  • uv add cowsay: Adds a package and updates the project files. The live output showed:

    Using CPython 3.14.3
Creating virtual environment at: .venv
Resolved 2 packages in 126ms
Installed 1 package in 7ms
 + cowsay==6.1

  • pyproject.toml: Declares the project name, version, Python requirement, and dependencies. The class version pinned cowsay==6.1 and set:

    [tool.uv]
# `uv add` writes an exact version (==)
add-bounds = "exact"

  • Exact pins vs lower bounds:

    • cowsay>=6.1 allows newer versions, including potentially breaking major-version changes.
    • cowsay==6.1 records the exact version the analysis was run with.
    • Daniel said data analysis projects should usually pin exact versions, while packages being published to other people should usually declare ranges.
    • uv add can write lower bounds by default; add-bounds = "exact" makes it write ==.
    • Existing lower bounds do not automatically convert; you may need to re-add a package with an exact version.

  • uv.lock: Records the locked dependency graph. It can contain information for multiple operating systems, but uv sync installs only what the current system needs.

  • .python-version: Tells uv which Python version to use for the project. The demo file contained:

    3.14

    Daniel emphasized that Python version matters because some packages, such as PyTorch, are not always compatible with the newest Python release.

  • uv run hello.py: Runs a Python script inside the project’s uv environment. The demo script used cowsay to print a short message.

4. Building a uv project image

The class built the following Dockerfile in the demo repository:

FROM ubuntu:24.04

# how to install uv
COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/

WORKDIR /workspace

ENV UV_PROJECT_ENVIRONMENT=/opt/venv
COPY pyproject.toml uv.lock .python-version ./
RUN uv sync --locked
  • FROM ubuntu:24.04:
    • Starts from Ubuntu Linux.
    • Daniel said most Docker containers run some version of Linux even when the host is Windows or macOS.
    • Ubuntu was chosen as a reasonable starting point; smaller images such as Alpine exist but may require installing more system tools.
  • COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/:
    • Copies the uv and uvx programs from the official uv image.
    • The tag 0.13.7 pins the uv version, similar to how a lockfile pins a package.
    • This line follows uv’s Docker installation guide.
  • WORKDIR /workspace:
    • Sets the working directory for later build steps and for containers started from the image.
    • The project folder will be mounted at /workspace.
  • COPY pyproject.toml uv.lock .python-version ./:
    • Copies only the files needed to install the environment.
    • Does not copy the analysis code.
    • This supports layer caching: changing code files does not force package installation to rerun.
  • RUN uv sync --locked:
    • Installs Python and the packages from uv.lock into the image.
    • --locked makes the build fail if uv.lock is out of sync with pyproject.toml.
    • Daniel described this as a deliberate placeholder: if the files do not match, the build should stop.
  • Layer caching:
    • Each Dockerfile instruction creates a layer.
    • If a layer and all layers above it are unchanged, Docker can reuse the cached layer.
    • Changing one layer reruns that layer and every layer below it.
    • Slow, rarely changing steps such as installing software should go near the top; frequently changing files should go near the end.
    • Daniel said starting with more Dockerfile lines is not wrong; layer order is an efficiency concern, not a correctness requirement.
  • Related textbook sections:
    • 29 Customizing and building containers
    • 29.1.3 Layer caching
    • 30 Python packages with uv in an image
    • 22 uv: pinning exact versions

5. Separating code from the installed environment

  • Problem with copying code into the image:
    • If the Dockerfile copies all analysis files into the image, every code change requires rebuilding the image.
    • The image becomes a snapshot of the code at build time.
    • This makes active EDA or group work harder because the container may contain stale code.
  • Mounting the project folder:
    • docker run -v "$(pwd):/workspace" ... mounts the current host folder into /workspace in the container.
    • The mount is live: files edited on the host are visible in the container, and files changed in the container can affect the host folder.
    • Daniel compared it to a shared drive, not a Google Drive sync: you are working on the same files.
    • The demo used my_secrets.txt to show that editing the file on the host changed what cat my_secrets.txt printed inside the container.
  • Why mount instead of installing Git in the container:
    • Installing Git inside the container raises SSH key and token problems.
    • The container would need credentials for git pull / git push.
    • A mounted volume avoids needing Git credentials inside the container for normal development.
  • Editor refresh:
    • Daniel warned that Positron may not immediately notice a file changed on disk.
    • You may need to refresh the file in the editor after external changes.
  • Build vs run:
    • COPY happens during docker build; it snapshots files into the image.
    • -v happens during docker run; it mounts a live host folder into the container.

6. Keeping the virtual environment in /opt/venv

  • The problem:
    • By default, uv uses a .venv folder inside the project.
    • If the project folder is mounted at /workspace, the host’s .venv can hide or replace the image’s environment.
    • The host .venv may contain Python binaries and packages for your host operating system, not for the container’s Linux environment.
    • Daniel compared this to copying a Mac .venv onto a Windows machine and expecting it to work.
  • Live warning from the terminal:

    • Before the ENV fix, uv run inside the mounted container reported that it was ignoring an existing virtual environment linked to a non-existent Python interpreter.

    • It then printed:

      Removed virtual environment at: .venv
Creating virtual environment at: .venv

    • This is the dangerous behavior to avoid: the container can remove or overwrite the host-side .venv in the mounted project folder.

  • Fix:

    • Add:

      ENV UV_PROJECT_ENVIRONMENT=/opt/venv

      before RUN uv sync --locked.

    • This tells uv to store the project virtual environment at /opt/venv, outside the mounted /workspace folder.

    • The image builds the Linux packages into /opt/venv.

    • When the project folder is mounted, uv should ignore the mounted .venv and use /opt/venv.

  • Checking the environment:

    • uv tree listed the project and cowsay v6.1.

    • uv which python failed because which is not a uv subcommand.

    • uv run which python printed:

      /opt/venv/bin/python

    • That confirmed the container was using the image-built environment.

  • Portability:
    • Teams may have different operating systems and CPU architectures, for example AMD/Intel amd64 and Apple silicon arm64.
    • The container should contain a Linux-compatible environment.
    • Keeping the environment inside the image, rather than in the mounted project folder, makes the image more portable.

7. Docker Compose

  • Purpose:

    • Docker Compose stores container launch parameters in a YAML file.
    • It replaces long, repeated docker build and docker run commands.
    • The file can be version-controlled and shared.

  • File name: docker-compose.yml.

  • Class file:

    services:
  analysis-env:
    build: .
    image: 2026-11-24-docker
    volumes:
      - .:/workspace
    • services: lists the containers to run.
    • analysis-env is the service name.
    • build: . builds from the Dockerfile in the current directory.
    • image: 2026-11-24-docker names the image.
    • volumes: - .:/workspace mounts the current folder into the container.

  • Common commands:

    • docker compose build: builds the image from the compose file.
    • docker compose up: starts the service.
    • docker compose up --detach: starts the service in the background.
    • docker compose ps: lists running compose containers.
    • docker compose exec <service> bash: runs a command inside a running container.

  • Live demo issue:

    • docker compose up created the container and printed:

      Attaching to analysis-env-1
analysis-env-1 exited with code 0

    • The container did not stay running.

    • Daniel said he would fix the demo for next class.

  • Compose outside the course:

    • Many open-source applications ship their own compose files.
    • Examples mentioned included Actual Budget, Jellyfin, and n8n.
    • In those cases, docker compose up can start a complete software stack, not just an analysis environment.

  • Related textbook section: 33 Containers: Docker Compose

8. Week’s assignment

  • Goal: Create a Dockerfile that is the compute environment for your analysis.
  • Expected behavior:
    • The container should replicate the compute environment needed for your project.
    • You should be able to mount the necessary folders into the container.
    • You should be able to run the analysis, for example with uv run quarto render, and have the report render inside the container.
  • Grading approach: Daniel said the TAs would take the repository, build the container, and try to run the analysis in the container.
  • Optional additions:
    • You may need extra tools inside the container, such as a text editor.
    • Some analyses may need system dependencies, for example geospatial tooling.
    • Extra RUN commands are acceptable if you understand why they are needed.
  • Assignment page: The course materials live in the student repository; no exact due date was stated in the session.

R version 4.6.2 (2026-10-29) -- "Diversified Portfolio"

docker run --rm -it 2026-11-24-docker bash

Inside the container, pwd printed /, and ls showed the Linux system directories. The home directory was empty.

Create the uv project on the host

uv add cowsay

ls

The class wrote a small hello.py that imported cowsay and called cowsay.cow. The important project files after this step were pyproject.toml, uv.lock, .python-version, and hello.py.

Build the Ubuntu image with uv

docker build --tag 2026-11-24-docker .
docker run --rm -it 2026-11-24-docker bash
# at container shell:
pwd
ls
ls -a
exit

The container started in /workspace because of WORKDIR /workspace. It contained the copied project metadata files and the virtual environment created during the build.

Copy code into the image

docker build --tag 2026-11-24-docker .
docker run --rm -it 2026-11-24-docker bash
# at container shell:
ls
uv run hello.py
exit

This version of the Dockerfile copied hello.py into the image. Daniel later removed that copy because active code should usually be mounted, not baked into the image.

Mount the project folder into the container

docker build --tag 2026-11-24-docker .
docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash
# at container shell:
ls
cat my_secrets.txt
uv run hello.py
ls -alh
python
exit

The mount made the host project folder visible at /workspace. Editing my_secrets.txt on the host changed what cat my_secrets.txt showed inside the container. python was not available as a bare command; uv run was the supported way to use the project’s Python environment.

Rebuild with UV_PROJECT_ENVIRONMENT=/opt/venv

docker build --tag 2026-11-24-docker .
docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash
# at container shell:
which uv
uv tree
uv run which python
exit

This confirmed that uv was using the image-built environment at /opt/venv, not the mounted host .venv. uv tree printed:

2026-11-24-docker v0.1.0
└── cowsay v6.1

uv run which python printed:

/opt/venv/bin/python

Use Docker Compose

docker compose build
docker compose up
docker compose ps
docker compose exec analysis-env bash

docker compose build read docker-compose.yml and built the image. docker compose up created the network and container, but the live demo container exited immediately. docker compose exec analysis-env bash failed because the service was not running.

What went wrong live

  • docker compose up did not keep the container running:

    Attaching to analysis-env-1
analysis-env-1 exited with code 0

    The demo docker-compose.yml did not keep a long-running process alive, and Daniel said he would fix the demo for the next class.

  • Typo in detach flag:

    docker compose up --detatch

    Docker printed:

    unknown flag: --detatch

    The correct flag shown in the course materials is --detach, with the common short form -d.

  • uv which python is not a uv command:

    uv which python

    printed:

    error: unrecognized subcommand 'which'

    The working command was:

    uv run which python

  • No text editor inside the Ubuntu container:

    nano my_secrets.txt
vi my_secrets.txt

    Both reported command not found. Daniel used this to say that extra tools can be installed with additional RUN commands when the workflow requires them.

  • Mounted .venv warning before the /opt/venv fix: uv run inside the container warned that it was ignoring an existing virtual environment linked to a non-existent Python interpreter and then printed:

    Removed virtual environment at: .venv
Creating virtual environment at: .venv

    This demonstrated why the project virtual environment should live outside the mounted project folder.

  • Typo in ls flags:

    ls 0alh

    produced:

    ls: cannot access '0alh': No such file or directory

    The corrected command was:

    ls -alh

  • Compose exec used the wrong service name or a stopped service:

    docker compose exec analysis-env bash
docker compose exec 2026-11-24-docker bash

    The first failed because the analysis-env service was not running after up; the second used the image/repository name instead of the running service name.

  • Q: A student noticed that docker compose up did not keep the container running. A: The terminal showed the container attaching and then exiting with code 0. The class had not yet provided a long-running command for the compose service, and Daniel said he would fix the demo for the next class.
