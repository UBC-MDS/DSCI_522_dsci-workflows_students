## Knowledge Points

### 1. Dockerfile Layer Caching and Structure

- **Layer caching**: Every instruction in a `Dockerfile` creates a new image layer. Docker reuses cached layers if their inputs haven't changed. To optimize builds, place heavy, infrequently changing steps (e.g., installing system packages or running `uv sync`) at the top, and place frequently changing steps (e.g., `COPY`ing project code) at the bottom. Changing a middle step forces a rebuild of all subsequent layers, which can be slow for large dependencies.
- **`WORKDIR`**: Sets the container's working directory. Using `WORKDIR /workspace` ensures that subsequent `COPY`, `RUN`, and `CMD` commands execute relative to that path, and it becomes the default directory when the container starts.

### 2. Pinning Dependencies with `uv`

- **`pyproject.toml` declarations**: This file declares dependencies. By default, `uv add` writes lower bounds (e.g., `pandas>=3.1.1`). Lower bounds are flexible but risky for long-running analyses because a future `uv lock --upgrade` could pull in a breaking major version.
- **Exact pins (`==`)**: Data analysis projects should use exact pins (e.g., `cowsay==6.1`) to guarantee reproducibility. Configure `uv` to write exact pins automatically by adding `[tool.uv]` `add-bounds = "exact"` to `pyproject.toml`.
- **`uv.lock` vs `pyproject.toml`**: `uv.lock` always records exact versions and is used for actual installations. However, external tools (like `pip` or CI systems) and humans reading the code reference `pyproject.toml`. Exact pins in `pyproject.toml` ensure the declared versions match the locked versions, making the analysis transparent to reviewers.

### 3. Cross-Platform Virtual Environments in Containers

- **The mounting conflict**: When running `docker run -v "$(pwd):/workspace"`, the host's `.venv` folder is mounted into the container, hiding the container's own `.venv`. If `uv sync` runs inside the container, it will recreate the environment for the host's OS/architecture, breaking cross-platform compatibility.
- **Fix with `ENV UV_PROJECT_ENVIRONMENT`**: Add `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` to the `Dockerfile` before running `uv sync`. This forces `uv` to install packages in `/opt/venv` (outside the mounted directory), preserving the Linux-compiled packages and ignoring the host's `.venv`.

### 4. Volume Mounting for Live Development

- **`-v "$(pwd):/workspace"`**: Mounts the host's current directory into the container at `/workspace`. This creates a live sync, meaning edits to code on the host are immediately visible inside the container without rebuilding the image.
- **Separation of concerns**: Instead of `COPY`ing entire projects into the image (which requires constant rebuilds and snapshots), volume mounting separates the static compute environment (built in the image) from the dynamic source code (mounted at runtime). This mirrors how you would work on your local machine while keeping dependencies isolated.

### 5. Docker Compose for Reproducible Commands

- **`docker-compose.yml`**: A YAML file that replaces long, error-prone `docker run` command-line flags. It stores parameters like `build`, `image`, `volumes`, and `ports` in a version-controlled file, making workflows easier to document, share, and reproduce.
- **Usage**: Run `docker compose build` to build images and `docker compose up` to start containers. Compose reads paths natively across OSes, avoiding shell-specific syntax issues like `/$(pwd)` in Git Bash.

## Commands from class

### Setting up the local uv project

```bash
uv init --bare          # Initialize an empty Python project
uv add cowsay           # Add a dependency; with `add-bounds = "exact"`, writes `==`
uv sync                 # Install dependencies into .venv
uv run hello.py         # Execute a Python script using the project's environment
```

*These commands set up the local development environment that will later be replicated inside the container.*

### Building the Docker image

```bash
docker build --tag 2026-11-24-docker .   # Build image from Dockerfile in current directory
docker run --rm -it 2026-11-24-docker    # Launch container interactively; defaults to CMD ["R"]
docker run --rm -it 2026-11-24-docker bash  # Overwrite CMD to get a bash shell
```

*The `.` at the end specifies the build context (current directory). `--tag` names the image. `--rm` removes the container after exit. Overwriting the default command with `bash` is necessary when the image lacks a default shell or when you want direct terminal access.*

### Running with volume mounts

```bash
docker run --rm -it -v "$(pwd):/workspace" 2026-11-24-docker bash
```

*Mounts the host's current directory to `/workspace` inside the container. Enables live code editing and running `uv run` against local files without rebuilding the image.*

### Managing with Docker Compose

```bash
docker compose build   # Builds using docker-compose.yml
docker compose up      # Starts the container(s) defined in the compose file
docker compose ps      # Lists running containers for the project
```

*Consolidates build and run flags into a single YAML configuration. `docker compose up` reads all volume and port mappings defined in the compose file.*

## Questions

- **Q:** What happens if a container's `Dockerfile` doesn't specify a `CMD` or `ENTRYPOINT` command?
  **A:** The container will start and immediately exit because there's no default process to run. To interact with such a container, you must overwrite the command at runtime by appending a shell (e.g., `docker run --it <image> bash`) to get a terminal session.
- **Q:** How do we prevent the host's local virtual environment from interfering with the container's packages when using volume mounts?
  **A:** By setting `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` in the `Dockerfile` before running `uv sync`. This redirects all package installations to `/opt/venv` inside the container, keeping them separate from the host's `.venv` folder that gets mounted over `/workspace`. This ensures the container always uses packages compiled for Linux.
- **Q:** Why do we need a `.python-version` file if `uv.lock` already specifies Python dependencies?
  **A:** `uv.lock` pins exact package versions, but the `.python-version` file explicitly tells `uv` which Python interpreter version to use when setting up the environment. This is crucial when packages have strict Python version requirements (e.g., PyTorch is rarely compatible with the absolute latest Python release) and ensures consistent environments across different machines.
