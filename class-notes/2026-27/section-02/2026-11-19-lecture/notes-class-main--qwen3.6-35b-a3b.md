### 2. Git Branching and Pull Requests (*00:06:05–00:25:29*)

- **Branch workflow**: Always ensure you are on the intended branch before committing. Use `git switch -c <branch-name>` to create and switch to a new branch.
- **GitHub Issues as project management**: Use issues to track tasks, meeting notes, and action items. Assign people to issues to clarify responsibility.
- **Cross-referencing**: Issues and pull requests share a single numbering sequence. Use `#<number>` in descriptions or commit messages to create two-way links.
- **Closing issues automatically**: Use keywords `fixes #<number>` or `closes #<number>` in a pull request description. Merging the PR will automatically close the referenced issue(s).
- **Cleaning up branches**: After merging a PR, delete the remote branch via the GitHub UI. Locally, run `git fetch --prune` to remove remote tracking references, then `git branch -d <branch-name>` to delete the local branch.

> [!WARNING]
>
> Keep your first pull request or issue comment updated. It serves as the primary summary for reviewers and future team members; the rest of the conversation is secondary.

### 3. Introduction to Containers and Docker ([27 Introduction to containerization](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers.html)) (*00:25:33–00:46:44*)

- **Why containers?**: Virtual environments (`uv`, `renv`) manage packages but not the underlying OS or system dependencies. Containers isolate the entire operating system user space, solving compatibility issues across different machines and operating systems.
- **Containers vs. Virtual Machines**: Virtual machines emulate full hardware and OS, making them heavy (gigabytes). Containers are stripped-down, share the host OS, and are lightweight (often <1 GB), making them faster to start and share.
- **Pulling and running images**: `docker pull <image>` downloads an image. `docker run --rm -it <image>` starts an interactive session. `--rm` deletes the container when it exits, preventing clutter. `-it` enables interactive terminal mode.
- **Version isolation**: Containers allow running specific software versions (e.g., R 4.3.2 inside a container while the host has R 4.6.2) without interfering with the host system.

> [!WARNING]
>
> Containers reset to their initial state when stopped. Any packages or changes installed interactively are lost upon exit unless explicitly saved via a `Dockerfile` or volume mount.

### 4. Running Web Applications in Containers ([28.1.3 Mapping ports to containers with web apps](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-running.html#mapping-ports-to-containers-with-web-apps)) (*00:46:47–01:03:00*)

- **Browser-based apps**: Tools like JupyterLab, RStudio Server, and VS Code run inside containers and are accessed via a web browser.
- **Port mapping**: Use `-p <host_port>:<container_port>` to map a container's port to your local machine. RStudio defaults to port 8787. You can run multiple containers by mapping them to different host ports (e.g., `8788:8787`).
- **Environment variables**: Pass configuration using `-e VARIABLE_NAME="value"`. For RStudio, you can set a custom password with `-e PASSWORD="yourpassword"` to avoid the default generated one.
- **Security note**: Port mapping only exposes the app to your local machine. External access depends on your network configuration, but locally it is restricted to `localhost`.

### 5. Building Custom Containers with Dockerfile ([29 Customizing and building containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html)) (*01:03:00–01:20:39*)

- **Dockerfile structure**: A plain-text file (named `Dockerfile`) that defines the steps to build a container image. It always starts with a base image.
- **`FROM`**: Specifies the starting base image (e.g., `rocker/r-ver:4.6.2`).
- **`RUN`**: Executes shell commands during the image build process (e.g., `RUN Rscript -e "install.packages('cowsay')"`) to install software permanently into the image layers.
- **`CMD`**: Sets the default command a container runs when started from this image. It replaces the base image's default. Syntax uses JSON array format: `CMD ["executable", "param1"]`.
- **Building and running**: Use `docker build --tag <image_name> .` to build the image from the current directory. Run it with `docker run <image_name>`. You can override the default `CMD` by appending a command like `bash` to the run command.

> [!WARNING]
>
> Always pin software versions in your `Dockerfile` (e.g., `FROM rocker/r-ver:4.6.2`). Relying on `latest` can cause unexpected breaks if upstream packages update outside your control.

## Commands from class

### Git branch workflow

```bash
git switch -c today                  # Create and switch to a new branch
git add README.md                    # Stage changes
git commit -m "today we are talking about containers" # Commit with message
git push origin today                # Push branch to remote
git switch main                      # Switch back to main
git pull origin main                 # Ensure main is up to date
git fetch --prune                    # Remove deleted remote branch references
git branch -d today                  # Delete local branch
```

The instructor demonstrated moving a change from `main` into an isolated branch, pushing it, and then cleaning up local and remote tracking references after the pull request was merged.

### Pulling and running base R container

```bash
docker pull rocker/r-ver:4.3.2       # Download a specific R version image
docker run --rm -it rocker/r-ver:4.3.2 # Start interactive session, auto-delete on exit
```

This command downloads the R 4.3.2 image if missing and launches an interactive R session. The container's R version runs independently of the host machine's R installation.

### Running RStudio container (web app)

```bash
docker pull rocker/rstudio:4.4.2     # Download RStudio Server image
docker run --rm -p 8787:8787 rocker/rstudio:4.4.2 # Run with port mapping
docker run --rm -p 8787:8787 -e PASSWORD="apassword" rocker/rstudio:4.4.2 # Set custom password
```

Web applications inside containers must be accessed via the host's browser. Port mapping exposes the container's port 8787 locally, while `-e PASSWORD` overrides the auto-generated login credentials.

### Building a custom container

```bash
docker run --rm -it rocker/r-ver:4.6.2 bash # Start base R image with bash shell
Rscript -e "install.packages('cowsay')" # Install package inside container
docker build --tag hello-cowsay .      # Build image from current Dockerfile
docker run --rm -it hello-cowsay       # Run custom image
docker run --rm -it hello-cowsay bash  # Override default CMD to get bash shell
```

Because interactive changes are lost when a container stops, a `Dockerfile` is used to bake the installation into the image layers. The `CMD` instruction defines the default startup behavior, which can be overridden by appending a command to `docker run`.
