Containers: Running and Building a Shareable Compute Environment

Date: 2026-11-19

Generated by qwen3.8-27b-sglang, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Summary

The session opened with the pre-lecture setup and a Git review. Students were asked to have Docker Desktop running and to complete the three docker pull commands posted in Slack, then to practise the branch → commit → push → pull-request cycle on the class’s demo repository. The review covered creating a branch with git switch -c, committing and pushing, and using GitHub issues as a lightweight project board — including cross-referencing issues and pull requests with closes and fixes so that a merged pull request auto-closes its issues, and cleaning up the branch references after the merge.

Before the container material, the instructor gave strong advice on the group project: keep the analysis simple and technically correct rather than ambitious, because DSCI 522 is a workflows course, not a model-fitting course. The lecture then introduced containers as the course’s answer to “this works on my machine.” It contrasted virtual environments, virtual machines, and containers, explained why a container pins not just packages but the system tools themselves, and ran the rocker R and RStudio images to show how a container behaves like a separate, shareable machine — including port mapping for web apps and passing environment variables.

The second half was a build-a-container walkthrough: start from a base image, explore it with a shell instead of the default command, install the cowsay package interactively, and only then write the commands into a Dockerfile using FROM, RUN, and CMD. The class built the image with docker build --tag hello-cowsay . and verified it with docker run. The session closed by stressing version pinning — so that tools do not update without your say-so — and pointed to next class for stringing multiple containers together.

Key takeaways

  • Confirm the branch you are on with git status before git add and git commit, and pull main before starting work in a branch.
  • Keep the first comment on an issue or pull request current, and use the closes/fixes keywords so a merged pull request auto-closes its issues.
  • A container is a stripped-down, shareable “virtual computer” that pins system tools as well as packages, which is what makes it more portable than a lock file alone.
  • docker pull downloads an image; docker run --rm -it <image> starts it — -it gives an interactive terminal and --rm removes the container on exit.
  • Web-app containers (RStudio, Jupyter) are reached through a mapped port, e.g. -p 8787:8787, then http://localhost:8787 in the browser.
  • A Dockerfile starts with FROM, installs with RUN, and ends with CMD; build it with docker build --tag <name> . and test with docker run.
  • Version-pin your tooling in the Dockerfile so a floating update cannot silently break a build you have already validated.

Knowledge Points

1. Class setup: Docker Desktop and the pre-lecture docker pull commands (27 Introduction to containerization)

00:00:14–00:01:41

  • Docker Desktop must be running: on macOS and Windows, open Docker Desktop before running any docker command; if you get an error like “can’t find Docker”, install Docker (the application called Docker) and start it, or the commands will tell you to turn it on.
  • Pre-lecture pulls: run the three docker pull commands posted in Slack before class so the images are downloaded by the time the session begins — pulling takes a while.
    • The three images: rocker/r-ver:4.3.2, rocker/rstudio:4.4.2, and quay.io/jupyter/datascience-notebook:2025-03-14 (the Jupyter image is the largest, around 9 GB).
  • The exercise for the day: practice making a branch, creating a pull request, and merging it, plus working with pull requests and issues.
  • Why it matters: this is the same workflow you will reuse for every assignment moving forward.

2. Project advice: keep the analysis simple and correct

00:01:41–00:06:05

  • Do not make the analysis difficult: the single biggest tip — if your model is a straight line, fit a straight line; resist the urge to add a neural network “to make it your time to shine.”
  • This course is not model fitting: DSCI 522 is about workflows, so almost no machine-learning code appears in the lectures.
  • The report is not the point: there is a lot more to do than write a report; keep the analysis short, but still include data-download code, some cleaning, EDA, modelling code, and figures and tables.
  • Accuracy does not matter, correctness does: a 60%-accurate model is fine, but the data science and ML techniques must be technically correct — for example, do not fit logistic regression to a numeric outcome.
  • Portfolio projects later: if you want a portfolio piece, build it in parallel, not inside this assignment.
  • Timeline: it is the same project you build on for three or four weeks; you need a machine-learning project to start with even though no ML code is shown in class; this week’s individual focus is getting everything on Git, next week’s is containers.

[!WARNING]

Over-scoping the project is the common mistake that backfires: the instructor warned that if you turn a simple task into a complicated model now, “you’re going to have a very bad time in about two weeks.” Keep it simple and correct.

3. Git review: branch, commit, and push for the pull-request task

00:06:05–00:09:50

  • The task: create a repository, bring it onto your local machine (git clone the demo repository), then create a pull request.
  • Check your branch before committing: in a branch workflow, run git status right before git add and definitely before git commit to confirm which branch you are on; a cheat sheet in the textbook lists commands for moving commits if you accidentally commit on main.
  • Pull main before you start: in an actively collaborating environment, make sure main is up to date so you are not changing something stale.
  • The live sequence: edit README.md, git switch -c today to create the branch, git status to confirm you are on today, git diff to show the added line, git add README.md, git commit -m "today we are talking about containers", then git push origin today.
  • Why this is new since 521: what was single-user in DSCI 521 now matters with multiple people actively working on multiple branches.

4. Issues as a project board

00:09:50–00:16:17

  • Issues track what is happening: a simple view of who is responsible for what; the issue board can even double as meeting notes (MDS keeps meeting notes in the issue board of an internal repository).
  • Action items spawn issues: write a meeting note, then create separate issues for each to-do and assign them.
  • Shared numbering: issues and pull requests share one counter (issue #2, then PR #3), so you can reference any item with a hash number, e.g. #1.
  • Two-way references: referencing #1 from another item creates a back-link automatically; this cross-linking is a big reason GitHub (as a service) became popular.
  • Ideas and agents: use issues as a dump for random ideas or stretch goals; when working with an agent, you can ask it to file an issue so you do not lose track.
  • One pull request can close several issues: the class requires three issues, but one pull request is allowed to deal with all three.
  • Assignment and review: you can assign people to issues and to pull requests; the assign section claims responsibility, while the reviewer section requests a look-over (larger projects can block a merge until a reviewer approves).
  • Demo repository items: issue #1 what are we doing today? and issue #2 edit the readme with today’s topic.

5. Pull-request descriptions, checkboxes, and auto-close keywords

00:16:17–00:22:18

  • Keep the first comment current: the first comment on an issue or pull request should hold all the context, because people read that and not the later conversation; project owners can edit others’ comments to keep it up to date.
  • Markdown checkboxes: use - [x] item 1 and - [ ] item 2 in a pull request to track what is done; with the draft button, teammates can see status at a glance.
  • closes and fixes keywords: a sentence ending in closes #1 or fixes #2 references those issues; when the pull request merges, GitHub auto-closes the referenced issues.
  • GitHub, not Git: this auto-close is a GitHub service feature, not part of the Git version-control system; you can reference multiple issues or the same one multiple times.
  • Strategic messages: write the description so that merging the pull request closes all the issues at once instead of clicking close several times; the instructor’s own textbook workflow does this (“fixes #N” in the message closes the issue on merge).
  • Stretch goals as issues: you can create issues for future ideas; the class does not grade on all issues being closed.
  • The demo pull request is #3 today we are talking about containers, whose description uses closes #1 fixes #2.

6. Merging the pull request and cleaning up branches

00:22:18–00:25:29

  • Finish on main: after the pull request merges, git switch main and git pull origin main to bring the merge down locally.
  • Delete the remote branch: on GitHub, after merging there is a “delete branch” button; or use the branches view and click the trash can. This is not required in the class — you may keep branches as a record.
  • Teams differ: the way shown here is one valid way to work with Git; other teams and companies do it differently.
  • Clean up local references: git log --oneline --graph --all still shows the branch tip; run git fetch --prune to drop the remote-tracking reference, then git branch -d today to delete the local branch.
  • Why keep or delete: deleting loses the quick git switch today shortcut, but the merge commit still records that it happened; some keep branches so they do not lose the reference.

7. Why containers: a stable, shareable compute environment (27 Introduction to containerization)

00:25:29–00:33:21

  • From homework to projects: 522 moves from short, instructor-supplied package files to data-science projects that can last days to years and are often team-based.
  • Different package needs: each project (R or Python; Altair, Plotly, or Matplotlib) has its own package requirements; you now manage your own list instead of the instructor’s, and keep it to the bare minimum.
  • Stable for you and others: uv and renv (from 521) keep packages consistent on one machine; Docker goes further so a teammate on a different operating system or CPU architecture (Intel vs ARM, Mac vs Windows) can run the same environment.
  • “Works on my machine” fails: the goal of the course is a compute environment you can share and run all of your code through, not a private one.
  • A virtual computer: instead of handing over your machine, build a virtual one (a container) and give everyone that; you can prototype locally and then run the identical environment on a bigger machine.
  • Sandbox and performance: there is a performance hit from the extra layer; if you break the sandbox you just restart it; it is a safe place to learn to muck around an operating system.
  • Instances and other tools: cloud “instances” are often containers; besides Docker there are LXC, LXD, Podman, and cloud-specific variants.

8. Containers versus virtual machines (27 Introduction to containerization)

00:33:21–00:36:47

  • Virtual machine: a full operating system (for example, a complete Windows install with a graphical interface) that you log into; the instructor still uses VMs, e.g. to test the MDS install while pretending to be on Windows.
  • Container: a stripped-down environment containing only what you install plus a terminal; it has no graphical interface, which fits the 521 habit of working at the command line.
  • Size difference: a virtual machine can take 50–80 GB; the containers used in class are under about 1–2 GB and still run a full computational stack.
  • Performance: containers are lighter in disk, memory, and compute because there is less to run; think of a container as a virtual machine with the full operating system and visual bits removed.

9. Running the R container: docker pull and docker run (27 Introduction to containerization)

00:36:47–00:45:01

  • docker pull rocker/r-ver:4.3.2: the name looks like user/repo:tag; rocker is an organization that builds R-only images, and the tag picks R 4.3.2. Pulling downloads the image, or reports it is up to date and shows a content hash.
  • Two versions of R: the host has R 4.6.2 (check with R --version), while the container runs R 4.3.2. A real case is a pharmaceutical or clinical-trial analysis where the R version must stay fixed for years, and a drug submission requires the code plus the exact compute environment.
  • Lock files vs system tools: uv/renv lock files pin package versions but not the tooling itself (for example, the installed version of git); a container pins the system tools too.
  • docker run --rm -it rocker/r-ver:4.3.2: docker run starts a container, pulling the image first if needed; --rm deletes the container when it stops so stopped containers do not pile up; -i keeps input open (interactive) and -t attaches a TTY so R runs interactively; single-letter flags can be chained (-it).
  • Proof it is a different machine: the container opens R 4.3.2 while the host has 4.6.2; library(tidyverse) fails in the bare container (there is no package called 'tidyverse') but works on the host — two terminals on one computer doing different things.
  • Know where you are typing: the only cue is the prompt (the container’s prompt looks different from the host’s); this mirrors working on a remote or cloud machine, and is why 521 taught whoami-style checks.

10. Web-app containers: RStudio and browser-first tools (28 Using and running containers)

00:45:01–00:54:10

  • Browser-first applications: many data-science tools — JupyterLab at localhost:8888, VS Code, GitHub Codespaces — are built as browser apps (often via Electron) so the same interface can run on a remote machine or in a container.
  • RStudio as a web app: the rocker/rstudio image runs RStudio Server, which you reach from a browser; it is an easier one to teach than a plain terminal.
  • Why it matters for 532: a dashboard is a browser app; you can containerize it so an end user only needs Docker to run it.
  • Same interface, different machine: connecting to the container’s web app is the same idea as connecting to cloud compute.
  • The class took a five-minute break at this point before continuing with the RStudio container.

11. Port mapping the RStudio container (28 Using and running containers)

00:54:10–00:59:14

  • docker run --rm -p 8787:8787 rocker/rstudio:4.4.2: the RStudio image listens on port 8787; -p host:container maps a local port to the container’s port.
  • Running it more than once: the container side is fixed at 8787, but you can map it to a different local port (up to roughly 60,000 ports) so multiple RStudio containers run at the same time.
  • Open it in the browser: go to http://localhost:8787; sign in with username rstudio and the password printed in the terminal (a generated one on the first run).
  • Confirm it is the container, not the host: local RStudio runs the host’s R (4.6.2), while the containerized RStudio runs a different version (the rocker/rstudio:4.4.2 image) — two independent machines.
  • Resources: each running container uses RAM; leaving several open can make the machine sluggish, which is why --rm is used.

12. Environment variables and running dashboards in containers (28 Using and running containers)

00:59:20–01:03:00

  • -e PASSWORD="apassword": pass environment variables at run time; the rocker/rstudio image reads PASSWORD to set the login password instead of generating a random one.
  • Not every container exposes the same variables: behavior depends on how the image was built; more is covered when building containers.
  • Is the port reachable by others?: the instructor checked that localhost:8787 is only reachable by someone who can log into the host machine — a good habit for verifying what a port mapping actually exposes.
  • Dashboards in 532: put dashboard code in a container; the end user installs nothing but Docker and runs docker run with the right flags, so all the heavy installation (environment, Quarto, etc.) is already done inside.

13. Building interactively: base image and the cowsay package (29 Customizing and building containers)

01:03:00–01:08:46

  • Start from a base image: even when customizing, pick a starting point; here rocker/r-ver:4.6.2 already has R and the tooling a fresh install would otherwise need (like the compiler setup that Windows and Mac users had to do by hand).
  • Get a shell, not R: docker run --rm -it rocker/r-ver:4.6.2 bash starts bash instead of the image’s default R, so you can run the install commands you plan to document.
  • Try before you write: run the steps interactively first (install cowsay with install.packages("cowsay"), then cowsay::say('hello')), and only document what actually works.
  • No persistence: exit the container and any package you installed is gone the next time you start it — a container has no save state and resets to the image; that is also a safe place to run destructive commands or experiment with new packages without harming the real machine.

14. Writing the Dockerfile: FROM, RUN, and CMD (29 Customizing and building containers)

01:08:46–01:15:01

  • The Dockerfile: a plain-text file (capital D, no extension) holding the instructions to build the machine; it is version-controlled like a pyproject.toml or lock file (see the Dockerfile the class committed).
  • FROM rocker/r-ver:4.6.2: the first line sets the base image; you can choose an even smaller, near-bare Linux image and install everything by hand.
  • RUN: bash commands to run during the build, e.g. RUN Rscript -e "install.packages('cowsay')"; mind the quoting (double quotes on the outside, single quotes on the inside), because Rscript -e runs an R expression from the command line.
  • CMD: the default command when the container starts; here CMD ["Rscript", "-e", "cowsay::say('Hello from my first image!')"] so the image prints the message; ENTRYPOINT is the rarer alternative for fixed commands.
  • COPY + uv sync: for a Python image you would COPY in your lock files and run uv sync so the packages are installed at build time; next week you will install the language, Quarto, and packages the same way.

15. Building and running the hello-cowsay image (29 Customizing and building containers)

01:15:01–01:18:44

  • docker build --tag hello-cowsay .: --tag (or -t) names the image; the . is the build context / current directory where Docker looks for the Dockerfile.
  • Run from the repository root: the . convention assumes you run commands from the directory root — the same assumption used in the milestone-one instructions.
  • Check it built: docker images lists local images, including hello-cowsay:latest and its disk size (about 1.45 GB).
  • Run it: docker run --rm -it hello-cowsay executes the CMD (the cowsay message); docker run --rm -it hello-cowsay bash drops you into a shell where library(cowsay) now works, proving the RUN step baked the package into the image.

16. Version pinning and wrap-up (29 Customizing and building containers)

01:18:44–01:20:39

  • Pin your tooling: add a placeholder for the uv/renv setup and pin the Quarto version (or any tool version, e.g. an older Quarto) so the image installs exactly those versions.
  • Control what updates: as long as you do not change the install line, a year from now you are still on the same tool versions.
  • The Dockerfile as the control point: you say “here is the version I want; it will not change until I update that line.”
  • Next time: this was an introduction to containers (using and building them); the next class builds on it, including stringing multiple containers together and the sections listed as not reached.

[!WARNING]

Do not let tool versions float. The instructor recounted restarting a container without hard-version-pinning its tools, where an overnight update broke everything and hours were spent fixing the update instead of doing the work. Pin the versions in the Dockerfile so an unexpected update cannot silently break a validated build.

Getting the demo repository and creating the today branch

Checking the merge and deleting the branch references

git switch main
git pull origin main
git log --oneline --graph --all      # still shows the branch tip
git fetch --prune                    # drop the remote-tracking branch after the GitHub branch was deleted

Comparing R versions on the host and in the container

R --version                            # host R is 4.6.2
docker pull rocker/r-ver:4.3.2          # download the R 4.3.2 image
docker run --rm -it rocker/r-ver:4.3.2 # start R 4.3.2 inside the container

library(tidyverse) fails in the bare container but works on the host, showing the two terminals are different machines.

Running the RStudio web-app container

docker pull rocker/rstudio:4.4.2
docker run --rm -p 8787:8787 rocker/rstudio:4.4.2                       # first run prints a generated password
docker run --rm -p 8787:8787 -e PASSWORD="apassword" rocker/rstudio:4.4.2  # set a known password

Open http://localhost:8787 and sign in with username rstudio.

Exploring a base image with a shell and installing cowsay

docker run --rm -it rocker/r-ver:4.6.2 bash   # get a shell instead of starting R
Rscript -e "install.packages('cowsay')"        # the RUN line, typed at the container shell

Rscript -e runs an R expression from the command line, which is the form a RUN line needs.

Building and running the hello-cowsay image

docker build --tag hello-cowsay .          # build from the Dockerfile in the current directory
docker images                              # list local images; hello-cowsay:latest is present
docker run --rm -it hello-cowsay           # runs the CMD (the cowsay message)
docker run --rm -it hello-cowsay bash      # open a shell to check library(cowsay) works
