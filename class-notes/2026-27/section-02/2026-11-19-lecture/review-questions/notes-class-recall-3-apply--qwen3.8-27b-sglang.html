1. Pre-lecture setup: Docker Desktop and the docker pull commands (27 Introduction to containerization)

00:00:14–00:01:41

  • Q: You open a new terminal, type docker pull rocker/r-ver:4.3.2, and get an error saying Docker cannot be found. What is the most likely cause, and what do you do before re-running the command? A: The Docker Desktop application is not running. On macOS and Windows, Docker commands require the Docker engine managed by Docker Desktop; you need to open Docker Desktop (the application called Docker) so the engine is available, then re-run the docker pull command. (00:00:33)

  • Q: You are preparing for the day’s container exercises and have four actions in front of you: (a) run docker pull rocker/r-ver:4.3.2, (b) open Docker Desktop, (c) run docker pull quay.io/jupyter/datascience-notebook:2025-03-14, and (d) run docker pull rocker/rstudio:4.4.2. Put them in the order you should perform them, and explain why the first one must come first. A: Open Docker Desktop (b) first, then run the three docker pull commands (a, c, d in any order). Docker commands require the Docker engine to be running; if Docker Desktop is not open, the commands will fail with a “can’t find Docker” error. (00:00:33)

  • Q: You are following the pre-lecture instructions and have the three docker pull commands ready. A teammate asks, “Why do we run docker pull now instead of just using docker run later when we need the container?” What is the difference, and why is pull the correct preparation step? A: docker pull downloads the image to your machine without starting a container, so it is ready and waiting when you later run docker run. docker run would start a container immediately (pulling the image first if it is missing), but the pre-lecture task is to have all three images downloaded in advance so the session can begin without waiting on downloads. (00:00:14)

2. Project scoping: keep the analysis simple and correct

00:01:41–00:06:05

  • Q: Your project’s outcome is a continuous value (for example, house price). You are choosing between a logistic regression model and a linear regression model for the modelling step. Which one do you use, and why would the other choice be technically incorrect? A: Use linear regression. Logistic regression is for binary or categorical outcomes; fitting it to a numeric outcome is technically wrong. The guidance is that the model must be correct even if it is simple — a 60 %-accurate linear model is acceptable, but the technique must match the outcome type. (00:05:24)

  • Q: Your project uses a simple linear regression for the modelling step. A code reviewer checks your pipeline and says it is missing components. Even though the model is just a straight line, what types of code must still be present in the pipeline? A: Data-download code, some cleaning code, EDA (exploratory data analysis) code, modelling code, and code for figures and tables. Keeping the analysis short does not mean skipping these stages; they are still required, just kept simple. (00:02:41)

  • Q: You are scoping your project. Your model currently fits a straight line, and a teammate suggests adding a neural network because “it’s our time to shine.” What do you decide, and what is the specific risk that was highlighted for making the analysis too complicated this week? A: Keep the straight-line model. The course is about workflows, not model fitting, and the risk of over-scoping now is “you’re going to have a very bad time in about two weeks” because the project will be hard to finish with all the workflow infrastructure (Git, containers, reports) still in place. If you want a portfolio piece, build it in parallel, not inside this assignment. (00:02:03)

3. Git review: branch, commit, and push on the demo repository

00:06:05–00:09:50

  • Q: You have cloned the 2026-11-19-docker demo repository, and git status shows you are on branch main with README.md modified but uncommitted. You want to commit the change on a new branch called today. Put the Git commands in the order you would run them, including the step where you verify you are on the right branch. A: git switch -c today (create and switch to the new branch), git status (confirm you are on today and that README.md is still modified), git add README.md, git commit -m "today we are talking about containers", then git push origin today. Checking the branch before add and commit is the habit the session emphasised. (00:08:57)

  • Q: You accidentally ran git add README.md and git commit while still on branch main instead of your feature branch. You have not pushed yet. What should you have checked before running git add and git commit, and where in the textbook can you find commands to move the commit to the correct branch? A: Run git status right before git add and definitely before git commit to confirm which branch you are on. If you committed on main by mistake, the textbook has a cheat sheet with commands for moving commits around so you can move the commit to the intended branch. (00:07:44)

  • Q: You are on branch main in the demo repository and a teammate has just pushed a new commit to main on GitHub. Before you create your feature branch, you run git pull origin main. Predict: what does this command do to your local main, and why is it recommended before starting work in a new branch? A: It downloads and merges the latest main commits from the remote into your local main. In a multi-person, multi-branch environment, your local main may be behind the remote; pulling first ensures you are not building your branch on an outdated base. (00:08:27)

  • Q: You are on branch main in the demo repository. You have edited README.md (adding a new line) but have not staged or committed the change. You now decide to create a branch called today for this edit. Can you create the branch now, and what happens to your uncommitted change when you switch to today? A: Yes. Run git switch -c today. The uncommitted change carries over to the new branch because it lives in the working directory, not yet in any commit. After switching, git status shows you are on today with README.md still modified. (00:08:57)

4. Issues as a project board on the demo repository

00:09:50–00:16:17

  • Q: You have created issue #1 “what are we doing today?” and issue #2 “edit the readme with today’s topic” in the 2026-11-19-docker repository. You want issue #2 to link back to issue #1 so anyone viewing #2 can find the original topic. What do you type in issue #2’s text to create the link, and what does GitHub do automatically? A: Type #1 (the hash followed by the issue number) in issue #2’s text, for example in a sentence like “meeting from #1.” GitHub creates a two-way reference: from #2 you see a link to #1, and from #1 you see that #2 references it. The shared numbering means every issue and pull request gets a unique hash you can use this way. (00:12:30)

  • Q: Your group meeting just ended and produced three to-do items: set up the Git repository, download and clean the data, and write the first Quarto report. You are on the demo repository’s issue board. How do you set up the issues to track the meeting and the action items? A: Create a meeting-note issue with the general topic (for example, “Meeting from #1”), then create three separate issues for the to-do items and assign each one to the responsible team member. The meeting note can hold the discussion, and the individual issues “spawn out of” it so each task has its own tracking thread and owner. (00:10:49)

  • Q: You just opened a pull request on the demo repository from your today branch. A teammate asks whether they should assign themselves to the pull request or use the reviewer section. In what situation would you assign a teammate to the pull request rather than yourself, and what is the difference between the two sections? A: You assign yourself to a pull request because it is your work and you are claiming responsibility for it. The reviewer section is where you request that a teammate look over the changes; in larger projects a merge can be blocked until a reviewer approves. You typically do not assign a teammate to your own pull request unless they are the one who must approve or block the merge. (00:14:47)

5. Pull-request descriptions, checkboxes, and auto-close keywords

00:16:17–00:22:18

  • Q: You are writing the description for pull request #3 in the 2026-11-19-docker repository, which addresses issues #1 and #2. What exact text do you include in the description so that GitHub automatically closes both issues when the pull request merges, and what happens to the issues at merge time? A: Include closes #1 fixes #2 (or any sentence ending with those keywords) in the pull request description. When the pull request merges, GitHub auto-closes both referenced issues. The keywords closes and fixes are GitHub service features, not part of the Git version-control system. (00:18:33)

  • Q: You have been working on a pull request and have completed some changes but not all. You want to track your progress visibly for your teammates without turning the pull request into a draft. What Markdown syntax do you add to the pull request description, and how will it appear to your teammates in the GitHub interface? A: Add lines like - [x] item 1 and - [ ] item 2. They render as Markdown checkboxes: a check mark for done items, an empty box for remaining items. Teammates can see at a glance what is complete without reading the full conversation thread. (00:17:43)

  • Q: A teammate edited the first comment of a pull request weeks ago, but a major decision was made in the comment thread last week and the first comment no longer reflects it. As the project owner, what can you do to fix this, and why does the first comment matter more than the later conversation? A: You can edit the first comment (project owners have access to edit other people’s comments) to add the reference or decision. The first comment matters because most people look at it to understand what the pull request is about and why it exists; they do not read through the entire conversation thread, so the first comment should hold all the context. (00:16:40)

6. Merging the pull request and cleaning up branches

00:22:18–00:25:29

  • Q: Pull request #3 has been merged on GitHub. You are still on branch today locally in the 2026-11-19-docker repository. Put the complete sequence of steps in order: get the merged code onto your local main, delete the remote today branch on GitHub, and clean up the local branch references. A: git switch main, then git pull origin main to bring the merge down locally. On GitHub, use the “delete branch” button on the merged pull request (or the branches view) to delete the remote today branch. Then run git fetch --prune to drop the remote-tracking reference, and git branch -d today to delete the local branch. (00:22:25)

  • Q: After merging PR #3 and deleting the branch on GitHub, you run git log --oneline --graph --all and still see the today branch label next to commit 3c6d82a. What two commands do you run locally to remove the remaining references, and what does each one specifically remove? A: git fetch --prune removes the remote-tracking reference (origin/today), and git branch -d today removes the local branch. After both, the commit 3c6d82a is still visible in the merge history (the merge commit records it), but the quick git switch today shortcut is gone. (00:24:30)

  • Q: You want to delete the today branch on GitHub after merging PR #3, but you are not in the pull request view. Where else in GitHub’s interface can you find and delete the branch, and what visual cue tells you it is safe to delete? A: Go to the branches view (the list of all branches on the repository). Find the today branch; it shows that it was pull request #3 and that it was merged. Click the trash-can icon to delete it on GitHub. The merged status is the cue that it is safe to delete. (00:22:53)

  • Q: You have deleted the today branch both on GitHub and locally. A week later you need to check out commit 3c6d82a for a quick fix. You try git switch today and get an error. What alternative does the session mention for reaching that commit without the branch, and what did you lose by deleting the branch? A: You can switch directly to the commit hash: git switch 3c6d82a (or the longer hash). Deleting the branch loses the named shortcut git switch today; the merge commit still records that the work happened, but the quick reference by branch name is gone. (00:25:05)

7. Why containers: a stable, shareable compute environment (27 Introduction to containerization)

00:25:29–00:33:21

  • Q: Your teammate is on a Windows machine with an ARM chip, and you are on a Mac. You send your uv lock file, but your teammate reports that a compiled package will not install because the binary was built for a different architecture. Why does the lock file alone not solve this, and what is the course’s answer for sharing the environment across different operating systems and CPU architectures? A: A lock file pins the versions of the packages but not the underlying operating system, CPU architecture, or system tools. The course’s answer is to build a container — a virtual computer that includes the exact OS, architecture, system tools, and packages — and share that container so everyone runs the same environment regardless of their physical machine. (00:28:34)

  • Q: You are prototyping an analysis on your laptop and later need to run the same pipeline on a larger machine with access to the full dataset. How does the container approach let you guarantee the compute environment is identical on both machines? A: Build the environment as a container image (specifying the exact OS, tools, and packages). Run the same container image on your laptop and on the larger machine. Because the container is a self-contained virtual computer, the environment is identical on both; you do not need to reinstall or reconfigure on the second machine. (00:32:15)

  • Q: You accidentally run a destructive command (for example, deleting a system file) inside a rocker/r-ver container. Predict how this differs from running the same command on your host machine, and what you do to “reset” the environment. A: Inside the container, the command only affects the container’s isolated filesystem; your host machine is unaffected. You exit the container (or it is removed by --rm), and when you start a new container from the same image, it resets to the clean image state. A container has no save state, so any changes are gone — making it a safe sandbox for experimentation. (00:33:05)

8. Containers versus virtual machines (27 Introduction to containerization)

00:33:21–00:36:47

  • Q: Your team needs to share the project’s compute environment with a teammate on a different operating system. You have a container image (under 2 GB) and a virtual-machine image (about 80 GB). Based on the size and resource trade-offs, which do you use for the shared project, and what is the one performance trade-off you accept? A: The container. It is far smaller in disk, memory, and compute usage, making it practical to download, build, and share. The trade-off is a performance hit from the extra virtualization layer, which is unavoidable (“there’s no way around that”). (00:36:32)

  • Q: You are writing the project’s README and need to explain the difference between the container and a virtual machine to a new teammate. Your teammate writes: “A container is a full operating system in a box, just like a VM but smaller.” Based on the session’s description, what is the specific thing the container does NOT include that the virtual machine does? A: The container does not include a full operating system with a graphical interface. It is a stripped-down environment containing only the software you install, accessed through a terminal. A virtual machine emulates an entire computer including a complete OS (for example, a full Windows install) that you log into with a GUI. (00:35:00)

  • Q: Your team needs to test the MDS software installation on a Windows machine, but no one on the team has a Windows laptop. Based on the session’s description, which tool (container or virtual machine) do you use for this specific test, and why does a container not replace it here? A: A virtual machine. The session noted that a VM is still used to test the MDS installation while pretending to be on a Windows machine, because it provides a full Windows OS with a graphical interface. A container has no GUI and cannot replicate the full Windows desktop experience needed for that test. (00:36:16)

9. Running the R container: docker pull and docker run (28 Using and running containers)

00:36:47–00:45:01

  • Q: You run docker run --rm -it rocker/r-ver:4.3.2 and R 4.3.2 opens. You type library(tidyverse) and get Error: there is no package called 'tidyverse'. You open a second terminal on the same machine, type R, and library(tidyverse) loads without error. Explain why the two terminals behave differently, and what this tells you about the container. A: The first terminal is running R 4.3.2 inside the rocker/r-ver:4.3.2 container, which is a separate, isolated machine that only has R installed (no additional packages). The second terminal is running R 4.6.2 on your host machine, where tidyverse is installed. The container has its own filesystem and package library, independent of the host. (00:43:49)

  • Q: You run docker run --rm -it rocker/r-ver:4.3.2 and R opens. You type q() to quit R. Predict: what happens to the container process, and what would be different without the --rm flag? A: With --rm, the container is automatically deleted when R exits. Without --rm, the container would remain on your machine in a stopped state, and you would have to manually delete it. The --rm flag prevents stopped containers from piling up. (00:40:55)

  • Q: You are working inside the rocker/r-ver:4.3.2 container and want to confirm you are inside the container and not back on your host machine. The session noted that the only reliable visual cue is the prompt. What do you look for in the prompt, and what other command can you run to verify which machine you are on? A: The container’s prompt looks different from the host’s (for example, root@<container-id>:/# versus your normal host prompt). You can also run whoami to see the username (root inside the container versus your own username on the host). Knowing where you are typing is critical because a blinking cursor gives no other context. (00:45:04)

  • Q: You need to pin R to version 4.3.2 for a multi-year clinical-trial analysis, but your host machine has R 4.6.2 and R releases a new version every six months. Your renv lock file pins all the R package versions. Why does the lock file not solve the problem of R itself upgrading, and what does the container add that the lock file does not? A: A lock file pins the versions of the packages but not the R tool itself or other system tools. The container pins the entire system, including the specific R version (4.3.2) and the OS dependencies, so the environment stays stable even as R releases new versions. The session’s example: if you wanted to block git switch, you could ship a container with a 2019 version of Git that does not support it. (00:39:02)

10. Web-app containers: RStudio and browser-first tools (28 Using and running containers)

00:45:01–00:54:10

  • Q: A new student asks why JupyterLab is accessed at localhost:8888 in a browser rather than by double-clicking an application icon. Based on the session’s explanation of browser-first tools, what is the reason for the browser-based interface, and how does this design benefit the container workflow? A: JupyterLab (like VS Code and GitHub Codespaces) is built as a browser-first application so the same interface can run on a remote machine or inside a container. This means you can run JupyterLab in a container on a powerful remote server and access it from your local browser, without installing Jupyter or its dependencies on your own machine. (00:48:04)

  • Q: Your teammate asks, “Why does the course teach us to run RStudio in a container with docker run --rm -p 8787:8787 rocker/rstudio:4.4.2 instead of just installing RStudio on our laptops?” What is the key benefit of the container approach that the session highlighted? A: The container gives every team member the same RStudio interface running in an isolated environment with a specific, shared version of R and RStudio, regardless of what is installed on their individual machines. You are all working on the same virtual computer, which is the goal of the course: a compute environment you can share and run all your code through. (00:49:00)

  • Q: The session mentioned Electron as the technology behind many browser-first applications. Your teammate is building a small tool and asks, “Should I use Electron because the course talked about it?” What is the actual point the session made about Electron, and does it apply to your teammate’s decision to build a new tool? A: The session’s point is that existing data-science tools (JupyterLab, VS Code, RStudio Server) are already browser-first, which is why they can run inside a container and be accessed through a browser. It is not a recommendation to build every tool with Electron; it explains why certain tools are compatible with the container workflow. Your teammate’s decision depends on their tool’s requirements, not on the course’s container setup. (00:47:15)

11. Port mapping the RStudio container (28 Using and running containers)

00:54:10–00:59:14

  • Q: You want to run two rocker/rstudio:4.4.2 containers at the same time. The RStudio application inside the image always listens on port 8787. How do you map the ports for both containers so they are accessible from your local machine, and what URLs do you use in the browser for each? A: First container: docker run --rm -p 8787:8787 rocker/rstudio:4.4.2 (browser: localhost:8787). Second container: docker run --rm -p 8788:8787 rocker/rstudio:4.4.2 (browser: localhost:8788). The container side is always 8787; you change the host-side port to a different number (up to roughly 60 000) to avoid conflicts. (00:56:31)

  • Q: You run docker run --rm -p 8787:8787 rocker/rstudio:4.4.2 and the terminal prints The password is set to ooph3Aef2Ohcahcu. You open localhost:8787 in your browser, type that password in the password field, and the login fails. What went wrong, and what is the correct username? A: You need the username as well as the password. The username for the rocker/rstudio image is rstudio. The first run generates a random password (printed in the terminal), but the login form requires both the username rstudio and the generated password. (00:58:32)

  • Q: You are running the RStudio container and want to confirm you are using the container’s R, not your host’s R. Your host has R 4.6.2. What did the session compare between the two RStudio instances to verify they were running independent versions of R? A: The R version. The local RStudio desktop runs the host’s R (4.6.2), while the containerized RStudio runs the R version bundled in the rocker/rstudio:4.4.2 image, which is different. Two different R versions in two RStudio instances confirms they are independent machines. (00:58:41)

  • Q: You have started four RStudio containers and your laptop is becoming sluggish. The session explained that each running container takes up RAM. What flag in your docker run command helps prevent stopped containers from piling up and holding resources, and what does it do when you exit the container? A: The --rm flag. It automatically deletes the container when it stops, so stopped containers do not accumulate on your machine and keep holding resources. Without it, each exited container remains and you must manually clean up, which contributes to the resource pressure. (00:55:17)

12. Environment variables and running dashboards in containers (28 Using and running containers)

00:59:20–01:03:00

  • Q: You run docker run --rm -p 8787:8787 rocker/rstudio:4.4.2 and the terminal prints a random password you do not want to memorise. You want to set your own password instead. How do you modify the command, and what is the environment variable name? A: Add the -e flag with the PASSWORD variable: docker run --rm -p 8787:8787 -e PASSWORD="apassword" rocker/rstudio:4.4.2. The rocker/rstudio image reads the PASSWORD environment variable to set the login password instead of generating a random one. (01:00:05)

  • Q: You set -e PASSWORD="apassword" and start the RStudio container on your laptop. A teammate on the same Wi-Fi network tries to open localhost:8787 from their own computer and cannot reach it. Based on the check the session performed, why is this expected? A: The port mapping exposes the service only on your host machine’s localhost. The session verified that even though the container runs on port 8787, it is only reachable by someone who can log into your physical machine. A teammate’s localhost resolves to their own computer, not yours, so they cannot reach your container’s port. (01:00:28)

  • Q: You are preparing to share a dashboard (a browser-based application) with an end user who has no Python, R, or Quarto installed. Based on the session’s description of the dashboard workflow, what does the end user need to have on their machine, and what command do they run to start the dashboard? A: The end user needs Docker installed. They run docker run with the appropriate flags (port mapping, environment variables) to start the container that contains all the dashboard code and dependencies. The end user does not need to install the environment, Quarto, or any packages — everything is already inside the container image. (01:02:20)

13. Building interactively: base image and the cowsay package (29 Customizing and building containers)

01:03:00–01:08:46

  • Q: You want to build a custom container starting from rocker/r-ver:4.6.2. You run docker run --rm -it rocker/r-ver:4.6.2 bash instead of docker run --rm -it rocker/r-ver:4.6.2. What is the difference in what opens, and why is the bash version the correct choice for the building workflow? A: Without bash, the container starts R (the image’s default CMD). With bash, you get a terminal instead, so you can type and test installation commands interactively before writing them into the Dockerfile. The bash option is the “try before you write” step: you verify the commands work, then document them. (01:04:53)

  • Q: Inside the rocker/r-ver:4.6.2 container’s bash shell, you run Rscript -e "install.packages('cowsay')" and it succeeds. You exit the container. You start a new container from the same image and type R, then library(cowsay). Predict what happens, and explain why. A: library(cowsay) fails with Error: there is no package called 'cowsay'. The container has no save state: when you exit, the container is deleted (because of --rm), and any packages you installed are gone.
