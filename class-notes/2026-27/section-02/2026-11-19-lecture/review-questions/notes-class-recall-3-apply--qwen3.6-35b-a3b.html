1. Git Branching and Pull Requests

00:06:05–00:25:29

  • Q: You edit a file on main by mistake and want to move your uncommitted changes to a new branch called feature before committing. Which command do you run to create the new branch and switch to it? A: Run git switch -c <branch-name> to create a new branch and immediately switch your working directory to it, preserving your unstaged changes on the new branch instead of committing them to main. (00:09:17)

  • Q: After finishing work on a feature branch and merging it to main on GitHub, you want to completely remove the remote branch reference from your local machine. What two commands do you run to prune the remote tracking reference and delete the local branch? A: Run git fetch --prune to remove the deleted remote tracking references, then run git branch -d <branch-name> to delete the local branch reference. (00:24:30)

  • Q: You create a pull request to fix two open issues. How should you write the pull request description so that merging the pull request automatically closes both issues? A: Include the keywords fixes #<number> or closes #<number> at the end of a sentence in the pull request description, which triggers GitHub to automatically close the referenced issues when the pull request is merged. (00:18:33)

2. Introduction to Containers and Docker (27 Introduction to containerization)

00:25:33–00:46:44

  • Q: You need to run R version 4.3.2 on your Mac, but your system has R version 4.6.2 installed. Which Docker command runs the older R version interactively without leaving stopped containers cluttering your machine? A: Run docker run --rm -it rocker/r-ver:4.3.2, which downloads the specific versioned image if missing, starts an interactive R session, and automatically deletes the container instance when you quit. (00:40:41)

  • Q: You are exploring a newly started container and notice the terminal prompt shows root@<container_id>:/#. How do you verify that the R version running inside matches the one you requested in the docker run command, rather than the one on your host machine? A: Type R --version inside the R session to verify the version matches the requested tag, while noting that your host terminal remains on the system’s default R version. (00:43:10)

  • Q: You accidentally install a package inside an interactive container session, but when you stop the container and restart it, the package is gone. Why does this happen, and what is the intended use case for this behavior? A: Containers do not save state between runs; they reset to the exact configuration defined in the image each time, which is intentionally designed so you can safely experiment or test commands without risking your host machine. (00:08:10)

3. Running Web Applications in Containers (28 Using and running containers)

00:46:47–01:03:00

  • Q: You want to run RStudio Server inside a container and access it through your web browser. Which flag and syntax do you use in the docker run command to map the container’s default port to your local machine? A: Use the -p flag with the format -p <host_port>:<container_port> (e.g., -p 8787:8787), which forwards network traffic from a specified port on your local machine directly to the web application inside the container. (00:56:55)

  • Q: The RStudio container you just started generates a random default password for login. How can you modify your docker run command to set a custom password instead? A: Append -e PASSWORD="yourpassword" to your run command, which passes the environment variable to the container to override the default auto-generated login credentials. (01:00:05)

  • Q: You try to run two separate RStudio containers simultaneously, but both fail to start on port 8787. What modification do you make to the port mapping for the second container to allow both to run? A: Change the host port number in the -p flag for the second container (e.g., -p 8788:8787), which maps the container’s internal port to a different available port on your local machine to prevent conflicts. (00:57:29)

4. Building Custom Containers with Dockerfile (29 Customizing and building containers)

01:03:00–01:20:39

  • Q: You are designing a custom R container and have just tested an installation command at the Bash prompt. How do you translate that command into a Dockerfile so it executes during the image build process? A: Prefix the tested command with RUN in the Dockerfile (e.g., RUN Rscript -e "install.packages('cowsay')") so that it executes as a step during the image build sequence rather than at runtime. (01:12:41)

  • Q: You have finished writing a Dockerfile in your project root that installs a package. Which command do you run to compile this file into a named Docker image named hello-cowsay? A: Run docker build --tag hello-cowsay ., which reads the Dockerfile in your current directory and compiles the specified instructions into a named Docker image on your local machine. (01:15:38)

  • Q: After building a custom image, you want it to automatically run a specific R script every time it starts, instead of opening an interactive terminal. Which Dockerfile instruction do you use to define this default startup behavior? A: Use the CMD instruction with JSON array syntax (e.g., CMD ["Rscript", "-e", "cowsay::say('Hello')"]) to specify the command that runs by default when a container starts from this image. (01:13:36)
