2. Project advice: keep the analysis simple and correct

00:01:41–00:06:05

  • Q: Why does the instructor tell students not to make the group-project analysis difficult? A: This course is about workflows, not model fitting. If you turn a simple task into a complicated model now, you will have a bad time in about two weeks because there is a lot more workflow work to do. (00:02:03)

  • Q: What does the instructor mean when saying the accuracy of the model does not matter? A: A model can be only sixty percent accurate and that is acceptable. What matters is that the data science and machine-learning techniques are technically correct. (00:03:04)

  • Q: Why is it okay to fit a linear or logistic regression rather than a fancier model? A: The class will not penalize simplicity. The requirement is correctness, so you should not, for example, fit logistic regression to a numeric outcome. (00:05:12)

3. Git review: branch, commit, and push for the pull-request task

00:06:05–00:09:50

  • Q: Why does the instructor say to run git status right before git add and definitely before git commit? A: In a branch workflow you need to confirm which branch you are on. If you accidentally commit on main, the textbook has a cheat sheet of commands that can move the commits. (00:08:08)

  • Q: Why should you pull main before starting work on a new branch in a collaborating environment? A: You want to start from an up-to-date main. That prevents you from making changes based on something that is out of date while multiple people are working on multiple branches. (00:08:27)

  • Q: Why could the instructor create the today branch after already editing README.md on main? A: He had not committed anything yet. git switch -c today created the new branch and kept the uncommitted README.md change on today instead of main. (00:08:57)

  • Q: What does git push origin today make possible on GitHub? A: It uploads the today branch to the remote. GitHub can then show the pull-request button so you can open a pull request for that branch. (00:09:44)

4. Issues as a project board

00:09:50–00:16:17

  • Q: Why does the instructor recommend using GitHub issues to track a project? A: Issues give a simple project-board view of what is happening in the project. They can also record who is responsible for what and can hold meeting notes and action items. (00:10:08)

  • Q: How can an issue board be used as meeting notes in the MDS workflow? A: You can write a big note in an issue during a meeting. Then you create separate issues for the action items or to-do items that spawn out of that meeting note. (00:10:49)

  • Q: Why do issues and pull requests share the same numbering sequence? A: The shared number lets you refer to any issue or pull request from another item with a hash number. For example, you can refer to issue #1 from a pull request. (00:11:54)

  • Q: What does a “two-way reference” between an issue and a pull request mean? A: When one item references another by number, the referenced item also gets a back-reference. That makes the items link to each other automatically. (00:13:34)

  • Q: Why is it acceptable for one pull request to deal with all three required issues? A: The instructor says the point is to gain experience with the project-board system. A single pull request can therefore deal with multiple issues, even though one issue, one branch, and one pull request is the clean extreme. (00:14:23)

5. Pull-request descriptions, checkboxes, and auto-close keywords

00:16:17–00:22:18

  • Q: Why should the first comment on an issue or pull request be kept up to date? A: Other people typically look at the first comment to understand what is happening and why the item exists. Project owners can edit it because issues and pull requests evolve over time. (00:16:40)

  • Q: What are Markdown checkboxes in a pull request used for? A: They let you track items that are done or not done in the pull request. If the pull request is not marked as a draft, teammates can see that work is still unfinished. (00:17:37)

  • Q: What do the keywords closes and fixes do when they appear in a pull-request message? A: A sentence such as closes #1 or fixes #2 references those issues. When the pull request is merged, GitHub automatically closes the referenced issues. This is a GitHub service feature rather than part of the Git version-control system. (00:18:33)

  • Q: Why does the instructor prefer putting fixes #N in the pull-request message rather than relying on a commit message? A: It is easier to see in the pull request than in a commit message. When the merge happens, the issue tab gets smaller automatically, so you do not have to manually close several issues. (00:19:55)

6. Merging the pull request and cleaning up branches

00:22:18–00:25:29

  • Q: What does git switch main followed by git pull origin main accomplish after pull request #3 is merged? A: It moves the local checkout to main. Then git pull origin main brings the merged pull-request commit down from origin/main so the local README.md change is present. (00:22:25)

  • Q: Why is deleting the merged today branch on GitHub optional in this course? A: The instructor says you do not have to delete branches in this course. Some people keep branches as a record, and different teams or companies have different Git conventions. (00:23:16)

  • Q: Why run git fetch --prune and then git branch -d today after the remote today branch is deleted? A: The local machine still has branch references that show up in git log --oneline --graph --all. git fetch --prune removes the remote-tracking reference, and git branch -d today deletes the local branch reference while the merge commit remains. (00:24:30)

7. Why containers: a stable, shareable compute environment (27 Introduction to containerization)

00:25:29–00:33:21

  • Q: Why does DSCI 522 move from a single supplied package file to projects that need their own environments? A: Data-science projects can last days, weeks, or years and are often team-based. Each project may need a stable compute environment that more than one person can share. (00:26:11)

  • Q: Why does the instructor say “this works on my machine” is not good enough? A: A teammate may have a different operating system or CPU architecture, such as a Windows ARM machine versus your Mac. The course goal is a shared compute environment where all the code can run. (00:29:32)

  • Q: Why does the instructor advise keeping the package list to the bare minimum? A: Installing packages you do not use wastes disk space. Later, updating everything in one go can fail because different packages have different update cycles and may become incompatible. (00:27:38)

  • Q: Why can a container act as a sandbox for learning operating-system commands? A: It adds an extra layer between you and your real machine. If you break the sandbox, you can restart it and get a new one rather than damaging your computer. (00:33:05)

8. Containers versus virtual machines (27 Introduction to containerization)

00:33:21–00:36:47

  • Q: What is the difference between a virtual machine and a container? A: A virtual machine installs a full operating system with a graphical interface you can log into. A container is a stripped-down environment containing only the bare minimum software you need and usually just a terminal. (00:34:48)

  • Q: Why are containers more performant than virtual machines? A: They do not include a full visual operating system. That makes them use less disk space, memory, and compute. (00:35:33)

  • Q: Why does the instructor still use virtual machines? A: He uses them when he needs to test the MDS install by pretending he is on a Windows machine. In that case, having a full operating system is the point. (00:36:01)

9. Running the R container: docker pull and docker run (28 Using and running containers)

00:36:47–00:45:01

  • Q: What does the tag 4.3.2 mean in docker pull rocker/r-ver:4.3.2? A: It selects the image whose R version is 4.3.2. That lets the container run R 4.3.2 even when the host machine has a different R version. (00:37:26)

  • Q: Why is running rocker/r-ver:4.3.2 a useful example for a stable analysis environment? A: It shows you can keep a fixed R version for a long-running analysis, such as clinical-trial or drug-submission work. The host’s R can keep upgrading without changing the analysis environment. (00:37:54)

  • Q: What do the flags --rm and -it do in docker run --rm -it rocker/r-ver:4.3.2? A: --rm deletes the container when it stops so stopped containers do not pile up. -it gives an interactive terminal, with -i keeping input open and -t attaching a TTY. (00:40:55)

  • Q: Why does library(tidyverse) fail inside the bare rocker/r-ver:4.3.2 container but work on the host? A: The bare container only has R installed, not tidyverse. The host has its own packages, which shows that the two terminals are effectively different machines. (00:43:49)

  • Q: Why does the instructor emphasize paying attention to the prompt when working in a container? A: The prompt is often the only visual cue that you are typing in the container rather than on your local machine. This is similar to connecting to a remote machine, where you need to know which machine you are on. (00:45:04)

10. Web-app containers: RStudio and browser-first tools (28 Using and running containers)

00:45:01–00:54:10

  • Q: Why can applications such as RStudio, Jupyter Lab, and VS Code be run in a container and opened in a browser? A: Many of these tools are browser-first applications. They can run on a remote or container machine while still giving the user the same application interface. (00:47:15)

  • Q: What does it mean that Jupyter Lab is built to run in a browser? A: It means you can connect to Jupyter Lab that is running in a container or on a bigger machine. You still use the familiar browser interface even though the compute is elsewhere. (00:48:04)

  • Q: Why does the instructor choose the RStudio container as the example for running “an actual application”? A: The instructor calls the RStudio example the easier one to teach. RStudio can be run as a web app inside a container and then accessed through a browser. (00:46:47)

11. Port mapping the RStudio container (28 Using and running containers)

00:54:10–00:59:14

  • Q: What does -p 8787:8787 do in docker run --rm -p 8787:8787 rocker/rstudio:4.4.2? A: It maps port 8787 on the local computer to port 8787 inside the container. RStudio is listening on that internal port, so the browser can reach it at localhost:8787. (00:56:31)

  • Q: Why can you run the RStudio container more than once at the same time? A: The container’s internal port is fixed at 8787, but you can map it to a different local port. That lets multiple RStudio containers run at the same time on different local ports. (00:56:38)

  • Q: What does the instructor mean by saying port numbers are “very arbitrary”? A: The number is chosen by the tool or image, and you can map to many different local ports. Numbers like 8787 or 8888 are common conventions rather than required Docker rules. (00:56:19)

  • Q: Why is --rm useful when running several RStudio containers? A: Each running container uses RAM on the computer. --rm shuts down and removes the container when you exit, so you do not leave many machines running. (00:55:06)

12. Environment variables and running dashboards in containers (28 Using and running containers)

00:59:20–01:03:00

  • Q: What does -e PASSWORD="apassword" do when running the rocker/rstudio:4.4.2 container? A: It passes the environment variable PASSWORD into the container. The RStudio image uses that value to set the login password instead of generating a random one. (00:59:29)

  • Q: Why did the instructor check whether port 8787 is available to someone who cannot log into the host machine? A: He wanted to verify what the port mapping actually exposes. If you cannot log into the physical host machine, the local port is not available to you. (01:00:16)

  • Q: Why can a dashboard be deployed as a container in a course like DSCI 532? A: The container can include all the installation and environment setup. An end user only needs Docker, then runs the container and opens the dashboard’s port. (01:01:47)

13. Building interactively: base image and the cowsay package (29 Customizing and building containers)

01:03:00–01:08:46

  • Q: Why does the instructor start from rocker/r-ver:4.6.2 instead of an empty machine? A: The base image already has R and some of the system setup needed for R to work. It can skip several low-level installation steps, such as compiler setup that Windows and Mac users otherwise had to do by hand. (01:03:42)

  • Q: Why run docker run --rm -it rocker/r-ver:4.6.2 bash rather than letting the container start R? A: The bash command overrides the image’s default start-up, which would otherwise open R. It gives a terminal where you can test installation commands before writing them into a Dockerfile. (01:04:44)

  • Q: Why does cowsay disappear after you exit and restart the rocker/r-ver:4.6.2 container? A: A container has no saved state for interactive changes. When you turn it off and start the image again, it resets to the original image without the package you installed. (01:06:49)

  • Q: Why is a container a safe place to practice destructive command-line operations? A: If you “delete the computer,” you are only deleting the container. You can restart from the image and get a clean machine without affecting your real computer. (01:07:25)

14. Writing the Dockerfile: FROM, RUN, and CMD (29 Customizing and building containers)

01:08:46–01:15:01

  • Q: What is the role of a Dockerfile in the class’s workflow? A: It is the plain-text file that records the instructions for building the container machine. It specifies which base image to start from and which packages or setup commands to run. (01:10:18)

  • Q: What does the FROM rocker/r-ver:4.6.2 line tell Docker? A: It sets the starting-point image for the new image. The build therefore begins with a machine that already has R 4.6.2 installed. (01:11:17)

  • Q: Why is Rscript -e "install.packages('cowsay')" the form used in the Dockerfile instead of starting R interactively? A: RUN lines need terminal commands, and Rscript -e runs an R expression from the command line. The outer double quotes and inner single quotes keep the shell quoting correct. (01:09:07)

  • Q: What does CMD ["Rscript", "-e", "cowsay::say('Hello from my first image!')"] control? A: It sets the default command that runs when a container from the new image starts. The container prints the cowsay message unless you override it with another command such as bash. (01:13:25)

15. Building and running the hello-cowsay image (29 Customizing and building containers)

01:15:01–01:18:44

  • Q: What does docker build --tag hello-cowsay . do? A: It builds an image named hello-cowsay from the Dockerfile in the current directory. The . tells Docker where to look for that file. (01:15:06)

  • Q: Why does the instructor use . as the build context in the build command? A: It assumes you are running the command from the project root, where the Dockerfile lives. That matches the milestone instruction to assume commands are run from the directory root. (01:16:29)

  • Q: Why does docker images matter after running the build? A: It lists the local images so you can confirm that the new hello-cowsay image exists. It also shows the image’s disk usage. (01:17:01)

  • Q: Why does docker run --rm -it hello-cowsay bash show that library(cowsay) works? A: The image’s RUN step installed cowsay at build time. A shell started from the new image therefore has the package already present. (01:17:52)

16. Version pinning and wrap-up (29 Customizing and building containers)

01:18:44–01:20:39

  • Q: Why does the instructor advise pinning tool versions, such as Quarto, in a Dockerfile? A: Pinning the install line means the image will install the exact versions you chose. As long as you do not change that line, a year later you can still be on the same tool versions. (01:19:25)

  • Q: What problem did the instructor report when a container was restarted without hard-version-pinning its tools? A: An update had happened the day before the instructor restarted the container. After that, nothing worked, so time was spent fixing the update instead of doing the actual project work. (01:19:50)

  • Q: What is the purpose of the placeholder for the language and package setup that the instructor mentions for the Dockerfile? A: It is where the Dockerfile will install the programming language, Quarto, and the package environment. That lets the image contain the full compute environment, not just the base language. (01:19:02)
