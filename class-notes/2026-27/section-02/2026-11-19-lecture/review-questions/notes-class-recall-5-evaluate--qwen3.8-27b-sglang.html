1. Docker Desktop and pre-lecture pulls (Download the images before you start)

00:00:14–00:01:41

  • Q: A teammate plans to run the three pre-lecture docker pull commands on a laptop while Docker Desktop is closed, because they want to download the images before class. Is that plan acceptable for the class setup? A: No, the instructor says Docker Desktop must be open before running these commands; otherwise Docker may report that it cannot be found and tell you to turn it on. The pre-lecture pulls are meant to have the images ready while the class is checking the environment. (00:00:33)

2. Project scope: keep it simple and correct

00:01:41–00:06:05

  • Q: A group project plan replaces the required simple regression with a neural network because the team wants a more impressive portfolio model in this course. Would you approve that plan? A: No, the instructor’s biggest tip is to keep the analysis simple and technically correct, and if the model is fitting a straight line, fit the straight-line model. DSCI 522 is not a model-fitting course, and over-complicating the analysis now is the mistake that can backfire later. (00:02:03)

  • Q: A teammate proposes fitting logistic regression to predict a numeric outcome because the outcome scale is 0 to 1. Is that acceptable according to the class’s correctness criterion? A: No, the instructor explicitly says you should not be fitting logistic regression when you are trying to predict a numeric outcome. The class cares that the data science and machine-learning technique is technically correct, not that the model has a high accuracy score. (00:05:24)

3. Branch, commit, and push for the pull-request task

00:06:05–00:09:50

  • Q: A branch plan edits README.md, runs git add README.md and git commit while git status shows main, then creates the today branch after the commit. Is that acceptable for the class’s branch workflow? A: No, in a branch workflow you should check the branch with git status right before git add and definitely before git commit. The demonstrated workflow creates the branch with git switch -c today before committing the README.md change. (00:08:08)

  • Q: A plan skips git pull origin main before creating a branch because the local repository was just cloned. Is that acceptable in an actively collaborating environment? A: No, the instructor says to make sure main is pulled so your work is not based on something out of date. That matters when multiple people are actively working in multiple branches. (00:08:27)

4. Issues as a project board

00:09:50–00:16:17

  • Q: A teammate argues that the demo repository’s issue #1 and issue #2 require two separate pull requests, one for each issue, even though the today branch changes the same README.md. Is that required by the class? A: No, the class says one extreme is one issue, one branch, and one pull request, but one pull request is allowed to deal with all of your issues. The requirement is to have three issues and practice the project-board system, not to split every issue into its own pull request. (00:14:23)

5. Pull-request descriptions, checkboxes, and auto-close keywords

00:16:17–00:22:18

  • Q: A pull request’s first comment only says “update README”; the necessary fixes #2 is added in a later comment after discussion. Would you approve that description? A: No, the class says the first comment should carry the references and context because people look there rather than the whole conversation. A strategic first comment can use closes or fixes so that merging the pull request auto-closes the referenced issues. (00:16:40)

6. Merging the pull request and cleaning up branches

00:22:18–00:25:29

  • Q: A team rule says a merged pull request is not finished until the remote branch and local branch are deleted. Is that a requirement in this course? A: No, the class explicitly says it is not requiring branch deletion; you may keep branches as a record, and other teams may use different Git practices. git fetch --prune and git branch -d today are cleanup steps, not a course rule. (00:23:16)

7. Why containers: a stable, shareable compute environment (27.1 Documenting and loading dependencies)

00:25:29–00:33:21

  • Q: For a team project where members use Macs and Windows machines with different CPU architectures, a teammate says the uv.lock file alone is enough because it pins package versions. Is that sufficient? A: No, lock files pin package versions but do not capture the tooling or system environment. The class’s criterion is a shareable compute environment that can run the same code across different operating systems and architectures, which a container provides as a virtual computer. (00:38:46)

8. Containers versus virtual machines (27.3 Contrasting containers with virtual machines)

00:33:21–00:36:47

  • Q: Two setup options are a full Windows virtual machine with a graphical interface and a container with only R and the analysis stack. Which would you recommend for sharing a command-line reproducible analysis, and why? A: Recommend the container, because the class contrasts virtual machines as full operating systems that can take 50 to 80 GB with containers as stripped-down environments that are lighter in disk, memory, and compute. A container can still run the full computational stack while fitting the command-line workflow. (00:36:01)

9. Running the R container: docker pull and docker run (28.1 Launching containers using Docker at the command line)

00:36:47–00:45:01

  • Q: A teammate proposes running docker run -it rocker/r-ver:4.3.2 for a short practice and keeping the stopped container because they might need it later. Is that the class’s preferred practice? A: No, the class uses --rm so the container is deleted automatically when it stops, avoiding stopped containers piling up. Without --rm, you would have to manually delete the container afterward. (00:40:55)

  • Q: A plan says library(tidyverse) should work in rocker/r-ver:4.3.2 because it works in the host terminal. Is that reasoning acceptable? A: No, the container is a separate virtual computer, and the bare R image does not include tidyverse. The class showed that library(tidyverse) fails in the container while it works on the host, using the prompt as the cue that you are typing in a different machine. (00:43:54)

10. Web-app containers: RStudio and browser-first tools (27.2 What is a container?)

00:45:01–00:54:10

  • Q: A plan says the RStudio container is useless unless the end user also installs RStudio locally. Is that acceptable according to the class’s discussion of browser-first tools? A: No, the class treats RStudio as a web application that runs inside the container and is opened through a browser. That is the same browser-first idea shown for JupyterLab and VS Code, so the container can provide the application interface without a local install. (00:48:04)

11. Port mapping the RStudio container (28.1.3 Mapping ports to containers with web apps)

00:54:10–00:59:14

  • Q: A teammate proposes running a second RStudio container with docker run --rm -p 8788:8788 rocker/rstudio:4.4.2 because the local port must be 8788. Is that command acceptable? A: No, the class’s -p host:container mapping requires the container side to be the port RStudio listens on, 8787. To run a second instance on a free local port, map that port to 8787, for example -p 8788:8787. (00:57:05)

12. Environment variables and running dashboards in containers (27.2 What is a container?)

00:59:20–01:03:00

  • Q: A teammate proposes omitting -e PASSWORD="apassword" and using whatever random password the first RStudio container prints. Is that the better approach for reproducible team use? A: No, the class shows you can pass the PASSWORD environment variable with -e so the container uses a known password instead of a generated one. The demonstrated command is docker run --rm -p 8787:8787 -e PASSWORD="apassword" rocker/rstudio:4.4.2. (01:00:05)

  • Q: A plan claims that mapping -p 8787:8787 makes the RStudio web app available to anyone on the local network. Is that the class’s conclusion? A: No, the class checked that if a person cannot log into the physical machine, the mapped localhost port is not available to them. The demonstrated point is that the container is reached locally after mapping the host and container ports. (01:00:28)

13. Building interactively: base image and the cowsay package (29.1.1 Workflow for building a Dockerfile)

01:03:00–01:08:46

  • Q: A teammate installs cowsay in a running rocker/r-ver:4.6.2 container, exits, and tells the team to use that same container later because it now has the package. Is that acceptable? A: No, the class showed that a container has no save state: after exiting and starting the image again, the runtime-installed package is gone. The reproducible alternative is to document the working install command in a Dockerfile and build an image. (01:07:04)

14. Writing the Dockerfile: FROM, RUN, and CMD (29 Customizing and building containers)

01:08:46–01:15:01

  • Q: A Dockerfile line says RUN install.packages("cowsay") because that is the R command used interactively. Is that line acceptable? A: No, RUN runs a Bash command during the image build, so the R expression must be executed through the command-line interface. The class used RUN Rscript -e "install.packages('cowsay')" because Rscript -e runs the R expression for the build step. (01:12:44)

15. Building and running the hello-cowsay image (29.1.2 Build your first image)

01:15:01–01:18:44

  • Q: A plan runs docker build --tag hello-cowsay . from inside a subdirectory while the Dockerfile is in the repository root. Is that acceptable? A: No, the . tells Docker to use the current directory as the build context where it looks for the Dockerfile. The class assumes you run this from the directory containing the Dockerfile, which is the repository root for milestone-one style instructions. (01:15:38)

16. Version pinning and wrap-up (29 Customizing and building containers)

01:18:44–01:20:39

  • Q: A Dockerfile installs Quarto with a command that always takes the latest version instead of pinning a version. Would you approve it for a reproducible group project? A: No, the class’s warning is to hard-pin tool versions so a build does not silently change when something updates. The instructor’s unpinned example broke after an overnight update, turning the work into hours of fixing an unexpected tool change. (01:19:50)
