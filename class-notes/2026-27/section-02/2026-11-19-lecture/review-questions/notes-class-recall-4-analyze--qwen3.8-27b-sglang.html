00:06:05–00:09:50

  • Q: Follow the today branch in the 2026-11-19-docker demo repository from the modified README.md to the pushed remote branch: which local commands change the local state, which command creates the remote branch, and how does that make GitHub’s pull-request path possible? A: git switch -c today creates and moves to today, so the subsequent commit will not go to main. git add README.md stages the one-line change shown by git diff, and git commit -m "today we are talking about containers" creates the local commit on today. git push origin today sends that commit to GitHub and creates the remote today branch. The push response prints a GitHub URL for creating a pull request from that remote branch. (00:09:25)

4. Issues as a project board

00:09:50–00:16:17

  • Q: Examine issue #1, issue #2, and pull request #3 in the 2026-11-19-docker demo repository: how do GitHub’s shared numbering and two-way hash references turn a meeting note, an action item, and a code change into one tracked project thread? A: Issues and pull requests use one shared counter, so the meeting note is #1, the action item is #2, and the branch change becomes #3. Referencing #1 in issue #2 creates a back-link, so the action item points to the meeting that produced it. Put the same references in the pull request description, and the pull request links back to the issues it addresses. This makes the project board show responsibility, progress, and related work without a separate document. (00:13:34)

7. Why containers: a stable, shareable compute environment (27.1 Documenting and loading dependencies)

00:25:29–00:33:21

  • Q: Break down the course’s “stable, shareable compute environment” goal into package lock files, operating-system/architecture differences, and the container. A: The class moves from instructor-supplied package lists to team projects where package needs differ by project and language. A lock file such as uv.lock or renv.lock keeps package versions consistent on one machine, but a teammate may have a different operating system or CPU architecture, such as Mac versus Windows or ARM versus Intel. The instructor’s solution is to build a virtual computer and share that container instead of asking everyone to replicate the local machine. This lets everyone run the same code through one shareable compute environment instead of depending on a private local machine. (00:31:17)

8. Containers versus virtual machines (27.3 Contrasting containers with virtual machines)

00:33:21–00:36:47

  • Q: Set a virtual machine and a container side by side on interface, operating system, and resource use, using the instructor’s comparison from class. A: A virtual machine installs a full operating system, such as Windows, and gives a graphical interface you log into. A container is stripped down to the bare minimum needed for the task and normally has only a terminal, not a graphical interface. The instructor contrasts a virtual machine’s 50 to 80 GB size with containers used in class that can be under about one to two gigabytes. Because containers carry fewer resources, they are lighter in disk, memory, and compute. (00:36:16)

A: The host reports R 4.6.2, while the pulled rocker/r-ver:4.3.2 image supplies a Linux container with R 4.3.2. docker run --rm -it rocker/r-ver:4.3.2 starts that container and gives an interactive R session from the container’s own environment. library(tidyverse) fails in the container because the image only has R, while the host terminal can load tidyverse from the host’s installed packages. The different version and different package availability show that the two terminals are operating in different machines. (00:44:09)

10. Web-app containers: RStudio and browser-first tools (27.2 What is a container?)

00:45:01–00:54:10

  • Q: Examine the instructor’s point that RStudio, JupyterLab, and VS Code are browser-first applications: what does that make possible when such an application is placed in a container, and where does the user’s interface actually run? A: Browser-first tools are built to serve their interface over a browser instead of requiring a local desktop double-click. Placing one in a container lets the application run inside the container while the user still opens the familiar interface in a local browser. The container supplies the compute environment and the application server, while the browser provides the graphical front end. This is the same idea as connecting to a remote cloud machine: the interface is local, but the work is done on another machine. (00:48:33)

11. Port mapping the RStudio container (28.1.3 Mapping ports to containers with web apps)

00:54:10–00:59:14

  • Q: Break down docker run --rm -p 8787:8787 rocker/rstudio:4.4.2 into the container-side port, the host-side port, and the browser address that makes RStudio reachable. A: Inside rocker/rstudio:4.4.2, RStudio listens on port 8787. The -p 8787:8787 flag maps a port on the local host to that container port, so the container’s service becomes reachable from the host. The user then opens localhost:8787 in a browser to get the RStudio sign-in page. To run another RStudio container at the same time, the container side can stay 8787 while the host side is mapped to a different available port. (00:57:05)

13. Building interactively: base image and the cowsay package (29.1.1 Workflow for building a Dockerfile)

01:03:00–01:08:46

  • Q: Trace why installing cowsay inside an interactive rocker/r-ver:4.6.2 container disappears after exit, and why the class runs docker run --rm -it rocker/r-ver:4.6.2 bash before writing the Dockerfile. A: The command ends with bash, which replaces the image’s default startup command, so the user gets a shell instead of immediately starting R. Inside that shell, Rscript -e "install.packages('cowsay')" can be tested as a non-interactive command that later fits a RUN line. When the container exits, --rm removes the running container, and the image has no saved state for packages installed only in that run. Starting the container again returns to the original image, so cowsay is missing until it is installed at build time. (01:07:25)

14. Writing the Dockerfile: FROM, RUN, and CMD (29.2 Dockerfile command summary)

01:08:46–01:15:01

  • Q: Break down the class Dockerfile into its FROM, RUN, and CMD lines, and say what each contributes to the behavior of the hello-cowsay image. A: FROM rocker/r-ver:4.6.2 chooses the base image and supplies R 4.6.2 as the starting machine. RUN Rscript -e "install.packages('cowsay')" installs cowsay while the image is built, so the package is baked into the image. CMD ["Rscript", "-e", "cowsay::say('Hello from my first image!')"] sets the default command that runs when a container starts from this image. A command after the image name in docker run, such as bash, can override that default for a one-time run. (01:13:40)

15. Building and running the hello-cowsay image (29.1.2 Build your first image)

01:15:01–01:18:44

  • Q: Trace how docker build --tag hello-cowsay ., docker images, docker run --rm -it hello-cowsay, and docker run --rm -it hello-cowsay bash together prove that the Dockerfile was built and that the image’s CMD can be overridden. A: docker build --tag hello-cowsay . reads the Dockerfile from the current directory and builds an image named hello-cowsay. docker images shows that local image, confirming it exists after the build. docker run --rm -it hello-cowsay runs without an extra command, so it executes the CMD and prints the cowsay message. docker run --rm -it hello-cowsay bash replaces the CMD with a shell, where library(cowsay) works because the RUN step installed it. (01:17:14)

16. Version pinning and wrap-up (29 Customizing and building containers)

01:18:44–01:20:39

  • Q: Examine where unpinned tool versions can break the Dockerfile-based workflow the class just built, and identify which Dockerfile lines act as the control point for keeping versions stable. A: The warning bites when a Dockerfile installs tools with floating or latest versions, so an external update can change the image without the user changing the project. The instructor’s example was restarting a container after an unpinned tool updated, after which nothing worked and hours were spent fixing the update. A pinned FROM line fixes the base language/tool version, and pinned RUN install lines fix the versions of later tools such as Quarto, uv, or renv. As long as those lines are not changed, rebuilding should keep the same tool versions instead of silently updating them. (01:20:27)
