2. Working on main together versus working on branches (8 Git branches)

00:06:49–00:09:43

  • Q: Set two ways of coordinating a group project side by side as the class discussed: everyone committing to main together versus each teammate committing to their own branch. On the points of whether you must pull before you can push, whether your unfinished work is visible to teammates, and what you are waiting on, how do the two line up? A: When everyone works on main, the DSCI 521 slide-deck pattern repeats: you often have to pull before you can push even without a real conflict, because a teammate pushed first, and your half-finished work is immediately exposed on the shared branch. On a branch you are in “your own little world” where you can push and pull against your branch until it is done, so the pull-before-push friction disappears for your own work and your unfinished piece stays out of main. In the first approach you are waiting on teammates’ pushes to land; in the second you are waiting only for the review that brings the finished branch back (for example a Friday review), so coordination happens through the pull request rather than through constant pulls. (00:09:19)

3. The local repository versus the remote origin

00:09:46–00:11:11

  • Q: Set the local repository and the remote origin side by side the way the instructor drew them: what kind of work lives on each, which commands move work between the two, and which of the two is the thing that actually gets graded and published? A: The local repository is where you edit, stage, and commit; origin (the cloud) is the shared copy every teammate coordinates through, reached once by git clone and then with git push sending your commits up and git pull bringing teammates’ commits down. Because a group routes all work through origin, it is the shared source of truth, and your local and remote copies can diverge until you push or pull. The instructor’s point is that the remote is what matters: if your work exists only on your local computer it “effectively doesn’t really exist” for grading or project purposes, so the remote is the state that gets graded and published. (00:11:05)

4. main, origin/main, and HEAD in the diagram (8 Git branches)

00:11:11–00:16:05

  • Q: Examine the Git diagram the instructor drew: what do the pointers main, HEAD, and origin/main each track, and what happens to each when you keep committing on main without pushing versus when you commit on a newly created branch? A: HEAD is the pointer to whichever branch you are on, so when it points at main your commits land on main; main then moves forward one commit at a time; and origin/main is your computer’s record of where the remote main actually is. If you only commit on local main and never push, local main pulls ahead of origin/main, so the two diverge until a push or pull closes the gap. When you create a branch and commit on it, the new branch name — not main — is the one that increments as HEAD moves onto it, leaving both main and origin/main where they were. (00:14:31)

5. Branching even when working alone (8 Git branches)

00:16:05–00:17:54

  • Q: Break down the reason the instructor gave for using branches even when a single person is working (as with the course textbook): what does committing on a branch contribute that committing on main does not, and what task becomes much easier afterward? A: Committing on a branch sections off a large set of changes so main stays stable and only changes after you have reviewed and tested everything, whereas committing directly on main mixes the new work into the shared state immediately. The benefit shows up in undo: if a branch was a bad idea you can abandon or delete the whole branch and return to main at your starting point, which is far easier than unwinding a tangled set of commits on main by copying and reverting bits through the history. So the branch trades a little setup for a clean, cheap way to keep main stable and to discard work that did not pan out. (00:17:22)

6. Creating a branch with git switch -c (8.1 Creating a branch using the command line)

00:17:54–00:23:46

  • Q: Break the branch-creation workflow the instructor ran in the demo repository into its steps and say what each contributes: git status, git pull origin main, git switch -c dan-b1, and then git add / git commit. Which step protects you from starting on an outdated local state, and which step is the one that actually moves HEAD? A: git status confirms you are on main and that the tree is clean, giving you a safe base; git pull origin main syncs your local main with whatever everyone has pushed so you do not branch from an old state (the instructor noted this saves time across multiple computers); git switch -c dan-b1 is the step that creates the new branch and moves HEAD onto it; and the later git add / git commit write your work so that dan-b1, not main, moves forward. The sync step and the switch step play different roles: one aligns your starting point with the remote, the other redirects where your future commits will land. (00:21:13)

7. Switching branches and reading the log (8.1.1 Switching to branches that already exist)

00:23:46–00:28:26

  • Q: Separate what git switch dan-b1, git switch main, and git switch -c <name> each do to HEAD as the class used them, and what adding --all to git log --oneline --graph --decorate changes about the branches you see in the graph. A: git switch dan-b1 and git switch main both move HEAD onto an existing branch, so switching back to main returns the working files to whatever main last stored while dan-b1 stays parked where it left off; git switch -c <name> is the different one, creating a brand-new branch and moving HEAD onto it in a single step. Because a branch you have not visited may not show up otherwise, the --all flag on the log makes every branch name appear in the graph — the instructor pointed out that if you do not see your other branch names, that is the flag you need. Together these let you move HEAD around the history and inspect where each branch actually points. (00:25:46)

8. Pushing dan-b1 to origin and viewing it on GitHub (8.1.3 Useful command line Git branching commands)

00:28:31–00:33:40

  • Q: Trace what happens when dan-b1 is pushed to origin: why does a plain git push while you are on main report “Everything up-to-date,” what does git push origin dan-b1 add to your local log afterward, and how can a teammate view that branch’s code on GitHub before it is merged into main? A: A plain git push on main does nothing useful here because local main already matches origin/main, so Git just reports “Everything up-to-date”; the meaningful command is git push origin dan-b1, which changes only the last word from main to the branch name and sends that branch’s commit up. After it runs, your local log gains the origin/dan-b1 reference next to the commit, telling your computer that GitHub now holds that branch in the same place as your local copy, while main and origin/main stay where they were. On GitHub, the branch selector (the main dropdown) lets a teammate switch the view to dan-b1 and read its changes even though nothing has been merged, so the work is inspectable before review is complete. 10. The pull request conversation versus the code review (10 Code review on GitHub)

00:39:56–00:45:41

  • Q: Set two surfaces of the open pull request side by side — the Conversation tab and the Files Changed tab: what each is for, where an inline code-review comment lands, and what happens to the pull request when the author commits and pushes again to the same branch versus when a reviewer would try to fix the code themselves. A: The Conversation tab holds the discussion and the first comment, which the instructor kept as the definitive explanation of all the changes (editing it rather than piling on new notes); the Files Changed tab is where code review actually happens, showing the diff between the original and new file, with the plus button by a line starting an inline comment. Those inline comments all get tracked back in the Conversation tab, so a review like “why switch and not checkout” lives on the diff but is logged in the conversation. The rule of thumb is that if it is your pull request, it is your job to fix it — the reviewer points out the problem, the author goes back to the branch, commits, and pushes to the same branch, and the pull request updates automatically (an edited commented line may collapse as “outdated”), rather than the reviewer rewriting the code. (00:44:51)

11. Draft pull requests, merging, and deleting the remote branch (9.2 Draft pull requests)

00:52:11–00:58:51

  • Q: Break the “not ready yet” workflow for a pull request into its parts: what “Convert to Draft” changes visually on the pull request, what it does to the merge button and why that matters, and what “Ready for review” reverses when the work is done. A: “Convert to Draft” turns an open pull request into a draft, which shows a gray bar instead of the green one — the visual cue that you can still look inside but the work is not ready for merge. It also grays out the merge button, so nobody can accidentally merge something that is explicitly marked not-working or not-ready, which is the protection the draft provides. Because of this, the instructor keeps draft pull requests open for days or months as a signal to the team that work is in progress, and it also stops an agent from auto-merging everything green. When the work is ready, “Ready for review” (at the bottom of the conversation) turns the draft back into an open pull request, restoring the green buttons. (00:55:03)

  • Q: Trace the outcome after dan-b1’s pull request #1 is merged and its remote branch is deleted on GitHub: what happens to the branch dropdown, and what remains in the commit history — including what the merge itself adds? A: After merging #1 and clicking delete branch, the branch dropdown on GitHub shrinks (from two branches to one) so the list does not grow into a long pile of finished branches, which is the cleanup the instructor recommended. But deleting the branch marker does not delete the commits: the two commits that were on dan-b1 are still in history, and the merge adds its own commit (“Merge pull request #1 from chendaniely/dan-b1”) on top of main. So the visible branch disappears while the work persists — you can still jump back to those commits or to the merge commit to inspect or undo the feature. (00:58:27)

12. Local cleanup after a merge (8.1.3 Useful command line Git branching commands)

00:58:53–01:03:51

  • Q: Break the local cleanup sequence the instructor ran after dan-b1 was merged into its steps and say what each contributes: git switch main plus git pull origin main, git branch -a, git fetch --prune, and git branch -d dan-b1. Which step is where local main finally catches up, which step removes the now-deleted origin/dan-b1 reference, and where does the lowercase -d versus capital -D distinction bite? A: Switching to main and running git pull origin main is where local main catches up to the merged work, because local main does not update by itself after a GitHub merge. git branch -a lists local and remote-tracking branches (the star marks the current one) so you can see what is still around; git fetch --prune talks to origin and prunes the local reference to any branch deleted on GitHub, which is why origin/dan-b1 disappears from the log afterward. git branch -d dan-b1 then deletes the merged local branch, and the lowercase -d is the safety: it only deletes a branch that has been merged, protecting you from throwing away unmerged work. The warning is that a capital -D force-deletes even unmerged work, and copied-and-pasted AI advice might hand you -D when you meant the safe -d, so the distinction bites exactly at this final cleanup step where unmerged commits could be lost. (01:03:21)

13. How the two-branch merge conflict arises (8.3 What happens when my feature branch falls behind main?)

01:03:51–01:10:51

  • Q: Trace how a merge conflict arises in the two-branch demo: both dan-fetch and dan-delete start from the same main, so why does neither pull request show a conflict before either is merged, and what specifically happens to the second pull request after the first is merged into main? A: Because both dan-fetch and dan-delete branch from the same main and edit the same region of README.md, looking at the two pull requests side by side does not reveal a conflict — each just asks to merge into main and each looks green on its own. The conflict is latent until main itself moves: when the first pull request is merged, main advances, and GitHub rechecks every open pull request that targets main to see whether it can still be merged. The second pull request, which was based on the old main, now fails that recheck and surfaces as a conflict, so the outcome (a conflicted PR) is caused by the first merge changing the base branch rather than by anything visible in the second PR before that merge. (01:10:31)

14. Resolving the conflict with git rebase main and git push --force-with-lease (8.3.2 Using rebase)

01:10:51–01:20:42

  • Q: Break the local conflict-resolution workflow the instructor ran for dan-delete into its steps and say what each contributes: git switch main plus git pull origin main, git switch dan-delete, git rebase main, editing the file plus git add README.md plus git rebase --continue, and git push --force-with-lease origin dan-delete. Why must main be synced before the rebase, and why is a force-with-lease push required instead of a plain push afterward? A: Syncing main first (git switch main then git pull origin main) is required because the rebase replays your branch’s commit on top of the current main; if local main still lacked the already-merged pull request, you would rebase onto the wrong base. git switch dan-delete moves HEAD back to the conflicting branch, and git rebase main replays that branch’s commit onto the updated main, which is exactly where the conflict in README.md surfaces and you resolve it by editing, then git add README.md and git rebase --continue to finish. The rebase rewrites the commit history of dan-delete (its base moves from the old main to the new one), so a plain git push origin dan-delete no longer works and git push --force-with-lease origin dan-delete is what rewrites the remote branch to match, after which the pull request can be merged. The instructor’s caution is that fixing the visible conflict markers is not the whole job — the code or report must work from top to bottom afterward — and the force push is mandatory because the pushed history changed. (01:20:21)

  • Q: Distinguish resolving the dan-delete conflict in GitHub’s web editor from resolving it locally with git rebase main: what each approach requires, which one the instructor chose to show and why, and what extra local step the rebase path adds at the very end. A: The web-editor path is for simpler conflicts: you open the conflict in GitHub’s editor, fix the markers, and commit, keeping everything on the remote side. The local path is more involved but more general: you sync main, rebase the branch onto it, resolve the file, git add and git rebase --continue, and then you must also handle the remote. The instructor chose to show the local version “for complexity’s sake,” because the command-line process is the more general skill you will need when conflicts are not simple. The extra local step at the end is the git push --force-with-lease origin dan-delete, which the web path does not require, because rebasing rewrote the already-pushed branch’s history. (01:12:33)
