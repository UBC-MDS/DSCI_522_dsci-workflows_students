It is not just for this course but is carried through the rest of the MDS program, which is why it is “super important.” (00:02:01)

  • Q: Why is lab attendance mandatory in DSCI 522? A: Because the course is a group project, the TAs go around during lab and talk to every single group. Students need to be present when a TA is with their group, so attendance is mandatory. (00:02:19)

2. Why branches exist: escaping the pull-before-push friction (8 Git branches)

00:06:49–00:09:43

  • Q: Why did the shared slide deck exercise in DSCI 521 create friction even when no actual conflict occurred? A: Because even without a conflict, there was always the step of “I have to pull first because someone else pushed before I can push again.” If two people are working on the same thing at the same time, you always run into that coordination friction, whether or not a real conflict materializes. (00:07:06)

  • Q: What is the benefit of working in parallel streams with branches? A: You are in “your own little world” where you can push and pull until you are actually done, waiting for review from teammates. If the work is self-contained parallel work, it does not matter what other people are doing; you can work from Tuesday to Friday on your part of the project without being blocked. (00:08:46)

  • Q: Why does the instructor say the first week of the group project will “get a little bit weird”? A: Because not every project can start with four parallel pieces of work at the same time. There is always a part of a project where you are bound or stuck by one or two people getting the basics down first, and that problem exists in a project no matter what. (00:07:40)

3. Local repository versus remote origin (8 Git branches)

00:09:46–00:11:11

  • Q: Why does the instructor say that work existing only on your local computer “effectively doesn’t exist” for grading or project purposes? A: Because the remote is “the thing we grade” and “the thing that gets published.” If your code is only on your computer, “your product is not shipped because the code isn’t anywhere to be shipped.” The remote is the state that matters. (00:10:48)

  • Q: How does the remote origin serve as the coordination point when multiple teammates are working on the same repository? A: You coordinate with your GitHub remote, and your three other teammates also coordinate with the same remote. There is “a lot of coordination work that needs to happen” through that shared point, with git push sending your work up and git pull bringing others’ work down. (00:10:20)

  • Q: What does it mean that git clone is a “one-time command” in the local/remote relationship? A: Clone brings the repository down to your computer once; after that, the ongoing connection is maintained through git push (to send commits up) and git pull (to bring others’ commits down). You do not keep cloning; you push and pull to stay in sync. (00:11:25)

4. main, origin/main, HEAD, and what a branch is (8 Git branches)

00:11:11–00:16:05

  • Q: What is the difference between main and origin/main in the Git diagram? A: main is the local branch pointer that increments as you write commits on your computer. origin/main is “the remote, what your computer thinks the state of GitHub is at.” If you write commits on main without pushing, your local main moves ahead of origin/main. (00:13:30)

  • Q: How does a branch change the behaviour of git commit compared to committing on main? A: Instead of incrementing where main is when you write a commit, you increment “some other name that you give it yourself.” The same git add and git commit process applies, but the named branch moves forward while main stays where it is. (00:13:55)

  • Q: Why does the instructor compare main to a “production final” branch? A: Because in larger projects, you want other moving pieces to move at a steady rate. You do not want one person to try something on main and have it break on all of their teammates’ computers. Everything in main should be in working order and stable, even if not finished. (00:15:10)

  • Q: What does it mean that HEAD is “attached to” a branch? A: HEAD is the pointer into the Git history that shows which branch you are currently on. When HEAD is pointed to main, you are on the main branch; when you switch to a new branch, HEAD moves to point at that branch. It is the visual cue of your current location in the repository. (00:13:17)

5. Branches are useful even when working alone (8 Git branches)

00:16:05–00:17:54

  • Q: Why does the instructor say you can use branches even when working by yourself? A: To “section off work” and test a whole bunch of stuff without the main branch changing without reviewing everything. He gave the example of the course textbook, where he did all his work in a sequence of branches so the textbook would not “start things moving around like crazy in the middle of a teaching day.” (00:16:12)

  • Q: What is the advantage of abandoning a failed branch versus undoing a tangled set of commits on main? A: If something did not work, it is “really easy to delete a branch” and come back to main. Versus if you wrote one commit that did twenty different things on main, you would have to “go through the git history, start copying and pasting all the bits that are actually relevant,” which is really hard. (00:17:00)

  • Q: How do git reset and git revert relate to the undo capability that branches provide? A: The instructor acknowledged that you could use git reset and git revert (from DSCI 521) to undo commits on main, but branches “sort of just make that a little bit easier” because you can simply discard the whole branch and return to main as your starting point. (00:17:22)

6. Creating a branch with git switch -c (8 Git branches)

00:17:54–00:23:46

  • Q: Why should you synchronize with the remote (for example, git pull origin main) before creating a new branch for coordinated project work? A: So your starting point is “essentially up to date.” The instructor shared a personal example of creating a branch, forgetting he was working on three different computers, and realizing he had already done half the work on another laptop. Syncing first “could have saved [him] a bunch of time.” (00:18:09)

  • Q: What does git switch -c <branch> do that a plain git switch <branch> does not? A: The -c flag stands for create: it creates a new branch and immediately moves HEAD to it. Without -c, git switch just moves HEAD to an existing branch. The instructor summarized the -c version as “create and move head to the branch name.” (00:20:09)

  • Q: Why does the instructor sometimes prefix branch names with the owner’s name in group repositories? A: So that “other people know that if something’s going on around here and something’s weird, this is the person to talk to.” It is a signal about who owns that branch and who to contact if something looks off. (00:20:31)

  • Q: What happens to the Git log immediately after running git switch -c dan-b1 but before making any new commits? A: Not much changes: you still have main, the remote references, and a new branch called dan-b1 with HEAD on it. No new commit was made; the only difference is that HEAD is now attached to the new branch instead of main. (00:21:15)

7. Switching between branches and seeing the repository state (8 Git branches)

00:23:46–00:28:26

  • Q: Why does the instructor recommend using git switch rather than git checkout when teaching? A: checkout was doing what switch does (moving HEAD around) but also “did a lot of what revert and restore was doing.” If you are not comfortable with what checkout does, the instructor suggests asking tools to use switch instead, because switch has a narrower, more predictable behaviour. (00:27:09)

  • Q: What is the difference between git branch <name> and git switch -c <name>? A: git branch just creates the branch but “doesn’t move [HEAD] to it.” You still have to checkout or switch after creating it. git switch -c does both in one step: it creates the branch and moves HEAD to it. (00:28:13)

  • Q: Why does the --all flag matter when running git log --oneline --graph --decorate? A: Without it, you may not see your other branch names in the log output. The instructor noted that if you do not see your other branch names, that is why he has --all typed out; it ensures all branches appear in the graph. (00:25:38)

8. Pushing a branch to origin and viewing it on GitHub (8 Git branches)

00:28:31–00:33:40

  • Q: Why does the instructor say the easiest way to combine a branch into main is to “don’t do it on your local computer”? A: Because the class workflow uses a review process—pull requests—rather than local merges. The pull request is where you review your own work and your teammates’ work before incorporating it into the project. (00:28:58)

  • Q: What does it mean when origin/dan-b1 appears in the git log after running git push origin dan-b1? A: It means “GitHub also has a branch called dan b one and is in the same location as whatever exists on your local computer.” The local computer now knows that the remote has that branch, but main has not changed at all. (00:31:19)

  • Q: Why is it useful to view a teammate’s branch on GitHub before it is merged into main? A: You can see their code or work “even though it’s not combined into the main branch yet.” For example, if a teammate made a cool figure, you can look at their code without running it. It does not mean the work is completely reviewed and ready to merge, but you can look around. (00:32:36)

  • Q: Why do you need to change the last word in git push origin main when pushing a new branch? A: Because you are no longer pushing the main branch; you are pushing a different branch. The behaviour of push is “exactly the same,” but the target branch name changes from main to whatever branch you created, such as dan-b1. (00:30:44)

9. Opening a pull request and reviewing the changed files (9 Pull requests)

00:33:40–00:39:56

  • Q: Why does the instructor recommend opening a pull request immediately after pushing a branch, even if the work is not finished? A: Because the “Compare and Pull Request” popup disappears after a day or so. Starting the process right away means the pull request exists and updates as you keep pushing commits, so you do not lose the opportunity to begin the review workflow. (00:35:00)

  • Q: Why is the first comment in a pull request important, and why should you edit it rather than just appending new notes? A: “That’s what people are going to read.” All of your changes should be defined and explained in the very first comment. If you keep making changes to the pull request, you should edit the first message rather than just adding new ones, so the description stays coherent. (00:40:48)

  • Q: What two things should you check in the Files Changed tab before creating a pull request, and why does the second check matter? A: First, confirm that all the files and bits of code you thought you worked on actually exist. Second, check for files that “don’t really belong here,” like .ipynb_checkpoints, .DS_Store, or Word backup files, because in this course, if such unwanted files are visible in a repository, “we will take points off.” (00:38:44)

  • Q: Why does the instructor say to pay attention to where you are merging in the pull request? A: In DSCI 522, main is probably the target, but in 524, “main is not always going to be the branch that you’re going to be incorporating work into.” In large open-source projects with forks, you also need to make sure you are sending your code to the right repository and branch. (00:35:38)

10. Pull request conversation, code review, and updating the same branch (10 Code review on GitHub)

00:39:56–00:45:41

  • Q: What does the “Files Changed” tab in a pull request show, and how does it relate to what “code review” means? A: It shows “the diff between the original file and the new file.” Code review is literally looking at that diff and making comments on specific lines using the plus button, which then get tracked in the main conversation tab. (00:41:22)

  • Q: Why is it the pull request author’s job to fix issues rather than the reviewer’s job? A: The reviewer’s job is to say “rewrite this” or “this doesn’t look right.” It is the author’s job to “go and actually fix it” in the codebase. The instructor emphasized: “if it’s your pull request, it is your job to fix it all.” (00:42:17)

  • Q: How does a pull request update when the author makes additional commits, and why does the author not need to close and recreate it? A: The pull request is tied to the actual branch. You just go back to the branch, add, commit, and push to the same branch, and “the pull request will update.” You do not need to close the pull request and create a new one; it keeps track of all the information as you push. (00:43:15)

  • Q: What does it mean when GitHub “auto-collapses” a comment as outdated? A: It means you changed the line that the comment was attached to, so “that original comment, probably doesn’t exist anymore or is relevant anymore.” GitHub collapses it “just so you don’t end up looking at too much stuff.” (00:45:02)

11. Draft pull requests, merging, and deleting the remote branch (9 Pull requests)

00:52:11–00:58:51

  • Q: Why does the instructor create the pull request early and then convert it to a draft rather than waiting until the work is complete? A: To “make sure all the pipeline is working” and to signal to the team that work is in progress. The pull request updates as he keeps pushing the branch, and a draft communicates “we’re still working on this” without the risk of premature merging. (00:53:26)

  • Q: What is the purpose of disabling the merge button on a draft pull request? A: So “no one can actually accidentally merge something that is very explicitly saying this not working or this not ready yet.” The gray bar instead of a green one is the visual cue that the work is not finished. (00:54:30)

  • Q: Why does deleting the remote branch after merging not remove the commits from the project’s history? A: Because the commits have been merged into main; “the commits are still there. It’s not that the commits have been gone.” Even after deleting the branch marker, you can see the commits in the history, including a separate merge commit that says “this stuff got merged in.” (00:58:10)

12. Local cleanup after a merge: git pull, git branch -a, git fetch --prune, and git branch -d (8 Git branches)

00:58:53–01:03:51

  • Q: Why does your local main branch not automatically update after a pull request is merged on GitHub? A: Because “main doesn’t automatically update itself.” You need a synchronization step: switch to main and run git pull origin main to get the merged changes onto your local machine. (01:00:17)

  • Q: What is the difference between git pull origin main and git fetch --prune in terms of what happens to your local files? A: git pull does two things: it runs fetch and then merge on top, which changes your files. If you do not want the files on your computer to change, you only run git fetch, which “is coordinating the history” without modifying files. The --prune flag additionally removes local references to branches that were deleted on GitHub. (01:02:07)

  • Q: Why does git branch -d refuse to delete a branch that has not been merged? A: Because “if you delete it, in theory, you’ve lost work.” Git makes it harder to delete work that is kind of permanent. The lowercase -d only allows deletion if the branch has been merged; if it has not, the command will not delete it. (01:02:54)

  • Q: Why does the instructor specifically warn about capital -D when copying commands from tools like ChatGPT? A: Because capital -D force-deletes a branch even if it has not been merged. The instructor warned: “Be very careful if you’re copying and pasting commands from ChatGPT because it might just say capital D delete, force delete, and then you could delete the commits that you’re working on.” (01:03:21)

13. Creating a merge-conflict scenario with two branches (8 Git branches)

01:03:51–01:10:51

  • Q: Why did the instructor create two separate branches (dan-fetch and dan-delete) from the same main state to demonstrate a merge conflict? A: To simulate what happens when two people make changes to the same line of the same file. The conflict arises from “the same change to the same line of the same file,” which is what happens when two branches both modify a region that the other has already changed. (01:04:00)

  • Q: Why does looking at the two pull requests side by side not obviously reveal that they will conflict? A: Each pull request looks like it can merge into main individually. “It’s not very obvious that their starting point is from that main branch,” and “nothing here actually tells you that a merge conflict is going to happen.” The conflict only becomes apparent after one branch is merged. (01:09:17)

  • Q: What happens when the first pull request is merged that causes the second pull request to become conflicted? A: The main branch changes, and then “every single pull request that is merging into main is going to recheck to see if it can be merged.” The second pull request, even though it previously showed everything in green, now ends up on a conflict page because it can no longer merge cleanly. (01:10:19)

14. Resolving the conflict locally with git rebase main and git push --force-with-lease (8 Git branches)

01:10:51–01:20:42

  • Q: Why does the instructor say that “fixing” a merge conflict in this course means more than just removing the conflict markers? A: Because your code or report “needs to work from top to bottom again.” A conflict on line thirteen “doesn’t mean that’s the only place your code is going to affect.” If changing the conflict affects a variable used later in the file, that is still your problem to deal with. (01:11:21)

  • Q: What does git rebase main do, and why is it used to resolve the conflict on the dan-delete branch? A: It “replay[s] all of my commits in this branch back to the main branch over the main branch.” This moves the branch’s commit on top of the updated main, which is where the conflict appears on your computer so you can go and fix it in your text editor. (01:17:14)

  • Q: Why can you not use a normal git push origin dan-delete after rebasing, and why is a force push necessary? A: Because rebase “changed the history of that commit.” The previous commit is no longer the same version of main; the history is actually changed. “You have to force push to force update the branch” because a normal push will not accept the rewritten history. (01:19:34)

  • Q: How does the rebase approach to triggering a conflict differ from the DSCI 521 approach? A: In DSCI 521, the conflict was triggered by running git pull origin main on a branch that was behind. Now it is triggered by “replaying commits over another branch” with git rebase main. The resolution process—finding the markers, fixing the file, running git add, and continuing—is the same. (01:17:56)
