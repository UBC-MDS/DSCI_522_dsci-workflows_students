2. Creating the repository, cloning, and owning your code

00:04:52–00:08:59

3. Reading the Dockerfile: base image and RUN/apt-get (29.3 Choosing a base image for your Dockerfile)

00:08:59–00:13:18

  • Q: Why does the choice of base image matter for this project?
    • A: The base image sets a floor on the size of the final image. rocker/r-ver works for Python but includes R and takes more storage, so graders or other users download it longer; the goal is a bare-minimum image. (00:09:51)
  • Q: Why are RUN commands described as bash commands?
    • A: RUN commands are shell commands executed inside the container’s Linux operating system. MDS uses Git Bash because that is the same command vocabulary you will use inside Docker containers. (00:10:35)
  • Q: Why install git, nano, and openssh-server with apt-get?
    • A: apt-get is Ubuntu’s package installer for system-level software. Those packages are needed inside the image: git for version control, nano to inspect files without leaving the container, and openssh-server for later remote connections. (00:11:02)
  • Q: Why was the Quarto installation section deleted from the demo Dockerfile?
    • A: The class did not need that section for today, so deleting it saved time and space. Quarto remains in the reference because milestone containers need a way to run reports. (00:12:57)

4. Installing uv in the image and keeping the environment portable (29.1 Building container images from Dockerfile’s)

00:13:18–00:19:28

  • Q: Why does MDS avoid teaching requirements.txt for this course?
    • A: requirements.txt is not how uv generally works, and MDS manages Python through uv. Teaching multiple installation styles would create five different ways to install the same software with no benefit. (00:13:47)
  • Q: Why use COPY --from=ghcr.io/astral-sh/uv... to install uv?
    • A: The uv documentation points to a pre-built container that already has uv installed. Docker’s COPY can copy files from another container or image into the new image. (00:14:29)
  • Q: Why does the image need to control the uv version?
    • A: pyproject.toml tracks the versions of Python packages, but not the version of the uv tool itself. Docker is a way to keep complete control over all pieces of software installed in the image. (00:14:57)
  • Q: Why use WORKDIR /workspace?
    • A: It tells Docker to start in /workspace instead of the container’s operating-system root. It creates the folder if it does not exist and keeps dangerous commands like rm * away from the whole OS. (00:16:13)
  • Q: Why use /opt/venv rather than the host .venv?
    • A: A .venv created by uv sync is specific to the host’s operating system and CPU architecture. When the project folder is mounted, the container would otherwise see a virtual environment that does not match its Linux environment, so uv is told to use /opt/venv instead. (00:17:01)

5. Environment variables, uv sync --locked, and the project files (29.2 Dockerfile command summary)

00:27:21–00:34:25

  • Q: Why set UV_PROJECT_ENVIRONMENT as an environment variable?
    • A: Like Python variables, tools use environment variables to control their behavior. uv looks up UV_PROJECT_ENVIRONMENT when it runs commands to decide where the project’s virtual environment should live. (00:27:30)
  • Q: Why append the variable to /etc/environment with echo ... >>?
    • A: SSH logins do not read the process environment variable set by ENV. The echo ... >> line writes that setting into a file that logins do read. (00:28:41)
  • Q: Why use uv sync --locked in the Dockerfile?
    • A: --locked is a guard that fails if uv.lock and pyproject.toml are not in sync. It ensures the image only builds when the dependency files match. (00:29:15)
  • Q: Why include .python-version in the image?
    • A: It tells uv which Python version to download for this project. That allows different projects to use different Python versions without changing the whole machine. (00:32:23)
  • Q: Why use date versioning and add-bounds = "exact" in pyproject.toml?
    • A: The date version records when the course finalized the packages, and hard pinning tracks exactly which versions are in use. add-bounds = "exact" makes uv add write == instead of >=, keeping the project pinned. (00:30:54)

6. Building the image: docker build (29.4 Dockerfile FAQ)

00:34:25–00:35:47

  • Q: Why use the trailing . in docker build --tag docker-uv-renv .?
    • A: The dot means the current working directory. docker build looks for a file called Dockerfile in that directory by default. (00:35:06)
  • Q: What does the step-by-step build output mean?
    • A: Docker is executing the Dockerfile in order: starting from the base image, copying files, setting the working directory and environment, running uv sync, and then exporting the image. It shows that the build reached the final image. (00:35:21)
  • Q: Why can docker build be pointed at another directory or Dockerfile?
    • A: The path argument tells Docker where to find the build context and the Dockerfile. The default is the current directory’s Dockerfile, but a different location can be specified. (00:35:13)

7. Running the container: docker run flags and a different prompt (29.1 Building container images from Dockerfile’s)

00:35:47–00:38:22

  • Q: Why use --rm in docker run?
    • A: --rm tells Docker to remove the container when you exit and shut it down. It keeps the container from lingering after an interactive test. (00:35:59)
  • Q: Why use the combined flag -it?
    • A: -i requests interactive mode and -t allocates a tty terminal prompt. Single-letter flags can be chained after one dash, while multi-character flags such as --rm use a double dash. (00:36:14)
  • Q: What does the root@...:/workspace prompt mean?
    • A: It means you are in a different computer-like environment, the container. root is the container’s username and /workspace is a folder inside the container, not necessarily a folder on your laptop. (00:37:15)
  • Q: Why does python fail but uv run python work inside the container?
    • A: The image’s Python packages are installed through uv, and plain python is not on the container’s PATH. uv run python starts the Python from uv’s environment, where the project packages live. (00:37:52)

8. Mounting the project folder with -v (33.1 Docker Compose to launch containers)

00:38:22–00:44:42

  • Q: What does -v "$(pwd):/workspace" mean?
    • A: It mounts the host’s current working directory into /workspace inside the container. The command uses $(pwd) so the same mount command works across Windows and macOS. (00:38:52)
  • Q: Why mount the project folder instead of COPYing it in the Dockerfile?
    • A: COPY freezes the files at the time of docker build. If your analysis changes constantly, you would have to rebuild the whole image just to move updated files into the container; mounting separates software from changing files. (00:39:55)
  • Q: Why is mounting useful for Git commands?
    • A: The container is like a brand-new machine to GitHub and resets when it is turned off. With the folder mounted, you can run git add, git commit, and git push on the host instead of re-configuring Git credentials inside the container each time. (00:40:50)
  • Q: Why is mounting credentials better than baking them into the image?
    • A: An SSH key is effectively a password to your account. If it were baked into the image, anyone who pulls that container could read the credential; mounting keeps it present only while the container runs. (00:41:50)
  • Q: Why warn against editing the same file on both sides at the same time?
    • A: The two sides do not merge changes; whoever saves last can silently overwrite the other side. The instructor compares it to a Git conflict without Git and recommends using the editor’s revert/refresh before editing. (00:43:21)

9. docker-compose.yml: putting the launch in a file (33.1 Docker Compose to launch containers)

00:44:42–00:55:31

  • Q: Why use docker-compose.yml instead of a long docker run command?
    • A: A docker run command can pile up many flags and become hard to paste, track, or edit in a terminal. A compose file keeps the launch parameters documented and version controlled in a file. (00:45:02)
  • Q: What does services: analysis-env mean in docker-compose.yml?
    • A: It names the service that the project will run. The image name can be different from the service name, and multiple services can be created from the same setup. (00:46:24)
  • Q: Why can the service name be different from the image name?
    • A: The image is the built software environment, while the service name is the compose identifier for a running container configuration. That allows you to run more than one container from the same image with distinct names. (00:46:42)
  • Q: What does ports: - "2222:22" mean?
    • A: The first number is the host port you connect to, and the second is the container port where the service listens. SSH listens on 22 inside the container, while 2222 on the host avoids overwriting the common host port 22. (00:48:04)
  • Q: Why mount the SSH public key read-only in the compose file?
    • A: The public key becomes the authorized key for root login, but it is mounted only while the container runs. It is not permanently stored in the image. (00:50:13)

10. exec, down, and shutting containers down (33.2 Docker Compose commands)

00:55:31–00:58:24

  • Q: Why does docker compose exec analysis-env bash use the service name?
    • A: docker compose exec looks up the service name from docker-compose.yml. The long name shown by docker ps is Docker’s container name, and using it can produce a service ... is not running error. (00:55:56)
  • Q: What does exit from an exec shell mean?
    • A: It returns you to the host terminal. The container keeps running until you stop it with docker compose down. (00:57:23)
  • Q: Why use docker compose down?
    • A: It reads the compose file and turns off and removes the containers and network it created. It is the compose equivalent of stopping the project’s containers. (00:57:30)
  • Q: Why be diligent about turning containers off?
    • A: Containers are other computers and they consume RAM. Running many at once can make your machine’s available memory shrink. (00:57:38)

11. One-off commands: docker compose run (33.3 Running a Docker container non-interactively using the Docker Compose)

00:58:24–01:01:13

  • Q: What does docker compose run --rm analysis-env <command> mean?
    • A: It starts a new short-lived container for the analysis-env service and runs the command you give it. --rm deletes that container when the command finishes. (00:58:24)
  • Q: Why does docker compose run --rm analysis-env python fail?
    • A: There is no plain python executable in the image’s PATH because the Python work is done through uv. The working command is uv run python, which uses uv’s Python and packages. (00:59:10)
  • Q: Why run uv run quarto render through docker compose run?
    • A: The slot after the service name accepts a bash command, so you can tell the container to build a report. This checks that the analysis renders in the exact environment you designed, without rerunning it locally. (01:00:35)
  • Q: Why did the instructor call this the reproducibility payoff?
    • A: The image and container are a machine you made. Sending commands into that machine tests that the analysis works in the reproducible environment. (01:00:56)

12. Connecting Positron or VS Code to the container with Remote SSH (33.2 Docker Compose commands)

01:01:41–01:06:55

  • Q: Why connect with Remote SSH instead of Microsoft’s attach-to-container extension?
    • A: Positron and other VS Code forks do not have access to the Microsoft extension store. Remote SSH can connect to the container as a remote machine instead. (01:02:15)
  • Q: Why connect to root@localhost on the host port 2222?
    • A: root is the username inside the container, so the default host username would not match. localhost with the mapped port 2222 reaches the container’s SSH service, which listens on port 22 inside. (01:03:26)
  • Q: Why open the /workspace folder after connecting?
    • A: /workspace is the mounted project folder inside the container. Once opened, the IDE behaves as if it is working inside the container and commands run there. (01:04:33)
  • Q: Why is this setup a placeholder for cloud computing?
    • A: The same remote-connection idea can point at a bigger machine over the internet when the local machine is too small for the dataset. It is the same workflow of connecting to another machine and working through an IDE. (01:05:19)

13. Docker Compose outside the classroom (33 Containers: Docker Compose)

01:06:55–01:08:33

  • Q: Why are Docker Compose files useful outside this course?
    • A: Many self-hosted open-source services ship a docker-compose.yml that lists their services, image, ports, environment variables, and volumes. docker compose up starts those services using that file. (01:06:59)
  • Q: What does the actual budget example show?
    • A: It shows a personal finance application that has a compose file with a service, image, port, and environment settings. The instructor runs it with docker compose up -d and it listens on port 5006. (01:07:41)
  • Q: Why does he say this skill is not only for MDS computational work?
    • A: The same pattern can be used to run containerized services on old Linux laptops or spare machines. It is a general deployment skill, not just a data-science course skill. (01:07:32)

14. Data validation setup: packages by hand (41 Data validation: Python (pointblank))

01:08:33–01:11:40

  • Q: Why did the instructor add packages by hand after uv add failed?
    • A: The uv add pandera pointblank command failed with an error about a missing [project] table, and he did not diagnose that live. Manually adding packages to pyproject.toml and running uv sync was the fallback he gave. (01:09:38)
  • Q: Why run uv sync after editing pyproject.toml?
    • A: uv sync resolves the packages in the project file, installs them, and creates or updates uv.lock. It is how the lock file is produced from the TOML file. (01:09:54)
  • Q: Why use palmerpenguins in the validation demo?
    • A: The class needed a dataset to validate, and load_penguins() provides the Palmer penguins data used in the examples. It gives a concrete data frame for pointblank checks. (01:10:09)
  • Q: Why import pointblank as pb?
    • A: The package is imported as pb so the demo can call pointblank functions concisely, such as pb.missing_vals_tbl. This is the alias used in the validation code. (01:10:52)

15. Why validate, and where the missing values are (41.1 Where are the missing values?)

01:11:40–01:13:45

  • Q: Why validate data before modelling?
    • A: Validation checks in code that the data actually contains the values you expect, such as not having pregnant men in health data. It also tests assumptions about ranges, like an upper bound for BMI. (01:11:48)
  • Q: Why check for 99 in survey data?
    • A: Some health survey data code missing values as 99 instead of a real missing value. Validation should follow the codebook and flag those non-real values. (01:12:15)
  • Q: What does pb.missing_vals_tbl(data=penguins) mean?
    • A: It reports where missing values are, broken into sections of rows from the top of the data. In the demo, it showed that much missingness was concentrated near the beginning. (01:12:47)
  • Q: What does the visual missingness view mean?
    • A: It shows whether there are “holes” in the data where values are missing. The instructor says the interpretation is subjective, but it starts the conversation about data quality. (01:13:18)

16. Chaining value checks with pb.Validate (41.2 Checking values)

01:13:45–01:18:29

  • Q: Why use thresholds=(0.01, 0.05, 0.10)?
    • A: The thresholds tell pointblank when to flag a step: warning when about 1% of rows fail, error at 5%, critical at 10%. They let you tolerate small problems while flagging larger ones. (01:14:20)
  • Q: Why use col_vals_in_set for species?
    • A: It checks the assumption that a column contains only certain allowed values. In the demo, it was used to test species values in code, including whether capitalization or unexpected values appear. (01:15:11)
  • Q: Why use col_vals_between for bill_length_mm?
    • A: It checks that values fall between sensible bounds, here 30 and 60. The check is inclusive by default, and the same idea can be used for columns like BMI that should have reasonable ranges. (01:16:07)
  • Q: Why use rows_distinct()?
    • A: It checks that each row is different. That is useful when duplicate rows would be a problem, such as duplicate sensor readings or two people coding the same record. (01:16:47)
  • Q: Why call interrogate()?
    • A: interrogate() is the method that actually runs all the chained checks. Before calling it, the steps are only defined on the validation object. (01:17:10)
  • Q: Why keep missing-value checks separate from value checks?
    • A: Missing values and out-of-range values are different problems that are often handled differently. The instructor recommends doing missingness as a separate analysis, checking per column and per row. (01:18:52)

17. Splitting passing and failing rows (41.4 Splitting the passing and failing rows)

01:18:29–01:20:48

  • Q: Why use values.get_sundered_data(type="pass")?
    • A: It returns a separate data frame containing the rows that passed every step. That frame can be passed to a downstream teammate who can build the next part of the pipeline on data that currently works. (01:19:52)
  • Q: Why use values.get_sundered_data(type="fail")?
    • A: It returns the rows that failed at least one check. That gives the person responsible for cleaning a focused set of rows to fix. (01:19:36)
  • Q: Why is this useful for a team project?
    • A: Downstream work does not have to wait for the data to be 100% clean. The team can split work: one person continues cleaning while another uses the passing rows. (01:19:08)
  • Q: Why can the failed rows be saved to a CSV?
    • A: The sundered results are ordinary data frame objects. They can be saved to CSV files so another person can pick up a concrete dataset to fix. (01:20:32)
