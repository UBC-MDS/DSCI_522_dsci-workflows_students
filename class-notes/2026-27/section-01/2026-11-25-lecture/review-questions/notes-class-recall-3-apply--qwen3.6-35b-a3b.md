- **Q:** You are starting a new Python-only project and want to minimize container download time. You notice the reference `Dockerfile` uses `rocker/r-ver:4.6.2`. What change do you make to the `FROM` line, and why?
    - **A:** Change `FROM rocker/r-ver:4.6.2` to a lighter Python or Ubuntu base image like `python:slim` or `ubuntu`. The reference image includes R and full Ubuntu dependencies, which unnecessarily increases storage and download time for downstream users who only need Python. *(00:09:51)*

- **Q:** You edit your `Dockerfile` to set `WORKDIR /workspace`, but when you run `docker run --rm -it your-image bash`, your prompt still lands in `/root`. What step did you misconfigure?
    - **A:** Ensure `WORKDIR /workspace` appears as a standalone instruction in the `Dockerfile` before any `RUN`, `COPY`, or `CMD` lines that depend on it. Docker applies `WORKDIR` only to subsequent layers, so if it is placed after the default entry point or missing, the container defaults to the root directory. *(00:16:13)*

- **Q:** You need to install a system-level dependency like `git` inside your container image. Which `Dockerfile` directive do you use, and what underlying command matches Ubuntu's package manager?
    - **A:** Use the `RUN` directive combined with `apt-get update && apt-get install --yes git`. `RUN` executes shell commands during the image build phase, and `apt-get` is the stable, script-compatible package manager for Ubuntu-based images that Docker uses. *(00:11:02)*

## 2. Volume mounting and container isolation

*00:18:00–00:27:21*

- **Q:** You run `docker run --rm -it your-image bash`, make changes inside, exit, and then run `docker run` again. Your changes are gone. You want to keep your analysis files synchronized with your local machine without rebuilding the image. Which flag do you add to your `docker run` command, and how does it work?
    - **A:** Add the `-v` flag with a mount path like `-v "$(pwd):/workspace"`. This links your local directory to a directory inside the container, creating a two-way sync that persists changes on your host machine and avoids rebuilding the image for every code update. *(00:38:52)*

- **Q:** You accidentally run `rm -rf /` inside a running container. What happens to your host computer's files, and what is the recommended way to recover the container's state?
    - **A:** Your host computer's files remain untouched because the container runs in an isolated environment. To recover, stop and restart the container, which resets the container's filesystem to the clean state defined in the image, effectively wiping the accidental deletion without affecting your host. *(00:51:25)*

- **Q:** You want to mount your local SSH key into a container for authentication, but you want to prevent the key from being permanently baked into the image or exposed if someone pulls your repo. How do you configure the volume mount to achieve this?
    - **A:** Use a read-only volume mount like `-v ~/.ssh/id_ed25519.pub:/root/.ssh/authorized_keys:ro`. The `:ro` flag ensures the key is only accessible while the container runs, keeps credentials out of the image layers, and limits exposure to read-only access inside the container. *(00:50:13)*

## 3. Docker Compose ([33 Containers: Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*00:27:24–00:44:45*

- **Q:** You have a long `docker run` command with multiple flags for ports, volumes, and environment variables. You want to make this reproducible and version-controlled. What file do you create, and which key-value pairs map directly to your `docker run` flags?
    - **A:** Create a `docker-compose.yml` file. Map flags to YAML keys: `ports:` for `-p`, `volumes:` for `-v`, `environment:` for `-e`, and `build: .` or `image:` for the image source. This consolidates all parameters into a single, readable, version-controlled configuration file. *(00:46:18)*

- **Q:** You run `docker compose up --detach` to start your container. You want to verify it started correctly and see its port mappings. Which command do you run next, and what should you look for in the output?
    - **A:** Run `docker compose ps`. Look for the container status (Up), the port mapping (e.g., `0.0.0.0:2222->22/tcp`), and the container name. This confirms the container is running in the background and the port forwarding is active. *(00:54:40)*

- **Q:** After debugging, you want to completely shut down and remove the container and its associated Docker network created by Compose. Which command do you execute?
    - **A:** Run `docker compose down`. This stops all containers defined in the Compose file, removes them, and deletes the network that Compose automatically created, freeing up system resources like RAM that run containers consume. *(00:57:33)*

## 4. Remote IDEs and non-interactive runs

*00:44:45–01:01:13*

- **Q:** You want to verify your Quarto report builds correctly in the exact container environment before submitting. You don't want to open a shell; you just want to run the build command non-interactively and remove the container afterward. Which command do you use?
    - **A:** Use `docker compose run --rm analysis-env uv run quarto render your_report.qmd`. The `run` command starts a temporary container using the Compose configuration, executes the command, and `--rm` deletes it immediately after completion, ensuring a clean, reproducible test. *(00:58:56)*

- **Q:** You connect Positron to your container via Remote SSH, but the terminal prompt shows `bash: python: command not found`. You know Python is installed in the container. Why does this happen, and how do you run it?
    - **A:** The container manages Python through `uv`, so the standard `python` command isn't in the `$PATH` or doesn't match the `uv`-managed environment. Run `uv run python` instead, which uses the virtual environment path configured by `UV_PROJECT_ENVIRONMENT` inside the container. *(01:00:18)*

- **Q:** You are editing files directly inside the container using a Remote SSH connection to your IDE. You save a file in the IDE, but your local Git workflow doesn't see the change immediately, or you get a conflict warning when trying to save. What is happening, and how should you handle it?
    - **A:** The mounted volume syncs changes immediately, but your IDE might not refresh its file state automatically. Use the IDE's "Revert File" or refresh command to update the local view before saving to avoid overwriting changes made concurrently, similar to working on a network share drive. *(00:43:34)*

    - **A:** Chain `.col_vals_in_set(columns="species", set=["Adelie", "Chinstrap", "Gentoo"])` to your `pb.Validate()` object. By keeping value checks separate from missingness checks and using `na_pass=True` on range-based steps, you ensure that only actual value mismatches trigger warnings rather than missing data. *(01:15:11)*

- **Q:** After running `interrogate()` on your validation object, you want to pass only the rows that meet all criteria to your modeling pipeline, while sending the problematic rows to a teammate for cleaning. Which method do you call on the validation object to split the data?
    - **A:** Call `.get_sundered_data(type="pass")` to get the rows that passed every check, and `.get_sundered_data(type="fail")` to get the rows that failed. This splits the dataframe into two subsets, allowing parallel workflows where downstream teams only process clean data while missing rows are handled separately. *(01:19:52)*

- **Q:** You set `thresholds=(0.01, 0.05, 0.10)` when creating the `pb.Validate()` object. If your validation report shows a yellow warning flag on a step, what does that indicate about the data?
    - **A:** It indicates that at least 1% of the rows in that column failed the check, but less than 5%. The thresholds map the percentage of failures to warning, error, and critical levels, providing a quick visual alert for the severity of data quality issues. *(01:14:50)*
