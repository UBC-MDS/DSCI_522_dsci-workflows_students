Building the milestone image, Docker Compose, and data validation: review questions, tier 5 — Evaluate

Generated by qwen3.8-27b-sglang, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Tier 5 of 5: Evaluate. Decide and justify your verdict before you read the answer; the criteria are the ones given in class.

1. Creating the repository, cloning, and owning your code

00:04:52–00:08:59

  • Q: A teammate commits the reference template as-is into the milestone repository because it already runs. Critique that plan against the class’s standard for working from the template.
    • A: Do not approve it. Daniel warned the class not to blindly copy the template because students must be responsible for and understand the work they submit. He also said any commit with your name on it is fair game to ask about, so even template-derived commits must be explainable. (00:08:15)
  • Q: A pull request clones the milestone repository inside the reference repository’s folder. Would you approve it?
    • A: No. Daniel recalled the DSCI 521 rule against nesting Git repositories and said a dedicated Git folder is a safe place to clone because it avoids that trap. The proposed layout violates the class standard. (00:06:22)

2. Reading the Dockerfile: base image and RUN/apt-get (29 Customizing and building containers)

00:08:59–00:13:18

  • Q: A Python milestone project keeps rocker/r-ver:4.6.2 in its Dockerfile because it already works. Judge whether that base image is suitable for a project that does not need R.
    • A: Not suitable unless R is actually required. Daniel said the R base is Ubuntu with R pre-installed, and although it works for Python work, it takes more storage and makes the download longer for people using or grading the container. The class criterion is to choose the smallest bare minimum image that does the needed work. (00:09:51)
  • Q: Assess a pull request that deletes the Quarto installation lines from the milestone Dockerfile because the in-class demo was Python-only.
    • A: Reject it for the milestone project. Daniel said the container needs Quarto because the milestone container must be able to run the report. The deletion was only acceptable for today’s reduced demo, not for a project that must render Quarto. (00:12:57)

3. Installing uv in the image and keeping the environment portable (29.1 Building container images from Dockerfile’s)

00:13:18–00:19:28

  • Q: A teammate proposes omitting the uv installation step from the Dockerfile and instead asking each teammate to install uv locally. Decide whether that meets the class standard.
    • A: No. Daniel said the point of Docker is complete control over all pieces of software being installed. pyproject.toml does not track the version of uv itself, so the image must control that tool. (00:14:46)
  • Q: Judge a plan to mount the host’s .venv into the container and reuse it for Python packages.
    • A: Do not approve it. Daniel said the host .venv is specific to the operating system and CPU that created it, while the container is a different Linux environment. The course solution is UV_PROJECT_ENVIRONMENT=/opt/venv, so packages are installed for the container and the host .venv is ignored. (00:17:19)
  • Q: A teammate proposes using a requirements.txt for the milestone project because an external university guide uses it. Recommend whether that is acceptable.
    • A: No, not for this course. Daniel said MDS manages Python through uv, and requirements.txt is not how uv generally works. He also warned that external instructions may not be uv-compatible and should not be blindly copied. (00:13:22)

4. Environment variables, uv sync --locked, and the project files (29.2 Dockerfile command summary)

00:27:21–00:34:25

  • Q: A pull request changes RUN uv sync --locked to RUN uv sync to make the build more permissive. Would you approve it?
    • A: No. Daniel called --locked a guard that fails if pyproject.toml and uv.lock are not in sync. Removing it deletes the class-standard check that the image installs the locked dependencies. (00:29:15)
  • Q: Assess a Dockerfile that sets only ENV UV_PROJECT_ENVIRONMENT=/opt/venv and claims SSH logins will see that variable.
    • A: It is not acceptable. Daniel said SSH does not read the process environment variable, so the value must also be written to /etc/environment. The echo ... >> /etc/environment line is needed for logins. (00:28:46)

5. Running the container: docker run flags and a different prompt (29.4 Dockerfile FAQ)

00:35:47–00:38:22

  • Q: A teammate says entering python at the container prompt after running docker run --rm -it docker-uv-renv bash should open the project’s Python. Judge that claim.
    • A: Not acceptable for this image. Daniel said plain python is not on the container’s PATH because the project’s Python is run through uv. The working command is uv run python, which uses the packages installed in the uv environment. (00:37:52)

6. Mounting the project folder with -v (33 Containers: Docker Compose)

00:38:22–00:44:42

  • Q: A teammate proposes copying the project files into the image instead of using the -v "$(pwd):/workspace" mount during active analysis. Critique that plan.
    • A: It is the wrong approach for active work. Daniel said copying files into the image freezes them at build time, so constantly changing analysis files would require rebuilding the container. The class rule is to bake in software and mount the files that keep changing. (00:39:55)
  • Q: Judge whether a Dockerfile should contain the team’s GitHub personal access token or SSH key so the container can push commits.
    • A: No. Daniel said the container is like a brand-new machine that resets, and you do not want Git credentials baked into the image because anyone who pulls it could read them. The secure workflow is to leave Git on the host through the mounted volume. (00:41:50)
  • Q: Would you recommend a teammate editing validation.py on the host and in the container at the same time?
    • A: No. Daniel warned that the two sides do not merge, so whoever saves last silently overwrites the other side’s changes. If the file is open on one side, use the editor’s revert-file refresh before editing. (00:43:21)

7. docker-compose.yml: putting the launch in a file (33 Containers: Docker Compose)

00:44:42–00:55:31

  • Q: A milestone README documents only a very long docker run command with all flags, and no docker-compose.yml. Assess whether that meets the class’s documentation standard.
    • A: It does not meet the standard I would approve. Daniel said long pasted commands are hard to track, edit, and document, while a compose file keeps the parameters in a version-controlled file. He called compose the easier way to specify the launch. (00:45:51)
  • Q: A pull request changes ports: from "2222:22" to "22:22" because it looks cleaner. Would you approve it?
    • A: I would reject it unless the host is known not to use port 22. Daniel said port 22 is a very common port used for real things, so you do not want to overwrite it by accident. The first number is the host port you connect to, so using 2222 avoids the collision. (00:49:03)

8. exec, down, and shutting containers down (33.2 Docker Compose commands)

00:55:31–00:58:24

  • Q: Assess a teammate’s habit of leaving many milestone containers running because they may need them again soon.
    • A: I would critique it. Daniel said containers are other computers that use RAM, and running too many at once can make the machine’s memory disappear into them. The class standard is to be diligent about turning things off, for example with docker compose down. (00:57:38)

9. One-off commands: docker compose run (33.3 Running a Docker container non-interactively using the Docker Compose)

00:58:24–01:01:13

  • Q: Critique a reproducibility plan that renders the Quarto report only on the laptop and never in the container.
    • A: It misses the class goal. Daniel said the container is the machine you made, and you test that machine by sending it commands, such as uv run quarto render. Rendering only locally does not verify that the report builds in the container’s exact environment. (01:01:05)

10. Connecting Positron or VS Code to the container with Remote SSH

01:01:41–01:06:55

  • Q: Assess a plan to run the same analysis in Positron on the host and inside the container at the same time on a resource-constrained laptop.
    • A: I would reject it. Daniel said if you are resource constrained, you probably should not run Docker at the same time because you want to save RAM. The better habit is to work locally and run the final check in the container rather than keeping both environments active. (01:06:42)

11. Why validate, and where the missing values are (41 Data validation: Python (pointblank))

01:11:40–01:13:45

  • Q: A data set codes missing BMI values as 99. A teammate’s pointblank check treats 99 as an out-of-range BMI value. Judge that check.
    • A: It is not a good check. Daniel said health surveys often code missing as 99 instead of a real missing value, so the codebook must guide the check. Treating 99 as a range failure confuses a coded missing value with a bad measurement. (01:12:15)

12. Chaining value checks with pb.Validate (41.2 Checking values)

01:13:45–01:18:29

  • Q: A teammate removes na_pass=True from col_vals_between(columns="bill_length_mm", left=30, right=60) so missing values fail the range check. Critique that change.
    • A: I would reject it for the value-check step. Daniel said missingness can be checked in its own checks, and na_pass=True lets missing values pass so the range check judges only values that are present. Mixing missingness into the range check hides which problem is occurring. (01:16:40)
  • Q: Judge a conclusion that the Palmer penguins data are invalid because the demo’s col_vals_in_set(columns="species", set=["Adelie", "Chinstrap"]) step reports failures.
    • A: The data are not necessarily invalid; the assumption is too narrow. Daniel said a check tests an assumption you have made, and the demo omitted “Gentoo” so the report would flag those values. The correct response is to correct the allowed-value set, not assume the data are wrong. (01:15:11)

13. Splitting passing and failing rows (41.4 Splitting the passing and failing rows)

01:18:29–01:20:48

  • Q: A teammate argues that downstream modelers should wait until the data set is 100% clean before receiving any rows. Would you defend that waiting rule?
    • A: No, I would not defend it. Daniel said you do not want to wait for data to be 100% clean because that will not happen and will block downstream work. get_sundered_data(type="pass") gives the working rows to downstream while the cleaning teammate fixes the failed rows. (01:19:20)
