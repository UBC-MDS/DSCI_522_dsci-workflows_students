2. Reading the milestone Dockerfile base and system packages (29.1 Building container images from Dockerfile’s)

00:08:59–00:13:18

  • Q: Break down the demo Dockerfile’s FROM rocker/r-ver:4.6.2 and RUN apt-get ... lines: what does the base image decide, what does the RUN line install, and why does that matter for a Python project?
    • A: The FROM line decides the starting operating system and preinstalled software, so rocker/r-ver brings Ubuntu and R and sets a larger size floor even for a Python project. The RUN apt-get line installs Linux system packages inside that image, such as git, make, nano, and openssh-server, because Docker images use Linux package commands rather than the laptop’s tools. This matters for Python because some Python packages need system-level pieces, like compilers or OS software, before their Python packages can work. (00:11:02)

3. Making the uv environment portable and working in /workspace (29.1 Building container images from Dockerfile’s)

00:13:18–00:19:28

  • Q: Separate the host machine’s .venv from the container’s /opt/venv in the demo Dockerfile: what each is tied to, why the mounted project folder can create a mismatch, and what tells uv to use the container’s location.
    • A: The host .venv is created by uv sync on a student’s laptop and is tied to that machine’s operating system and CPU architecture. The container is another Linux environment, so a mounted host .venv would not necessarily match the packages and binary format the container needs. The Dockerfile sets UV_PROJECT_ENVIRONMENT=/opt/venv, so uv installs the project’s packages into a Linux path instead of the machine-specific .venv. When the project folder is mounted later, the host .venv is simply ignored and the container uses the packages installed for its own environment. (00:18:38)
  • Q: Point out how WORKDIR /workspace fits between installing uv and mounting the project folder: what it changes about where commands run, how it behaves if the folder does not exist, and why that matters for a careless rm *.
    • A: WORKDIR /workspace makes later container commands start in the project folder rather than the root of the container’s filesystem. Docker creates the /workspace folder if it does not already exist, so it acts like mkdir plus cd for subsequent steps. That separation matters because working at the root mixes project files with operating-system folders, where a careless command like rm * could delete things the user did not mean to delete. It is why the demo’s prompt later lands in /workspace when the container is entered. (00:16:32)

4. UV_PROJECT_ENVIRONMENT, uv sync --locked, and copied project files (29.2 Dockerfile command summary)

00:27:21–00:34:25

  • Q: Examine the Dockerfile lines that set UV_PROJECT_ENVIRONMENT, copy pyproject.toml uv.lock .python-version, and run uv sync --locked: what problem each line solves for the final container.
    • A: The ENV line tells uv where to place the project virtual environment, but the SSH login does not read process environment variables, so the RUN echo ... >> /etc/environment line writes the same variable into a file that logins can see. The COPY line brings the project’s dependency description, lock file, and Python version pin into the image so the container can reproduce the same project setup. uv sync --locked then installs from uv.lock and fails if uv.lock and pyproject.toml disagree, acting as a guard that the locked package set matches the requested packages. .python-version contributes by telling uv which Python version to use for the project. (00:29:15)

5. Tracing the docker build log back to the Dockerfile (29.4 Dockerfile FAQ)

00:34:25–00:35:47

  • Q: Point out which build-log steps from docker build --tag docker-uv-renv . correspond to the base image, system packages, uv installation, working directory, environment line, copied project files, and locked sync.
    • A: The log starts by loading metadata for rocker/r-ver:4.6.2, which corresponds to the FROM base image. The cached RUN apt-get update && apt-get install --yes step corresponds to the system-package installation line. The COPY --from=ghcr.io/astral-sh/uv:0.13.7 step brings the uv and uvx binaries into the image from the prebuilt uv image. The later WORKDIR, RUN echo ... >> /etc/environment, COPY pyproject.toml uv.lock .python-version ./, and RUN uv sync --locked steps set the working folder, persist the uv environment variable for logins, bring in the project files, and install packages from the lock file. (00:35:21)

6. Running the image and reading the container prompt (29 Customizing and building containers)

00:35:47–00:38:22

  • Q: Break down docker run --rm -it docker-uv-renv bash: what --rm does, what -it combines, why bash matters, and how the prompt and pwd show the user is inside another computer.
    • A: --rm tells Docker to remove the container when the user exits, so the interactive test does not leave a stopped container behind. -it chains two single-letter flags: -i keeps the session interactive and -t allocates a tty, which is what makes a usable terminal prompt. bash after the image name starts a shell in the container instead of the image’s default command. The prompt changes to root@... and pwd reports /workspace, which means the user is operating as root in the container’s filesystem, not on their laptop. (00:37:15)

7. Mounting the project folder with -v (33 Containers: Docker Compose)

00:38:22–00:44:42

  • Q: Differentiate COPY-ing files into the image from docker run --rm -v "$(pwd):/workspace" -it docker-uv-renv bash: what each does to files, what the touch hello.py test proves, and where Git or credentials fit into the safer approach.
    • A: COPY in the Dockerfile freezes files into the image at build time, so changing a project file later would require rebuilding the image just to move that change into the container. The -v "$(pwd):/workspace" mount connects the current host folder to /workspace, so touch hello.py inside the container makes hello.py appear on the host immediately. This keeps day-to-day file changes out of the image while still letting the container use the project files. For Git, the host can keep the normal git add, git commit, and git push workflow because the container is a fresh machine that would otherwise need its own credentials; mounting also avoids baking an SSH key or token into the image. The class warned that editing the same mounted file on both sides at once can overwrite one side’s changes, so a “revert file” refresh is needed before editing. (00:41:50)

8. docker-compose.yml fields as a stored docker run setup (33 Containers: Docker Compose)

00:44:42–00:55:31

  • Q: Relate the analysis-env service in docker-compose.yml to the commands it replaces: what build and image do, what ports maps, what volumes mounts, and why putting those parts in a file helps.
    • A: The services key declares the container the project will run, named analysis-env in the demo. build: . tells Docker Compose to build from the Dockerfile in the current folder, and image: docker-uv-renv names the resulting image, matching the earlier docker build --tag docker-uv-renv .. The ports entry "2222:22" maps port 2222 on the host to port 22 in the container, where the container’s SSH server listens. The volumes entry .:/workspace mounts the project folder into the container, and the read-only SSH public key mount gives the container an authorized key without storing the credential in the image. Keeping these flags in docker-compose.yml makes the launch documented, editable, and version-controllable instead of a long pasted docker run command. (00:50:19)

9. docker compose exec, down, and container cleanup (33 Containers: Docker Compose)

00:55:31–00:58:24

  • Q: Distinguish the compose service name from Docker’s longer container name in docker compose exec, and break down what exit and docker compose down do to the running container.
    • A: docker compose exec analysis-env bash uses the service name from docker-compose.yml, while the long name shown by docker ps -a is Docker’s container name for that running instance. Trying to exec the long container name as a service can fail because Compose is looking for a service defined in the file, not the auto-generated container name. exit from the bash session leaves the shell but does not stop the container; the container keeps running in the background. docker compose down then reads the Compose file and stops and removes the container and its network, which matters because running containers consume RAM like other machines. (00:57:38)

10. One-off commands with docker compose run (33 Containers: Docker Compose)

00:58:24–01:01:13

  • Q: Examine the difference between docker compose run --rm analysis-env python and docker compose run --rm analysis-env uv run python: what run and --rm do, why the first command fails, and what the working command shows about the image’s Python.
    • A: docker compose run starts a new temporary container for the analysis-env service and runs the command given after the service name, while --rm deletes that temporary container when the command finishes. The first command fails with exec: "python": executable file not found in $PATH because the demo image does not put a plain python executable on PATH. The working command runs uv run python, which starts Python from the uv-managed environment where the project’s packages were installed. This shows that the container’s reproducibility comes from the uv environment, not from a system-wide Python that would ignore the installed packages. (00:59:10)

11. Connecting an IDE to the running container with Remote SSH (33 Containers: Docker Compose)

01:01:41–01:06:55

  • Q: Break down the Remote SSH setup used with Positron: what must be running on the container, which host address and port are used, what username is required, and how the mounted /workspace folder changes where commands execute.
    • A: docker compose up --detach must have started the analysis-env container so its SSH server is listening in the background. The IDE connects to localhost on port 2222, which is the host side of the Compose 2222:22 port mapping. The user must use root because the container prompt identified root as the username, not the laptop’s default user. After opening the mounted /workspace folder through the connection, the IDE behaves as if it is working inside the container, so commands run there instead of only on the host. (01:03:34)

13. Validation assumptions and missingness (41 Data validation: Python (pointblank))

01:11:40–01:13:45

  • Q: Separate the health-data examples Daniel gave into the kinds of pointblank checks they would motivate: which is an allowed-value or categorical check, which is a range check, and which is a missing-value or codebook check.
    • A: The “pregnant men” example motivates an allowed-value or categorical consistency check, because the relevant categories should not contain an impossible combination. The BMI upper-bound example motivates a range check, similar to the col_vals_between style used on bill_length_mm. The survey coding of missing values as 99 motivates a codebook and missing-value check, because 99 must be recognized as not a real measurement before the value checks are meaningful. These examples show that validation is not one block but several assumptions checked where the data enters the modelling workflow. (00:12:15)
  • Q: Separate the two things pb.missing_vals_tbl(data=penguins) gives the class from the later value-check workflow: what the table/visual report shows, where the penguin missingness appeared to be concentrated, and why that matters before deciding checks.
    • A: pb.missing_vals_tbl reports where missing values occur in the data, organized into row sections so the reader can see which parts of the dataset have missing entries. The penguin demo showed a lot of missingness near the beginning of the data, which the instructor tied to the order of collection rather than a proven data error. The visual missingness view complements the table by showing holes in the data at a glance, making it easier to spot unusual patterns before writing formal checks. This matters because the class wants to check data assumptions in code before modelling, and knowing where missingness is concentrated helps decide which checks and thresholds are relevant. (01:13:18)

14. Chaining pointblank value checks (41 Data validation: Python (pointblank))

01:13:45–01:18:29

  • Q: Break down the pb.Validate workflow used on penguins: what the thresholds mean, what each chained step checks, why na_pass=True matters, and what interrogate() does.
    • A: pb.Validate(data=penguins, label="Penguin measurements", thresholds=(0.01, 0.05, 0.10)) creates the validation object and sets failure levels where 1%, 5%, and 10% of a step’s rows become warning, error, and critical. col_vals_in_set(columns="species", set=["Adelie", "Chinstrap"]) checks that the species values are within a chosen set, and the demo intentionally left out Gentoo so the report could flag the extra values. col_vals_between(columns="bill_length_mm", left=30, right=60, na_pass=True) checks a sensible numeric range while allowing missing values to pass that step, and rows_distinct() checks that rows are not duplicates. interrogate() actually runs the chained checks and produces the pass/fail report that shows which steps reached each threshold. (01:17:12)

15. Splitting passing and failing rows (41 Data validation: Python (pointblank))

01:18:29–01:20:48

  • Q: Relate get_sundered_data(type="pass") and get_sundered_data(type="fail") to the group project workflow: what each data frame contains, what the class said to do with each, and why that helps a team that is still cleaning data.
    • A: get_sundered_data(type="pass") returns the rows that passed the validation steps, giving downstream team members a working data frame they can use to continue building the pipeline. get_sundered_data(type="fail") returns the rows that failed at least one step, giving the cleaning person a concrete set of records to inspect and fix. The class framed this as separating work so the project does not wait for the data to become perfectly clean before modelling or reporting can begin. Because the results are ordinary data frames, the failed rows can be saved to a CSV file and handed to a teammate as a standalone to-fix dataset. (01:20:32)
