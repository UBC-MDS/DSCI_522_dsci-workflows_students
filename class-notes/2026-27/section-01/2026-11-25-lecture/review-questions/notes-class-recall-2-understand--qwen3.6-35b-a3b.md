- **Q:** What is the difference between landing in the root directory of a container and using the `WORKDIR` command?
    - **A:** Without `WORKDIR`, a container starts in the root operating system directory, where a careless command like `rm *` could delete essential system files. Setting `WORKDIR /workspace` ensures you start directly in your project folder, keeping the OS files safe and keeping your focus on the files you actually care about. *(00:15:57)*

    - **A:** When you run `uv sync` locally, it creates a `.venv` folder that matches your host computer's operating system. Because the container runs a different OS (Linux), that local virtual environment folder would not match or work inside the container. This environment variable forces `uv` to install packages into a container-native path (`/opt/venv`), guaranteeing compatibility regardless of whether you run on Mac, Windows, or Linux. *(00:17:01)*

## 2. Volume mounting and container isolation ([33.1 Docker Compose to launch containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html#docker-compose-to-launch-containers))

*00:18:00–00:27:21*

- **Q:** Why is volume mounting with `docker run -v` preferred over using the `COPY` command for actively developing analysis files?
    - **A:** The `COPY` command only transfers files at build time, meaning you would have to rebuild the entire container every time you change a file during active work. Volume mounting creates a live, two-way sync between your local machine and the container, saving you from constant rebuilds and letting you use standard local Git commands without configuring credentials inside the ephemeral container. *(00:39:55)*

- **Q:** What is the security advantage of mounting an SSH key with the `:ro` (read-only) flag in a compose file?
    - **A:** Mounting the key as read-only ensures your credentials are only present while the container is actively running and are never baked into the Docker image itself. This prevents anyone who pulls your container from your repository from accessing your SSH keys or messing with your account. *(00:41:38)*

- **Q:** How does a container act as a sandbox, and why is that useful for testing new software installations?
    - **A:** Containers are completely ephemeral and isolated from your host machine. If you accidentally delete system files or install incompatible software inside the container, you can simply stop and restart it to instantly reset to a clean, built state. This makes it a safe playground to experiment with heavy dependencies like PyTorch without risking your actual computer. *(00:51:02)*

## 3. Docker Compose ([33 Containers: Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*00:27:24–00:44:45*

- **Q:** Why is a `docker-compose.yml` file considered better than typing out a massive `docker run` command in the terminal?
    - **A:** Long terminal commands are difficult to edit with a mouse, easy to break when copy-pasting due to spacing issues, and hard to track across sessions. A compose file keeps all flags and parameters in a readable, version-controlled document that automatically generates the correct command, making it easier to modify and share. *(00:44:45)*

- **Q:** What does the port mapping format `"2222:22"` in a compose file actually mean?
    - **A:** The first number (2222) is the port on your local computer, and the second number (22) is the port the service listens on inside the container. You intentionally map it to a different local port like 2222 to avoid conflicting with services that already use the standard port 22 on your machine. *(00:47:55)*

- **Q:** What does the `--detach` flag do in `docker compose up`, and why is it useful for development?
    - **A:** The `--detach` flag starts the container in the background, immediately returning your terminal prompt to you instead of hijacking the window with the container's output. This lets you continue running other compose commands or use your terminal normally while the container runs silently. *(00:54:00)*

- **Q:** Why should you be diligent about running `docker compose down` when you finish working?
    - **A:** Each running container acts like a separate machine and continuously consumes RAM. If you leave multiple containers running in the background, your computer's available memory will steadily decrease. Explicitly bringing them down frees up those system resources. *(00:57:30)*

## 4. Remote IDEs and non-interactive runs ([33.3 Running a Docker container non-interactively...](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html#running-a-docker-container-non-interactively-using-the-docker-compose))

*00:44:45–01:01:13*

- **Q:** Why must you run `uv run python` inside the container instead of just typing `python`?
    - **A:** The container manages all Python packages through `uv`, which controls the environment path. Running `python` directly fails because the standard interpreter isn't in the system `$PATH` and doesn't have access to the packages `uv` installed. You must use `uv run` to activate the correct environment inside the container. *(00:58:49)*

- **Q:** What is the functional difference between mounting a volume to edit files locally versus connecting to a container via Remote SSH in an IDE?
    - **A:** Mounting a volume lets you edit files on your host machine and run commands locally, testing them in the container separately. Connecting via Remote SSH treats the IDE as if it is inside the container, meaning every command you type and every file you open executes natively within the isolated environment, ensuring exact match between your code and dependencies. *(01:02:05)*

- **Q:** How does `docker compose run --rm` help verify that your analysis is truly reproducible?
    - **A:** It spins up a fresh container, runs your exact command (like rendering a Quarto report), and automatically deletes the container when finished. This proves your analysis builds correctly in the isolated environment without leaving temporary containers cluttering your system or hiding environment mismatches. *(00:58:24)*

    - **A:** It defines percentage cutoffs (like 1%, 5%, and 10%) that determine when a validation step triggers a warning, error, or critical failure. - **Q:** How does `get_sundered_data()` facilitate collaboration when cleaning large datasets?
    - **A:** It automatically splits the original dataset into two separate dataframes: one containing rows that passed every check, and another containing rows that failed at least one. You can immediately pass the clean data to a teammate for modeling while sending the failed rows back for data cleaning, keeping the pipeline moving without waiting for 100% perfect data. *(01:19:36)*

- **Q:** Why should you break validation into separate checks for missingness, value ranges, and duplicates instead of running everything in one block?
    - **A:** Missing values, invalid ranges, and duplicate rows represent fundamentally different data quality problems that usually require different handling strategies. Checking them separately keeps the validation output readable, makes debugging easier, and allows you to modularize your code so different team members can work on different parts of the cleaning pipeline at the same time. *(01:17:47)*
