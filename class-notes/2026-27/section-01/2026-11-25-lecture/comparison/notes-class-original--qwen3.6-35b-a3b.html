Docker Compose, Container Workflows, and Data Validation

Date: 2026-11-25

Generated by qwen3.6-35b-a3b, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Summary

This session reviewed the end-to-end workflow of building a reproducible data science container using Dockerfile, uv, and Docker, then transitioned to managing complex container lifecycles with docker-compose.yml. The instructor emphasized that while docker run is useful for quick testing, it quickly becomes unwieldy as flags accumulate. Docker Compose centralizes image building, volume mounting, port mapping, and environment configuration into a single version-controlled YAML file, making workflows more maintainable and reproducible across different operating systems and hardware architectures.

A major focus was placed on volume mounting (-v) and SSH key management. Mounting the local working directory into the container enables live file synchronization, prevents the need to rebuild the image for every code change, and securely passes authentication credentials without baking them into the image. The instructor warned about the practical pitfalls of live syncing, such as editor lock conflicts, and demonstrated how to safely test code inside the container without committing to persistent changes.

The lecture concluded with an introduction to data validation using the pointblank package. Rather than waiting for a perfectly clean dataset, validation checks are integrated into the workflow to catch missing values, invalid ranges, and duplicate rows early. The session demonstrated how to chain validation rules, set failure thresholds, and split datasets into passing and failing subsets so that downstream modeling work can proceed while data cleaning continues in parallel.

Knowledge Points

1. Dockerfile Structure & Environment Control

  • Base images: Containers should start from a minimal base image appropriate for the project. Using a heavy image like rocker/r-ver for a Python-only project wastes storage and increases download times for anyone downstream, including graders.
  • WORKDIR vs cd: WORKDIR in a Dockerfile acts as both mkdir and cd. It ensures the container opens directly into the project directory instead of the root filesystem, preventing accidental system-level commands like rm *.
  • UV_PROJECT_ENVIRONMENT override: By default, uv sync creates a .venv folder. This folder is tied to the host OS and CPU architecture. When mounting a volume into a Linux container, the host’s .venv becomes invalid inside the container. Setting ENV UV_PROJECT_ENVIRONMENT=/opt/venv forces uv to install packages into a container-native path, keeping the virtual environment OS-agnostic and mount-safe.

2. Volume Mounting & Port Mapping

  • -v flag: Mounts a local directory into the container. Benefits include immediate file sync, avoiding constant image rebuilds, and keeping Git credentials and SSH keys on the host machine rather than inside the container.
  • Security warning: Never bake SSH keys or personal access tokens into a container image. Anyone who pulls the image would inherit your credentials. Mounting them read-only (:ro) or keeping them on the host prevents accidental exposure.
  • Port mapping: Containers listen on internal ports (e.g., SSH on port 22). To access them from the host, map a host port to the container port (e.g., 2222:22). Using a high, unused host port prevents conflicts with host services. This pattern applies to Jupyter Lab (8888), RStudio (8787), and other services.
  • Sandbox testing: Because mounted volumes sync bidirectionally, the container acts as a sandbox. You can safely test risky installations or configurations inside the container, then run docker compose down to reset without affecting your host machine.

3. Docker Compose Workflows

  • docker-compose.yml: Replaces long, error-prone docker run commands. It defines services, build contexts, ports, volumes, and environment variables in a readable, version-controlled format.
  • Detached mode: docker compose up --detach starts containers in the background, returning the terminal immediately. This is ideal for keeping development environments running while you work elsewhere.
  • Interactive vs non-interactive execution:
    • docker compose exec <service> bash attaches to a running container for interactive work.
    • docker compose run --rm <service> <command> creates a temporary container, runs a single command (like rendering a report or running tests), and automatically removes the container when finished. This is ideal for CI/CD-style validation.

4. Data Validation with pointblank

  • Validation agent: pb.Validate() creates a testing object that chains rules like .col_vals_in_set(), .col_vals_between(), and .rows_distinct().
  • Thresholds: thresholds=(0.01, 0.05, 0.10) define failure tolerance. At 1% failure rate, the step flags a warning; at 5%, an error; at 10%, critical. This replaces binary pass/fail checks with actionable severity levels.
  • Splitting datasets: After .interrogate(), get_sundered_data(type="pass") and type="fail" separate rows. You can pass the clean subset to modeling pipelines while returning the failing rows to a data cleaner, enabling parallel teamwork without blocking downstream analysis.

Building & running the container directly

docker build --tag docker-uv-renv .                   # Build image from local Dockerfile
docker run --rm -it docker-uv-renv bash               # Start container interactively
docker run --rm -v "$(pwd):/workspace" -it docker-uv-renv bash  # Mount current directory to /workspace

Managing containers with Docker Compose

docker compose build                                  # Build image using docker-compose.yml
docker compose up --detach                            # Start containers in background
docker compose exec analysis-env bash                 # Attach to running container via service name
docker compose down                                   # Stop and remove containers & network
docker compose run --rm analysis-env uv run python    # Run one-off command, remove container after

What went wrong live

  • Running bash as an image: Typed docker run --rm -v "$(pwd):/workspace" -it bash, which told Docker to pull and run the bash image instead of the project container. Fixed by specifying the correct image: docker-uv-renv bash.
  • Incorrect service reference in exec: Ran docker compose exec 2026-11-25-docker-validate-analysis-env-1 bash, which failed because Docker Compose expects the service name defined in the YAML, not the auto-generated container ID. Fixed by using the service name: docker compose exec analysis-env bash.
  • Missing python executable: Ran docker compose run --rm analysis-env python, which threw exec: "python": executable file not found in $PATH. Fixed by running uv run python since the environment and packages are managed by uv, not a system Python install.
  • uv add failing on missing [project] table: Ran uv add pandera pointblank, which failed with error: Project is missing a [project] table. Instructor noted this can happen if the workspace configuration isn’t fully initialized, and resolved it by either re-running the command or manually adding the packages to pyproject.toml followed by uv sync.

Questions

  • Q: Can I leave out the --locked flag when running uv sync inside the container? A: Yes, you can, but it acts as a safety guard. --locked ensures the uv.lock file exactly matches the pyproject.toml dependencies. If they drift out of sync, the command fails instead of silently installing mismatched versions, which is preferable for reproducible workflows.

  • Q: How do I connect an IDE like Positron or VS Code directly to the container so I can edit files inside it? A: Run the container in detached mode with SSH port mapping (2222:22). Then use the IDE’s Remote SSH extension to connect to root@localhost on port 2222. The mounted /workspace folder will appear in the IDE, and all commands run inside the container. Note that forks of VS Code (like Positron) may not support official Microsoft extensions, so the connection method may vary slightly.

  • Q: What happens if two people (or two terminal windows) edit the same file at the same time while volumes are mounted? A: It behaves like a network share drive. Whichever process saves the file first wins; the other may be forced to overwrite, ignore, or see a conflict pop-up. The instructor recommended using your IDE’s “revert file” or refresh feature before editing to sync with external changes, avoiding accidental data loss.
