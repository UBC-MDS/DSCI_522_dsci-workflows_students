## Knowledge Points

### 1. Dockerfile Structure & Environment Control

- **Base images**: Containers should start from a minimal base image appropriate for the project. Using a heavy image like `rocker/r-ver` for a Python-only project wastes storage and increases download times for anyone downstream, including graders.
- **`WORKDIR` vs `cd`**: `WORKDIR` in a `Dockerfile` acts as both `mkdir` and `cd`. It ensures the container opens directly into the project directory instead of the root filesystem, preventing accidental system-level commands like `rm *`.
- **`UV_PROJECT_ENVIRONMENT` override**: By default, `uv sync` creates a `.venv` folder. This folder is tied to the host OS and CPU architecture. When mounting a volume into a Linux container, the host's `.venv` becomes invalid inside the container. Setting `ENV UV_PROJECT_ENVIRONMENT=/opt/venv` forces `uv` to install packages into a container-native path, keeping the virtual environment OS-agnostic and mount-safe.

### 2. Volume Mounting & Port Mapping

- **`-v` flag**: Mounts a local directory into the container. Benefits include immediate file sync, avoiding constant image rebuilds, and keeping Git credentials and SSH keys on the host machine rather than inside the container.
- **Security warning**: Never bake SSH keys or personal access tokens into a container image. Anyone who pulls the image would inherit your credentials. Mounting them read-only (`:ro`) or keeping them on the host prevents accidental exposure.
- **Port mapping**: Containers listen on internal ports (e.g., SSH on port `22`). To access them from the host, map a host port to the container port (e.g., `2222:22`). Using a high, unused host port prevents conflicts with host services. This pattern applies to Jupyter Lab (`8888`), RStudio (`8787`), and other services.
- **Sandbox testing**: Because mounted volumes sync bidirectionally, the container acts as a sandbox. You can safely test risky installations or configurations inside the container, then run `docker compose down` to reset without affecting your host machine.

### 3. Docker Compose Workflows

- **`docker-compose.yml`**: Replaces long, error-prone `docker run` commands. It defines services, build contexts, ports, volumes, and environment variables in a readable, version-controlled format.
- **Detached mode**: `docker compose up --detach` starts containers in the background, returning the terminal immediately. This is ideal for keeping development environments running while you work elsewhere.
- **Interactive vs non-interactive execution**: 
  - `docker compose exec <service> bash` attaches to a running container for interactive work.
  - `docker compose run --rm <service> <command>` creates a temporary container, runs a single command (like rendering a report or running tests), and automatically removes the container when finished. This is ideal for CI/CD-style validation.

### 4. Data Validation with `pointblank`

- **Validation agent**: `pb.Validate()` creates a testing object that chains rules like `.col_vals_in_set()`, `.col_vals_between()`, and `.rows_distinct()`.
- **Thresholds**: `thresholds=(0.01, 0.05, 0.10)` define failure tolerance. At 1% failure rate, the step flags a warning; at 5%, an error; at 10%, critical. This replaces binary pass/fail checks with actionable severity levels.
- **Splitting datasets**: After `.interrogate()`, `get_sundered_data(type="pass")` and `type="fail"` separate rows. You can pass the clean subset to modeling pipelines while returning the failing rows to a data cleaner, enabling parallel teamwork without blocking downstream analysis.

## Questions

- **Q:** Can I leave out the `--locked` flag when running `uv sync` inside the container?
  **A:** Yes, you can, but it acts as a safety guard. `--locked` ensures the `uv.lock` file exactly matches the `pyproject.toml` dependencies. If they drift out of sync, the command fails instead of silently installing mismatched versions, which is preferable for reproducible workflows.

- **Q:** How do I connect an IDE like Positron or VS Code directly to the container so I can edit files inside it?
  **A:** Run the container in detached mode with SSH port mapping (`2222:22`). Then use the IDE's Remote SSH extension to connect to `root@localhost` on port `2222`. The mounted `/workspace` folder will appear in the IDE, and all commands run inside the container. Note that forks of VS Code (like Positron) may not support official Microsoft extensions, so the connection method may vary slightly.

- **Q:** What happens if two people (or two terminal windows) edit the same file at the same time while volumes are mounted?
  **A:** It behaves like a network share drive. Whichever process saves the file first wins; the other may be forced to overwrite, ignore, or see a conflict pop-up. The instructor recommended using your IDE's "revert file" or refresh feature before editing to sync with external changes, avoiding accidental data loss.
