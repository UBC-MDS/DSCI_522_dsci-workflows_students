Docker Compose and pointblank data validation

Date: 2026-11-25

Generated by qwen3.8-27b-sglang, a local model, from the class recording, logs and readings. It can be wrong, or say things the class didn’t cover.

Instructor: Daniel Chen

Summary

This 2026-11-25 section 01 lecture reviewed the container workflow from the previous session and then introduced Docker Compose and data validation with pointblank. The class worked in the demo repository 2026-11-25-docker-validate, using files copied from the reference repository docker-uv-renv. The review covered building a Docker image from a Dockerfile, running an interactive container, mounting the project folder into the container at /workspace, and explaining why uv projects in Docker need the virtual environment placed outside the mounted folder so the container installs Linux-compatible packages.

The new material focused on replacing long docker run commands with a docker-compose.yml file. The class examined how build, image, ports, and volumes map to Docker commands, how to start and stop containers with docker compose up --detach and docker compose down, how to run commands inside a running container with docker compose exec, and how to run one-off commands with docker compose run --rm. The instructor also showed how Positron or a VS Code fork can connect to the container over Remote SSH, treating the container like a remote computer.

The final part introduced data validation using pointblank on the Palmer penguins dataset. The class explored missing-value reports, thresholded value checks, row distinctness checks, and how to split the data into passing and failing rows so different team members can work in parallel. The instructor framed this as preview material for the next week’s assignment, where students will add data checks at appropriate points in their analyses.

Knowledge Points

1. Demo repository and class workflow

  • Demo repository: The class worked in https://github.com/chendaniely/2026-11-25-docker-validate.
    • Files used or discussed: Dockerfile, docker-compose.yml, pyproject.toml, uv.lock, .python-version, and validation.py.
  • Reference repository: The class copied files from the textbook’s example project https://github.com/chendaniely/docker-uv-renv. The instructor described it as the technical foundation for the milestones.
  • Class review task:
    • Create a GitHub repository.
    • Copy the relevant files into it.
    • Generate the uv.lock file rather than blindly copying it.
    • Build the container from the Dockerfile.
    • Run the container and get a bash prompt.
  • Warning — do not blindly copy the template: The instructor said the template is useful for typing and avoiding mistakes, but students are responsible for understanding the work. He also said that if there is a commit with a student’s name on it, that commit is fair game for an exam or interview question.

2. Dockerfile review

The session reviewed the Dockerfile in the demo repository. The live demo used a reduced version of the reference Dockerfile, with the Quarto and R-specific parts deleted for time and space.

  • Base image:
    • The demo Dockerfile starts with FROM rocker/r-ver:4.6.2.
    • This is an Ubuntu-based image with R preinstalled.
    • The instructor noted that a Python project does not need R, and that using a larger base image increases download time and storage for downstream users, including graders.
    • The general goal is to use the smallest base image that can do the required work.
    • See 29.3 Choosing a base image for your Dockerfile.
  • Installing system software with RUN:
    • The demo installed system packages with apt-get:
      • curl
      • git
      • less
      • libuv1-dev
      • make
      • nano
      • openssh-server
    • RUN commands are Bash commands executed in the container’s Linux environment.
    • The instructor used PyTorch, geospatial packages, and Quarto as examples of cases where system software or compilers may be needed.
    • The reference repository also includes Quarto installation for milestone reports, but the live demo removed that section.
  • Installing uv:
    • The Dockerfile copies uv and uvx from a prebuilt image:
      • COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/
    • This is one way to control the version of uv itself.
    • pyproject.toml controls Python package versions, but it does not track the version of uv.
    • Docker is useful because it controls the surrounding tools and system dependencies, not just the Python packages.
  • WORKDIR /workspace:
    • Sets the default working directory when the container starts or when commands run.
    • Docker creates the folder if it does not already exist.
    • It is effectively a mkdir plus cd.
    • The instructor explained that this keeps work in /workspace rather than at the root of the container, which reduces the risk of accidentally deleting important operating-system files.
  • UV_PROJECT_ENVIRONMENT=/opt/venv:
    • The Dockerfile sets the environment variable UV_PROJECT_ENVIRONMENT to /opt/venv.
    • It also appends that variable to /etc/environment because SSH logins may not see normal ENV variables.
    • This tells uv to create the virtual environment in /opt/venv instead of .venv inside the mounted project folder.
    • The local .venv folder is specific to the host operating system and CPU architecture.
    • The container is Linux, so packages must be installed for the container’s environment.
    • When the host project folder is mounted into the container, the host’s .venv is ignored by uv inside the container.
  • Copying project files:
    • The demo copied pyproject.toml, uv.lock, and .python-version into the container.
    • Then it ran uv sync --locked.
  • uv sync --locked:
    • --locked is a guardrail.
    • It fails if uv.lock and pyproject.toml are out of sync.
    • It makes the build check that the locked dependencies match the project definition.
  • SSH setup:
    • The demo installs openssh-server.
    • The Dockerfile ends with CMD ["/usr/sbin/sshd", "-D"].
    • -D keeps sshd running in the foreground so the container stays alive.
    • This allows tools such as Positron to connect to the container over SSH.
    • For Linux laptops, the reference Dockerfile comments include a StrictModes no setting for sshd because the mounted SSH key ownership can differ on Linux.

3. Building and running containers

  • Building the image:
    • docker build --tag docker-uv-renv .
    • The . means “look for a Dockerfile in the current working directory.”
    • The image was named docker-uv-renv.
  • Running interactively:
    • docker run --rm -it docker-uv-renv bash
    • --rm: remove the container after exiting.
    • -it: interactive mode plus a terminal.
    • bash: start a Bash shell inside the container.
    • The prompt changed to something like root@<container-id>:/workspace#, showing that the user is now inside the container.
    • pwd showed /workspace.
    • whoami showed root.
  • Python inside the container:
    • Plain python was not found.
    • The working command was uv run python.
    • This matters because the project uses uv as the Python environment manager.
    • A prebuilt Python container may have a system python, but packages installed by uv will not necessarily be visible to that system python.
  • Mounting the project folder:
    • docker run --rm -v "$(pwd):/workspace" -it docker-uv-renv bash
    • This mounts the host’s current working directory into the container’s /workspace folder.
    • The instructor demonstrated that touch hello.py inside the container immediately created hello.py on the host.
    • He compared this to a network share drive: both sides see the same files.
  • File-conflict warning:
    • If the same file is open in two places, saving in one place can overwrite the other.
    • Some IDEs have a “revert file” action to refresh the open buffer.
    • The instructor advised reverting the file before editing if the file may have changed elsewhere.
    • Overwriting can lose changes, similar to a Git conflict but without Git’s merge process.
  • Why use volumes instead of copying files into the image?
    • COPY in a Dockerfile copies files at build time.
    • Active analysis files change often; rebuilding the image after every change would be slow.
    • Mounted volumes reflect changes immediately in both directions.
    • It avoids putting Git credentials or SSH keys into the image.
    • The container is reset when it is stopped and restarted, so secrets baked into the image would remain and be shared with anyone who pulls the image.
    • Mounting a public SSH key as authorized_keys is safer than storing private credentials in the container.
  • Container reset as a sandbox:
    • Changes inside the container are discarded when the container is stopped and started again, unless the changes are in mounted volumes.
    • This makes the container useful for experimenting with risky installs or commands.
    • The instructor said it is a good place to test something like rm -rf /, but warned emphatically not to run that on a real computer.

4. Docker Compose

The new topic was Docker Compose. A docker-compose.yml file stores the settings that would otherwise be typed as a long docker run command.

  • Why use Docker Compose?
    • Long docker run commands are hard to edit in a terminal.
    • Copy-pasted commands can break due to spaces, line breaks, or missing continuation characters.
    • A compose file is easier to document, version control, and reuse.
    • The same file can be used across macOS, Linux, and Windows.
  • Demo compose file:
    • The class used docker-compose.yml.
    • It defined one service named analysis-env.
  • Mapping compose fields to Docker commands:
    • services: lists the containers to run.
    • build: . builds the image from the Dockerfile in the current folder.
    • image: docker-uv-renv names the image, like docker build --tag docker-uv-renv.
    • ports: - "2222:22" maps host port 2222 to container port 22.
    • volumes: - .:/workspace mounts the host project folder into /workspace.
    • volumes: - ~/.ssh/id_ed25519.pub:/root/.ssh/authorized_keys:ro mounts the public SSH key as the container’s authorized keys, read-only.
  • Port numbers:
    • The first number is the host port used on the computer.
    • The second number is the port used inside the container.
    • SSH inside the container listens on port 22.
    • The host port was 2222 to avoid interfering with the host’s own port 22.
    • The instructor warned that port 22 is commonly used for real SSH connections, so it should not be overwritten accidentally.
    • If a service such as RStudio or Jupyter is running in a container, the host port and container port may be the same or different; the important thing is knowing which side you are connecting to.
  • Volumes and security:
    • .:/workspace makes the current project folder available inside the container.
    • The SSH public key mount allows SSH logins without storing private credentials in the image.
    • ro makes the mounted key read-only inside the container.
  • Service name, image name, and container name:
    • The service is analysis-env.
    • The image is docker-uv-renv.
    • Docker Compose names the running container using the project folder and service, for example 2026-11-25-docker-validate-analysis-env-1.
    • docker compose exec uses the service name, not the full container name.
    • You can run multiple containers from the same image as long as their service names or container names are different.
  • Docker Compose commands:
    • docker compose build: build the image described in the compose file.
    • docker compose up --detach: start the service in the background.
    • docker ps -a: inspect running and stopped containers.
    • docker compose exec analysis-env bash: run a command in the already running container.
    • docker compose down: stop and remove the container and its network.
    • docker compose run --rm analysis-env uv run python: run a one-off command in a new container and remove that container afterward.
  • Memory warning:
    • Containers are like other computers and use RAM.
    • Running many containers at once can consume a lot of memory.
    • The instructor advised being diligent about stopping containers when they are no longer needed.
  • Use beyond MDS:
    • The instructor mentioned that many open-source tools are deployed with Docker Compose files, for example N8N, Jellyfin, and a personal finance application.
    • Docker Compose is therefore a general skill, not only a data-science workflow detail.

5. Remote IDE connection and non-interactive execution

  • Connecting Positron or a VS Code fork:
    • Positron and other VS Code forks cannot use Microsoft-only extensions, so the Microsoft remote-container extension is not available.
    • The workflow demonstrated was Remote SSH.
    • The user is root inside the container.
    • The host is localhost because the container is running on the same computer.
    • The port is 2222, because the compose file maps host port 2222 to container port 22.
  • What the IDE sees:
    • The IDE terminal prompt shows root@<container-id>, confirming that commands are running inside the container.
    • The mounted project folder appears at /workspace.
    • Graphical IDE tools can still be used, but commands execute in the container environment.
  • Two common workflows:
    1. Mount the volume, develop locally, and test in the container separately.
    2. Connect the IDE directly to the container so commands run there from the start.
    • The instructor said he usually tests locally and then runs the final command in the container so that not everything is running at the same time.
  • Non-interactive container commands:
    • docker compose run --rm analysis-env uv run python
    • This starts a new container, runs uv run python, and removes the container when finished.
    • The same pattern can be used to render a Quarto report inside the container, for example by running the appropriate uv run quarto ... command.
  • Cloud computing connection:
    • The instructor described this as a placeholder for remote computation.
    • If a local machine is too small for a dataset, the same remote-SSH idea can be used to connect to a larger machine.
    • Docker containers and remote machines both allow work to happen on a machine other than the laptop.

6. uv project files

  • pyproject.toml:
    • The demo project used date-based versioning: version = "2026.11.13".
    • The instructor explained that this is not semantic versioning; it is a date-based scheme chosen so the course can track when packages were pinned.
    • Many dependencies were hard-pinned with ==.
    • [tool.uv] included add-bounds = "exact", which makes uv add write exact versions using == rather than minimum-version bounds.
  • .python-version:
    • The file contained 3.14.
    • It tells uv which Python version to download or use for the project.
    • Different projects can use different Python versions without changing the whole computer.
    • The instructor mentioned legacy code and large packages such as PyTorch as reasons projects may need a specific Python version.
  • uv.lock:
    • uv sync created the lock file from pyproject.toml.
    • The lock file records the exact resolved package versions.
    • The Dockerfile copies uv.lock and runs uv sync --locked to ensure the container uses the same locked environment.
  • requirements.txt:
    • The instructor noted that requirements.txt is common outside MDS.
    • MDS uses uv, so the workflow is different.
    • Instructions from external projects may not be compatible with uv without adjustment.

7. Data validation with pointblank

The session previewed the data validation chapter and used the pointblank for Python documentation package.

  • Packages:
    • The class discussed pandera and pointblank as validation tools.
    • The live demo used pointblank.
    • The demo also used palmerpenguins to load the Palmer penguins dataset.
    • pandera, pointblank, and palmerpenguins were added to the project for the validation part.
  • Loading the data:
    • from palmerpenguins import load_penguins
    • penguins = load_penguins()
  • Missing-value exploration:
    • pb.missing_vals_tbl(data=penguins)
    • This reports where missing values occur.
    • The instructor said it can be useful to inspect missingness before writing formal checks.
    • Missingness should often be treated as a separate analysis from value checks.
  • Validation object:
    • A validation starts with pb.Validate(...).
    • The demo used:
      • data=penguins
      • label="Penguin measurements"
      • thresholds=(0.01, 0.05, 0.10)
    • The thresholds mean:
      • at least 1% failure is a warning,
      • at least 5% failure is an error,
      • at least 10% failure is critical.
  • Checks shown in class:
    • col_vals_in_set(columns="species", set=["Adelie", "Chinstrap"])
      • Checks that species contains only the listed values.
      • The live demo intentionally omitted a species so the report would show a failure.
    • col_vals_between(columns="bill_length_mm", left=30, right=60, na_pass=True)
      • Checks that measured bill lengths are within a plausible range.
      • na_pass=True allows missing values to pass this value check.
    • rows_distinct()
      • Checks for duplicate rows.
      • Useful when sensor readings or repeated entries should be unique.
  • Running the checks:
    • .interrogate() runs the chained checks and returns a report.
    • The report shows which checks passed or failed and how close they are to the thresholds.
  • Splitting passing and failing rows:
    • values.get_sundered_data(type="pass") returns rows that passed the checks.
    • values.get_sundered_data(type="fail") returns rows that failed at least one check.
    • This supports team workflows: one person can continue with the passing data while another person fixes or investigates the failing rows.
    • The resulting data frames can be saved to files for handoff.
  • Where validation belongs in an analysis:
    • Data checks are not necessarily one block of code.
    • They can happen after cleaning and before modeling.
    • They can happen in multiple places as the analysis progresses.
    • The instructor said this would be part of the next week’s assignment, along with breaking code into smaller pieces.
  • Real data considerations:
    • Health data may contain impossible values, such as “pregnant men,” if such a variable exists.
    • Survey data may use codes such as 99 to represent missing values.
    • Plausible bounds can be useful for variables such as BMI or physical measurements.
    • Missing values should often be checked separately, by column and by row.

Commands from class

Cloning the demo repository

git clone git@github.com:chendaniely/2026-11-25-docker-validate.git
cd 2026-11-25-docker-validate
positron .

The instructor keeps Git repositories in a dedicated folder such as ~/git to avoid scattering repositories and to reduce the risk of nesting Git repositories. positron . opened the repository folder in the editor.

Creating the uv.lock file

uv sync

This created the local virtual environment and generated uv.lock from pyproject.toml. The lock file was then part of the files copied into the Docker image.

Building the Docker image

docker build --tag docker-uv-renv .

docker build read the Dockerfile in the current directory. The final dot means the build context is the current working directory. The image was named docker-uv-renv.

Running the container interactively

docker run --rm -it docker-uv-renv bash

This started an interactive Bash shell inside the container and removed the container after exit. Inside the container, Python was started with uv run python, not plain python.

Mounting the project into the container

docker run --rm -v "$(pwd):/workspace" -it docker-uv-renv bash

This mounted the host’s current directory into the container’s /workspace folder. The instructor then created hello.py inside the container to show that the file immediately appeared in the host folder.

Docker Compose commands

docker compose build
docker compose up --detach
docker ps -a
docker compose exec analysis-env bash
# After `docker compose exec analysis-env bash`, run `exit` inside the container to return to the host, then:
docker compose down
docker compose run --rm analysis-env uv run python
docker compose up --detach

docker compose build built the image from the compose file’s build: setting. docker compose up --detach started the service in the background. docker compose exec analysis-env bash entered the running service using the service name. docker compose down stopped and removed the service. docker compose run --rm ran a one-off command in a new container and removed that container afterward.

Adding data-validation packages

uv add pandera pointblank   # failed live
# manually add pandera, pointblank, and palmerpenguins to `pyproject.toml`, then:
uv sync

The live uv add attempts failed, so the packages were added manually to pyproject.toml. uv sync then installed the updated dependencies.

What went wrong live

  • Omitted the image name in docker run: The command docker run --rm -v "$(pwd):/workspace" -it bash caused Docker to treat bash as an image name:

    Unable to find image 'bash:latest' locally

    The fix was to include the built image name: docker run --rm -v "$(pwd):/workspace" -it docker-uv-renv bash.

  • Plain python was not found in the container: Inside the container, python gave:

    bash: python: command not found

    The working command was uv run python. This happened because the project uses uv to manage the Python environment, so the relevant Python interpreter and packages are accessed through uv.

  • Used the container name with docker compose exec: Running docker compose exec 2026-11-25-docker-validate-analysis-env-1 bash reported:

    service "2026-11-25-docker-validate-analysis-env-1" is not running

    The fix was to use the compose service name, analysis-env: docker compose exec analysis-env bash.

  • Tried to run docker compose down inside the container: Inside the container, docker compose down produced:

    bash: docker: command not found

    The fix was to exit the container and run docker compose down on the host.

  • uv add failed on the live project: The live attempts to add packages produced:

    error: Project is missing a `[project]` table; add a `[project]` table to use
       production dependencies, or run `uv add --dev` instead

    The instructor’s fallback was to add the packages to pyproject.toml manually and then run uv sync.

Questions

  • Q: Can I leave out --locked when running uv sync in the Docker build? A: Yes, but uv sync --locked is a useful guardrail. It fails if uv.lock and pyproject.toml are out of sync, so it checks that the locked dependencies are what the project expects before the container build continues.
