## Summary

This session transitioned from manually constructing Docker environments to managing them systematically using Docker Compose and integrating them directly with development environments. The instructor demonstrated how to streamline complex `docker run` flags into a version-controlled `docker-compose.yml` file, run non-interactive commands for reproducibility testing, and troubleshoot common workflow issues like path mismatches and volume mounting. The lecture concluded with a practical introduction to data validation using the `pointblank` Python package, showing students how to systematically check data quality before modeling and automatically separate passing rows from failing ones for downstream processing.

## Key takeaways

- Use `docker-compose.yml` to version-control container configurations and avoid typing excessively long `docker run` commands.
- Mount local folders into containers with `-v` to maintain a two-way sync, avoid constant rebuilds, and keep credentials secure.
- Always run Python commands inside the container using `uv run` rather than `python`, as `uv` manages the environment path.
- Connect IDEs like VS Code or Positron to a running container via Remote SSH to edit files directly inside the isolated environment.
- `pointblank` provides a robust framework for data validation, allowing you to chain checks, set warning thresholds, and automatically split data into passing and failing subsets.
- Docker containers are ephemeral sandboxes; deleting files or installing packages inside them only persists if they are written to a mounted volume.
- Data validation should be treated as an iterative process, separating checks for value ranges, missingness, and duplicates to maintain clean pipelines.

## Knowledge Points

### 1. Dockerfile structure and base images ([29 Customizing and building containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html))

*00:00:35–00:18:00*

- **Base image selection**: The course uses `rocker/r-ver:4.6.2` as a starting point because it includes R and Ubuntu. For Python-only projects, a lighter Ubuntu or Python base image is preferable to reduce download times and storage.
- **`RUN` commands**: These execute Linux commands (like `apt-get update && apt-get install`) inside the container. They mirror what you would type in a Linux terminal and are necessary for installing system-level dependencies (e.g., `git`, `nano`, `openssh-server`).
- **`COPY --from`**: Docker allows copying files directly from other images. The class copies the `uv` binary from `ghcr.io/astral-sh/uv:0.13.7` into the container so Python packages can be managed via `uv` without external installation steps.
- **`WORKDIR`**: Sets the default directory for subsequent commands and when the container starts. It prevents you from landing in the root OS directory, which avoids accidental system file deletion.
- **`ENV UV_PROJECT_ENVIRONMENT=/opt/venv`**: `uv` creates a `.venv` folder locally that matches your host OS. To ensure compatibility across different host machines (Mac ARM/Intel, Windows, Linux), this environment variable tells `uv` to install packages into a container-native path (`/opt/venv`).

> [!WARNING]
>
> Never run `rm -rf /` or similar destructive commands inside a container unless you understand that it will delete the container's entire file system. While containers are sandboxed, it highlights the importance of knowing your working directory.

### 2. Volume mounting and container isolation

*00:18:00–00:27:21*

- **`docker run -v` flag**: Mounting volumes (e.g., `docker run -v "$(pwd):/workspace"`) links a local folder to a folder inside the container. This creates an immediate two-way sync: changes made locally appear in the container and vice versa.
- **Why mount instead of `COPY`?**: `COPY` only runs at build time. If your analysis files change constantly, mounting saves you from rebuilding the container every time. It also allows you to use standard Git workflows (`git add`, `git commit`) on your local machine without configuring Git credentials inside the ephemeral container.
- **Security benefits**: Mounting your SSH key as a read-only volume (`:ro`) ensures credentials are only present while the container runs, preventing them from being baked into the image or exposed to others who pull your repo.
- **Sandboxing**: Containers act as isolated machines. If you accidentally delete system files or install incompatible software, you can simply stop and restart the container to revert to a clean state without affecting your host computer.

### 3. Docker Compose ([33 Containers: Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*00:27:24–00:44:45*

- **`docker-compose.yml`**: A YAML file that consolidates long `docker run` flags into a readable, version-controlled configuration. It defines `services`, which are named instances of your containers (e.g., `analysis-env`).
- **Specifying services**: Inside the YAML, `build: .` tells Compose to use the `Dockerfile` in the current directory. `image: docker-uv-renv` names the resulting image.
- **Port mapping**: The `ports:` section maps a host port to a container port (e.g., `"2222:22"`). The first number is the port on your computer, and the second is the port the service inside listens on. Mapping SSH to a custom port like 2222 avoids conflicts with your local machine's port 22.
- **Compose commands**: `docker compose up --detach` starts the container in the background. `docker compose exec analysis-env bash` opens an interactive shell inside the running container. `docker compose down` stops and removes the container and its associated network.

### 4. Remote IDEs and non-interactive runs ([33.3 Running a Docker container non-interactively using the Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html))

*00:44:45–01:01:13*

- **Non-interactive execution**: `docker compose run --rm analysis-env uv run python` executes a command inside a temporary container and deletes it (`--rm`) once finished. This is ideal for reproducibility checks, like running `uv run quarto render` to verify your report builds correctly in the exact environment you will submit.
- **Remote SSH connections**: IDEs like Positron or VS Code can connect directly to a running container via SSH. By specifying the container's username (`root`), host (`localhost`), and mapped port (`2222`), your editor treats the container as a remote machine.
- **Direct container editing**: Once connected, your IDE operates entirely within the container. All commands run in the isolated environment, ensuring that your code and dependencies match exactly. Changes you make are saved to the mounted local volume.

### 5. Data validation with `pointblank` ([41 Data validation: Python (pointblank)](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/data-validation-python-pointblank.html))

*01:01:13–01:20:48*

- **`pb.Validate()`**: The entry point for validation. You pass in your dataset and set `thresholds` (e.g., `(0.01, 0.05, 0.10)`) to automatically flag issues as warnings, errors, or critical failures based on the percentage of rows that fail.
- **Chaining checks**: Methods like `.col_vals_in_set()` and `.col_vals_between()` define rules. Using `na_pass=True` ensures that missing values do not automatically fail the check, keeping value range checks separate from missingness checks.
- **`interrogate()`**: Executes all chained validations and returns a summary table showing pass/fail statuses and flag colors.
- **`get_sundered_data()`**: Splits the original dataset into two subsets: rows that passed every check and rows that failed at least one. This allows you to pass the clean `passed` dataframe to modeling pipelines while sending the `failed` dataframe back to a colleague for data cleaning.
- **Separating concerns**: Validation should be modular. Check for missing values in one step, value ranges in another, and duplicate rows separately. This modular approach makes it easier to maintain and debug data quality issues across a complex workflow.
