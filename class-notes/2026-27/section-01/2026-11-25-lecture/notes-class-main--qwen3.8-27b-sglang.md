## Key takeaways

- The `Dockerfile` bakes in the software; your changing project files go in as a mounted volume (`-v` / `volumes:`) so you never rebuild the image just to move files around.
- Set `UV_PROJECT_ENVIRONMENT=/opt/venv` (via `ENV`, mirrored into `/etc/environment` for SSH logins) so the host's machine-specific `.venv` is ignored inside the container.
- `docker-compose.yml` records the whole launch — `build`, `image`, `ports`, `volumes` — in a versioned file: `docker compose build`, `up --detach`, `exec`, `down`, `run --rm`.
- A port map like `2222:22` is host:container; the first number is the one you connect to on your machine, and the two numbers do not have to match.
- In this image plain `python` is not on PATH: run things with `uv run python` (or `uv run quarto render`) so they use the packages `uv` installed.
- Never put credentials in the image: mount your SSH public key read-only (`:ro`) so it exists only while the container runs.
- The pointblank pattern: chain steps on `pb.Validate(data, label, thresholds=(0.01, 0.05, 0.10))`, run them with `interrogate()`, and split the result with `get_sundered_data(type="pass")` / `type="fail"`.

### 3. Reading the `Dockerfile`: base image and `RUN`/`apt-get` ([29.3 Choosing a base image for your Dockerfile](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html#choosing-a-base-image-for-your-dockerfile))

### 4. Installing `uv` in the image and keeping the environment portable ([29.2 `Dockerfile` command summary](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html#dockerfile-command-summary))

*00:13:18–00:19:28*

- MDS manages Python through `uv`; you will not meet a `requirements.txt` in this course, but it is the format you will see outside MDS, and instructions written for it may not be `uv`-compatible — do not blindly copy-paste them.
- Two ways to get `uv` into the image: the demo's `COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/` (Docker's `COPY` can pull files out of another container or image), or `FROM` a pre-built `uv` image and skip the step — many people do that.
- The point of Docker is control over every piece of software: `pyproject.toml` pins your packages, but not the version of `uv` itself — the image pins that. If you swap in a pre-built `uv` image, be prepared to find out where `uv` lives in it.
- `WORKDIR /workspace`: when the container starts you land here instead of the OS root. It acts like `mkdir` plus `cd` — Docker creates the folder if it does not exist. Working at the root mixes your project with the operating system's folders, which is where an `rm *` gets dangerous.
- The `.venv` that `uv sync` creates on your laptop is specific to your OS and CPU. Students span three operating systems (Windows, macOS, Linux) times two CPU architectures (Intel, ARM) — six different machines — and a `.venv` built on one will not match the container's Linux. So the `Dockerfile` tells `uv` to install into `/opt/venv` instead: when the project folder is later mounted into the container, the host `.venv` is simply ignored, and the container uses packages installed for its own operating system.

### 5. Environment variables, `uv sync --locked`, and the project files

*00:27:21–00:34:25*

- `UV_PROJECT_ENVIRONMENT=/opt/venv` is an environment variable: just as Python code has variables, every tool has its own, and `uv` looks this one up before deciding where to put the project's virtual environment.
- `ENV` in the `Dockerfile` is not enough for the SSH server, because sshd does not read process environment variables. So the `Dockerfile` also runs `RUN echo "UV_PROJECT_ENVIRONMENT=/opt/venv" >> /etc/environment` — `echo` writes what you see as-is, and `>>` appends that one line to the file logins do read.
- `COPY pyproject.toml uv.lock .python-version ./` brings the project files in, then `RUN uv sync --locked`. `--locked` is a guard: it fails if `uv.lock` and `pyproject.toml` disagree, so the image only builds when the two files are in sync.
- For a Linux laptop there is one extra commented-out line: `RUN echo "StrictModes no" > /etc/ssh/sshd_config.d/container.conf` — sshd wants root to own the key file, but on Linux the mounted key is owned by you, so strict modes have to be relaxed before Positron/VS Code can connect.
- The demo `pyproject.toml` uses calendar versioning (`version = "2026.11.13"` — the day the course finalized the packages) instead of semantic versioning, and `[tool.uv] add-bounds = "exact"` so that `uv add` pins with `==` rather than `>=`.
- `.python-version` contains just `3.14`: it tells `uv` which Python to download for this project. That lets different projects use entirely different Pythons — a fifteen-year-old project still on Python 2, PyTorch lagging behind new releases — without changing your machine.
- Locally, `uv sync` in the project folder is all it takes to create `uv.lock` from `pyproject.toml` (Daniel's ran fast because the packages were already cached) — after that the folder holds every file the `Dockerfile` copies.

### 6. Building the image: `docker build` ([29.4.3 How do I build an image locally on my laptop?](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-building.html#how-do-i-build-an-image-locally-on-my-laptop))

*00:34:25–00:35:47*

- `docker build --tag docker-uv-renv .` builds the image and names it `docker-uv-renv`.
- The trailing `.` is the current working directory (the "hidden folder" name from 521): `docker build` looks for a file called `Dockerfile` in that directory. You can point it at another directory or file, but the default is `./Dockerfile`.
- The build log walks the `Dockerfile` step by step: load the base image, run `apt-get`, copy `uv` from the `uv` image, set the `WORKDIR`, append the environment line, copy the three project files, run `uv sync --locked`, then export the layers.
- Daniel tagged the image `docker-uv-renv` even though the R parts had been deleted — it is the image name the compose file and the `docker run` examples will use.

### 7. Running the container: `docker run` flags and a different prompt

*00:35:47–00:38:22*

- `docker run --rm -it docker-uv-renv bash`: `--rm` removes the container when you exit; `-it` is two chained single-letter flags — `-i` interactive mode, `-t` tty (a real terminal prompt). Single-letter flags chain after one dash; multi-character flags take a double dash (`--rm`).
- After the image name you can ask for any command — here `bash` to get a shell.
- The prompt changes to `root@<id>:/workspace#` and `pwd` says `/workspace`: you are on another computer. `root` is the username (your computer's user is not called root), and that folder does not exist on your laptop. Same idea as cloud computing, except both sides are local.
- Inside, plain `python` is not on PATH (`bash: python: command not found`); the Python in the image comes from `uv`, so `uv run python` opens it (Python 3.14, linux). `exit` — not `quit` — leaves the shell.

### 8. Mounting the project folder with `-v`

*00:38:22–00:44:42*

- `docker run --rm -v "$(pwd):/workspace" -it docker-uv-renv bash` mounts the host's current folder at `/workspace` in the container; it is written with `$(pwd)` so the same command works on Windows and macOS.
- `touch hello.py` inside the container makes `hello.py` appear on the host immediately, and edits flow both ways — like a network share drive where two machines work on the same files.
- Why mount instead of `COPY` in the `Dockerfile`? `COPY` freezes the files at build time; if your analysis changes every minute you would rebuild the whole image just to move files in. Bake in the software; mount in the files that change.
- Practical Git reason: the container is, to GitHub, a brand-new machine — it does not inherit your personal access token or SSH key, and it resets when you turn it off. With the folder mounted you do `git add` / `git commit` / `git push` on the host instead of re-configuring Git in the container every time.
- Security reason: your SSH key is effectively your password; do not bake it into the image so that anyone who pulls the container can read it. Mounting keeps the credential out of the image and present only while the container runs.
- Exception: for the final submitted version where the container must stand alone, copying the files into the image is fine — that is a compliance artifact, not day-to-day work.

> [!WARNING]
>
> Do not edit the same file on the host and inside the container at the same time. Nothing merges the two sides: whoever saves last silently overwrites the other side's changes, like a Git conflict without Git. If you have the file open on one side, use the editor's "revert file" (refresh) before you edit it.

### 9. `docker-compose.yml`: putting the launch in a file ([33.1 Docker Compose to launch containers](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html#docker-compose-to-launch-containers))

*00:44:42–00:55:31*

- Motivation: `docker run` commands pile up flags (`-v`, ports, `-e` environment variables, `--rm`, …), and in a terminal you cannot click to a spot in a 20-line pasted command to edit it. A compose file keeps every parameter in a documented, version-controlled file.
- The file the class copied from the reference repository:
  - `services:` — the containers the project runs; there is one here, named `analysis-env`. The service name can differ from the image name — you could run `analysis-env-2` or `analysis-env-3` from the same setup.
  - `build: .` with `image: docker-uv-renv` — "if this image does not exist, build it from the `Dockerfile` in this folder and call it `docker-uv-renv`": the compose equivalent of `docker build --tag docker-uv-renv .`.
  - `ports: - "2222:22"` — the first number is your computer, the second is the container. SSH listens on 22 inside; 22 is a port your machine probably already uses for real things, so expose it as 2222. Other containers have their own ports too (RStudio on 8787, Ollama on a five-digit port); a second Jupyter Lab instance would default to 8889. The numbers do not have to match, and the first number is the one you connect to — when you use someone else's file, check which side they put which port on. The file's comment notes that writing `127.0.0.1:2222:22` stops others on the same Wi-Fi from reaching it.
  - `volumes:` — `.:/workspace` (the same mount as `-v`), plus `~/.ssh/id_ed25519.pub:/root/.ssh/authorized_keys:ro`: your SSH public key becomes the list of keys allowed to log in as `root`, read-only, and present only while the container runs — never baked into the image.
- `docker compose build` does the `docker build` from the file (and reuses cached layers). `docker compose up --detach` starts the container: `--detach` means "turn it on but do not give me the prompt inside" — it runs in the background and your terminal comes back, while the container keeps running its foreground `sshd -D` process.
- `docker ps -a` shows the result: a container named after the project folder and the service (`2026-11-25-docker-validate-analysis-env-1`), image `docker-uv-renv`, command `"/usr/sbin/sshd -D"`, and the forward `0.0.0.0:2222->22/tcp` — the port mapping you just read off the file.

### 10. `exec`, `down`, and shutting containers down ([33.2 Docker Compose commands](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html#docker-compose-commands))

*00:55:31–00:58:24*

- `docker compose exec analysis-env bash` drops you into a shell in the already-running container; `exit` returns to your host while the container keeps running.
- Use the service name from the compose file (`analysis-env`), not the long container name Docker invented (`2026-11-25-docker-validate-analysis-env-1`) — with that one, compose answers `service "…" is not running`.
- `docker compose down` reads the file and stops and removes the container and its network.
- Be diligent about turning things off: containers are other computers and they hold RAM; run enough of them at once and your machine's memory disappears into them.
- Connection to the course: everything you can do with `docker run` you can do with compose, and compose is the easier way to specify it — which is also one of the ways your milestones are graded and documented.

### 11. One-off commands: `docker compose run` ([33.3 Running a Docker container non-interactively using the Docker Compose](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/containers-docker-compose.html#running-a-docker-container-non-interactively-using-the-docker-compose))

*00:58:24–01:01:13*

- `docker compose run` starts a new, short-lived container for a service, runs the command you give it, and with `--rm` deletes the container when the command finishes.
- `docker compose run --rm analysis-env python` fails with `exec: "python": executable file not found in $PATH` — the image has no plain `python` on PATH because everything is installed through `uv`.
- The working form is `docker compose run --rm analysis-env uv run python`. Same point as the interactive container: even if a pre-built image has Python installed, `python` and `uv`'s Python are two different things, and the packages live in `uv`'s virtual environment.
- The slot after the service name accepts any bash command: for a Quarto report it would be `uv run quarto render <file>` — tell the container to build your analysis and check that it renders in the exact environment you designed, without re-running it locally.
- That is the reproducibility payoff Daniel kept returning to: "You made a machine. This is how you can go and test this machine by sending it commands."

### 12. Connecting Positron or VS Code to the container with Remote SSH

*01:01:41–01:06:55*

- Start with `docker compose up --detach` so the SSH server is running in the background.
- VS Code forks (Positron, Cursor, and anything that looks like VS Code but is not Microsoft's) do not have the Microsoft extension store, so instead of a Microsoft-only "attach to container" feature, you connect with the Remote SSH extension.
- Connect as `root@localhost` on port `2222` — the username from the container prompt you saw earlier, not your machine's username, which is what would be tried by default.
- Open the `/workspace` folder through the connection — it is the mounted project folder, and this is where knowing your paths pays off. From then on the window behaves as if you are inside the container: every command you run runs there, so you do not have to run things twice.
- Two ways to work: mount the volume and edit on the host (testing in the container when you want to), or live inside the container directly. Daniel's habit: work locally, then run the last command in the container, rather than having everything open at the same time.
- This is a placeholder for cloud computing: if your machine is too small for the dataset (last summer he used a 128 GB RAM machine for 100 GB datasets), the same remote-SSH setup points at a bigger machine over the internet. The milestones will not test the connection itself — pick whatever workflow you like.

### 13. Docker Compose outside the classroom

*01:06:55–01:08:33*

### 15. Why validate, and where the missing values are ([41.1 Where are the missing values?](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/data-validation-python-pointblank.html#where-are-the-missing-values))

*01:11:40–01:13:45*

- The goal, stated as next week's assignment work: before the modelling step (or right after the data-cleaning step), check in code that the data actually contains the values you expect.
- Daniel's examples from health data: you do not expect pregnant men; BMI should have an upper bound; health surveys often code "missing" as `99` instead of a real missing value, so checks must follow the codebook; and missingness should be (roughly) random — if it is not, find out why.
- `pb.missing_vals_tbl(data=penguins)` gives a report of missing values per column, broken into sections of rows from the top of the data down; the demo showed most missingness concentrated early in the data (his guess: the order collection happened — penguins struggling onto the scale).
- It also produces a visual of the missingness so you can see whether there are "holes" somewhere in the dataset; how you judge that is subjective, but it starts the conversation.

### 16. Chaining value checks with `pb.Validate` ([41.2 Checking values](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/data-validation-python-pointblank.html#checking-values))

*01:13:45–01:18:29*

- The workflow is "create an agent of tests, then ask it to report back": build the checks, chain them onto one object, then run them all at once.
- `pb.Validate(data=penguins, label="Penguin measurements", thresholds=(0.01, 0.05, 0.10))` — the thresholds say: start warning when 1% of a step's rows fail, error at 5%, critical at 10%. A 1% problem can be left silent if you decide it is not a big deal.
- `col_vals_in_set(columns="species", set=["Adelie", "Chinstrap"])`: an assumption about the allowed values, checked in code. The demo deliberately dropped "Gentoo" from the set so the step fails and you can watch the report flag the out-of-set values.
- `col_vals_between(columns="bill_length_mm", left=30, right=60, na_pass=True)`: a range check — inclusive by default, with an option to flag it as not inclusive. `na_pass=True` lets missing values pass the step so it only judges values that actually exist; the same idea works for BMI or any column with sensible bounds.
- `rows_distinct()` checks that no two rows are identical — for example, duplicate sensor readings or two people coding the same record.
- `interrogate()` is what actually runs every step; nothing happens until you call it. The report object shows a pass/fail rate with colors for each threshold level.
- The checks are not one block: you check the data in several places as the analysis progresses, and Daniel strongly recommended keeping missingness as a separate analysis from value checks (per column and per row).

### 17. Splitting passing and failing rows ([41.4 Splitting the passing and failing rows](https://ubc-dsci.github.io/reproducible-and-trustworthy-workflows-for-data-science/lectures/data-validation-python-pointblank.html#splitting-the-passing-and-failing-rows))

*01:18:29–01:20:48*

- `values.get_sundered_data(type="pass")` and `values.get_sundered_data(type="fail")` return two separate data frames: the rows that passed every step, and the rows that failed at least one.
- The workflow payoff: hand the passing frame to the teammate downstream ("build the rest of the pipeline on data that works right now") while the cleaning person keeps working on the failed rows — you do not wait for data to be 100% clean before the rest of the project can move.
- Because these are ordinary data frame objects, you can save the failed rows out to a CSV (the textbook's example: `failed.to_csv("penguins_to_fix.csv", index=False)`) and hand a teammate a concrete to-fix dataset.
- What this sets up for next week: "a lot of this data validation stuff and also breaking up your code into smaller pieces."

### Docker Compose lifecycle

```bash
docker compose build                 # build the docker-uv-renv image from the Dockerfile

docker ps -a                         # confirm: 0.0.0.0:2222->22/tcp, /usr/sbin/sshd -D
docker compose exec analysis-env bash   # shell in the running container (service name, not container name)

```

`exec` wants the service name from the compose file, and `exit` from the `exec` shell returns to the host while the container keeps running until `down`.

### One-off commands in a fresh container

```bash

```

`--rm` deletes the container when the command finishes. The same slot runs any command — for example `uv run quarto render` on a report — which is how you test that your analysis builds in the container's exact environment.
