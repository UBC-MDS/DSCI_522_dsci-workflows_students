Individual assignment 2

Practice building and publishing a Docker image

The purpose of this assignment is to make sure everyone gets hands-on practice building a Docker image from a Dockerfile and publishing it to Docker Hub with GitHub Actions.

Exercise instructions

  1. Create a public repository on GitHub.com, under your personal account, called dsci522-dockerfile-practice. Select the option to create the repository with a README file.

  2. Clone the repository to your computer. The rest of the work happens inside this folder.

  3. Make a small project with either uv (Python) or renv (R). Pick whichever language you prefer. Your project needs at least two packages that you haven’t used before, and each one must be pinned to an exact version.

    • uv:
      • Add your packages so that pyproject.toml lists them with == (see uv: pinning exact versions).
      • Pin Python to version 3.11 or newer, so that it is recorded in .python-version.
      • Commit pyproject.toml, uv.lock and .python-version to your repository. Don’t commit .venv/.
      • If you need a refresher on uv, see the DSCI 521 uv lecture notes.
    • renv:
      • List your packages in DESCRIPTION with (== x.y.z), and use explicit snapshots (see renv: declaring packages in DESCRIPTION).
      • Commit DESCRIPTION, renv.lock, .Rprofile and renv/ to your repository (the .gitignore inside renv/ keeps the installed packages out).

  4. Add a Dockerfile to the root of your repository. Its job is to build an image that has your packages installed, exactly as recorded in your lock file. Follow the chapter for the language you chose:

    • uv: Python packages with uv in an image
    • renv: R packages with renv in an image

    Your Dockerfile should do three things:

    • Start from a base image that has a version tag (for example rocker/r-ver:4.6.2), not latest, in the FROM line.
    • Use the COPY command to copy your project files, including the lock file, into the image.
    • Use the RUN command to install the packages from the lock file.

  5. Build your image and test it on your computer. Run a container from the image and load each of your packages inside it. If every package loads, your Dockerfile works. Fix any problems now, before you set up GitHub Actions, because it is much faster to debug on your own computer.

  6. Set up Docker Hub.

    • Create a free Docker Hub account if you don’t have one.
    • Create a public Docker Hub repository named dsci522-dockerfile-practice.
    • Create a Docker Hub access token with Read & Write permissions, and copy it somewhere safe. You can only see it once.

  7. Give GitHub your Docker Hub login, so that GitHub Actions can publish for you. In your GitHub repository, add two repository secrets (Settings > Secrets and variables > Actions > New repository secret):

    • DOCKER_USERNAME: your Docker Hub username.
    • DOCKER_PASSWORD: the access token from step 6 (not your Docker Hub password).

    Use these exact names, because the workflow looks for them.

  8. Add a GitHub Actions workflow that automatically builds your image and pushes it to Docker Hub. See Building images for several platforms for background on building images and pushing them to Docker Hub; for this assignment, use the single-platform workflow.

    • Copy the workflow into .github/workflows/publish-dockerhub.yml in your repository.
    • Change only its IMAGE line, so that the image goes to your Docker Hub account (and not somebody else’s): <your-docker-hub-username>/dsci522-dockerfile-practice, all in lowercase.
    • The workflow builds the image and pushes it to Docker Hub, tagged latest and with the commit SHA, so every pushed version of the image gets its own tag. It runs whenever a push changes the Dockerfile or a lock file, and you can also run it by hand.

  9. Push your changes and make sure the workflow runs and succeeds.

    • Push a commit that changes the Dockerfile or your lock file, and the workflow starts on its own.
    • If it doesn’t start, run it by hand: click the Actions tab, click the workflow in the left sidebar, then open the Run workflow drop-down menu and click Run workflow.
    • Watch the run on the Actions tab, and check that it finishes with a green check mark. Then look at your Docker Hub repository to see that the image is there.
    • If Git refuses to push the workflow file, your personal access token needs the workflow scope: on GitHub, go to Settings > Developer settings > Personal access tokens, select your token, and tick workflow.

  10. Add a LICENSE.md file that attributes the workflow you copied. The workflow comes from docker-uv-renv.

    • Copy the text of its LICENSE (MIT) into your LICENSE.md.
    • Add a note in the file saying that this license only covers the code you copied (.github/workflows/publish-dockerhub.yml).

Submission instructions

Follow the instructions for submission on Gradescope. We only need URLs, entered into Gradescope directly: there is no PDF to make. You will submit:

  1. A link to the GitHub.com repository that you create for this assignment.
    • You should name your GitHub.com repository dsci522-dockerfile-practice.
  2. A link to your Docker image on Docker Hub. You should name your Docker Hub repository dsci522-dockerfile-practice.

Rubric

This assignment will be graded for completion as follows:

Grade Description
-15% There were issues with the links submitted that made it difficult to find the GitHub or Docker Hub repository
-15% A package in pyproject.toml or DESCRIPTION is not pinned to an exact version
-15% There were authentication issues with publishing to Docker Hub
-33% Fewer than two packages are listed in pyproject.toml or DESCRIPTION
-33% The Docker image was not built successfully by GitHub Actions and published to Docker Hub
-100% Assignment was not completed (no GitHub repository was created, or the repository is missing the environment files or the Dockerfile)
