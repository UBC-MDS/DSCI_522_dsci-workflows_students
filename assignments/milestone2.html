Milestone 2

NoteThe end-of-course project goal

Your team answers a predictive question with a public data set, in R and/or Python, with a focus on reproducible and trustworthy workflows. By the end of the course, your single Quarto document will have become a project with:

  • well-documented, modular scripts in R and/or Python
  • a pipeline automated with GNU Make
  • a reproducible Quarto report
  • a Docker container for the computational environment
  • a GitHub repository for collaboration and sharing

Milestone 2 summary

This milestone is about moving your project into a container.

We give you the Dockerfile, the workflow file and docker-compose.yml (see below). They are adapted from docker-uv-renv.

ImportantYou only lose points once for the same mistake

If you lost points for something in Milestone 1, we won’t take points off again for it in Milestone 2. That would be unfair: you may not get your Milestone 1 grades back before Milestone 2 is due. Still fix it once you get the feedback: later milestones build on this work, and in Milestone 4 you can fix the mistakes you made in previous milestones.

ImportantSee what a finished Milestone 2 looks like

An example Milestone 2 that corresponds to our expectations from this year is here: Breast Cancer Predictor in Python 1.0.0. Use it as your model: compare your repository with it before you submit.

1. Put your environment in a container

  1. Add the Dockerfile. Copy the version for your project’s language(s) below into a file named Dockerfile in the root of your repository. If you use R, change 4.6.2 on the FROM line to the R version in your renv.lock. Always keep a version tag on the FROM line, never latest.

  2. Check your environment files. The image installs your packages from your lock files, so these must be in your repository and agree with each other:

    • Python (uv): pyproject.toml with every package pinned with == (not >=), uv.lock and .python-version. It must list ipykernel, nbclient and pyyaml (Quarto needs them to run the Python code in your report).
    • R (renv): DESCRIPTION with every package pinned with (== x.y.z), renv.lock, .Rprofile and renv/. DESCRIPTION is required, and it must list knitr and rmarkdown (Quarto needs them to run the R code in your report).

  3. Test the build on your computer before you push: docker build --tag my-project . (as in Individual Assignment 2). Fixing errors here is much faster than on GitHub Actions.

  4. Build and publish the image with GitHub Actions.

    • One team member sets up Docker Hub and the GitHub secrets (see below).
    • Copy the workflow below into .github/workflows/publish-dockerhub.yml, then commit and push. You don’t need to change anything in it.
    • It builds for linux/amd64 (Intel/AMD) and linux/arm64 (ARM, such as Apple silicon Macs), and publishes them under two tags: latest and sha- plus 7 characters of the commit ID.
    • Check that the run succeeds and that your image’s tag on Docker Hub lists both platforms.
    • Don’t turn on branch protection for main: the workflow commits the new image tag straight to your branches, and branch protection would block it.

  5. Add docker-compose.yml.

    • Copy the file below into the root of your repository.
    • Change its image: line to your image, pinned to the commit-SHA tag your workflow pushed, not latest (for example, image: yourname/your-github-repo-name:sha-1a2b3c4, all in lowercase). You only do this once: after that, the workflow updates the tag for you.
    • Keep the service name analysis-env, so the commands in part 2 work as written.

  6. Work in the container from now on, with Positron over ssh Follow the step-by-step guide below the first time. To add a package:

    • On a branch, add it with uv or renv, commit the changed files together and push.
    • GitHub Actions publishes a new image and commits its tag to docker-compose.yml on that branch.
    • Run git pull and docker compose pull, then merge the branch in a pull request.
    • The merge builds the image once more and commits a new tag to main. When that run finishes, everyone runs git pull on main and docker compose pull again.
TipThe Dockerfile (step 1)

Pick the tab for your project. All three start the ssh server, so you can work in the container with Positron.

  • Python only
  • R only
  • Python and R
Dockerfile
# Adapted from docker-uv-renv by Daniel Chen (MIT License)
# https://github.com/chendaniely/docker-uv-renv

# Start from Ubuntu Linux (this image also has R, which you can ignore).
FROM rocker/r-ver:4.6.2

# Install the programs the project needs:
# curl downloads files, git/less/nano let you work in a terminal,
# make runs a Makefile, openssh-server lets Positron connect over ssh
RUN apt-get update && apt-get install --yes \
    curl \
    git \
    less \
    make \
    nano \
    openssh-server

# Install Quarto (it comes with Typst for PDFs, so no LaTeX).
# dpkg --print-architecture gives amd64 or arm64, to match the computer.
RUN curl --location --output quarto.deb \
    https://github.com/quarto-dev/quarto-cli/releases/download/v1.11.9/quarto-1.11.9-linux-$(dpkg --print-architecture).deb \
  && apt-get install --yes ./quarto.deb \
  && rm quarto.deb

# Copy the uv program into the image (0.13.7 pins uv's version)
COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /uvx /usr/local/bin/

# Your project folder is mounted at /workspace,
# so the packages go in /opt instead
WORKDIR /workspace

# Python packages (uv) go in /opt/venv
ENV UV_PROJECT_ENVIRONMENT=/opt/venv
# ssh logins don't see ENV, only /etc/environment
RUN echo "UV_PROJECT_ENVIRONMENT=$UV_PROJECT_ENVIRONMENT" >> /etc/environment
COPY pyproject.toml uv.lock .python-version ./
# --locked: stop if uv.lock doesn't match pyproject.toml
RUN uv sync --locked

# On a Linux laptop, remove the # from the next line.
# (sshd wants root to own the key file, but on Linux the mounted one is yours.)
# RUN echo "StrictModes no" > /etc/ssh/sshd_config.d/container.conf

# Start the ssh server when the container starts.
# -D keeps it in the foreground, so the container keeps running.
CMD ["/usr/sbin/sshd", "-D"]

TipSetting up Docker Hub and the GitHub secrets (step 4)

One team member:

  1. Creates a public Docker Hub repository with the same name as your GitHub repository, in lowercase (e.g. GitHub Wine_Quality_Predictor becomes Docker Hub wine_quality_predictor).
  2. Creates a Docker Hub access token with Read & Write permissions.
  3. Adds two repository secrets to your GitHub repository (Settings > Secrets and variables > Actions > New repository secret): DOCKER_USERNAME (the Docker Hub username) and DOCKER_PASSWORD (the access token, not the Docker Hub password).
TipThe workflow file (step 4)

Job 1 runs the same docker build and docker push as Individual Assignment 2, on an Intel/AMD and an ARM computer at the same time. Job 2 puts the two images under one tag. Job 3 writes that new tag into your docker-compose.yml and commits it to the branch you pushed. You don’t need to change anything: the workflow names your image from the DOCKER_USERNAME secret and your GitHub repository’s name.

.github/workflows/publish-dockerhub.yml
# Builds the image from your Dockerfile for Intel/AMD and ARM computers,
# and publishes it on Docker Hub.
# Save this file as .github/workflows/publish-dockerhub.yml

name: Publish image to Docker Hub

# When the workflow runs
on:
  # by hand: Actions tab > Publish image to Docker Hub > Run workflow
  workflow_dispatch:
  # on its own: when a push changes one of these files
  push:
    # only branch pushes, not tags: a release creates a tag, and GitHub
    # ignores the paths filter for tag pushes, so it would run every release
    branches:
      - '**'
    paths:
      - Dockerfile
      - pyproject.toml
      - uv.lock
      - .python-version
      - renv.lock
      - .Rprofile
      - renv/activate.R
      - .github/workflows/publish-dockerhub.yml

env:
  # Your image: your Docker Hub username / this GitHub repository's name.
  # Nothing to change here.
  IMAGE_NAME: ${{ secrets.DOCKER_USERNAME }}/${{ github.event.repository.name }}

jobs:
  # Job 1: build the image on two computers at the same time,
  # one Intel/AMD and one ARM, and push one tag from each
  build:
    strategy:
      matrix:
        include:
          - runner: ubuntu-latest     # Intel/AMD
            arch: amd64
          - runner: ubuntu-24.04-arm  # ARM
            arch: arm64
    runs-on: ${{ matrix.runner }}
    steps:
      # 1. Docker image names must be lowercase, so save a lowercase copy as IMAGE
      - name: Make the image name lowercase
        run: echo "IMAGE=$(echo "$IMAGE_NAME" | tr '[:upper:]' '[:lower:]')" >> "$GITHUB_ENV"

      # 2. Copy your repository onto the computer
      - name: Check out the repository
        uses: actions/checkout@v7

      # 3. Log in to Docker Hub with your two repository secrets
      - name: Log in to Docker Hub
        uses: docker/login-action@v4
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      # 4. Build the image for this computer, tagged for example sha-1a2b3c4-arm64
      #    (sha- plus the first 7 characters of the commit ID, plus the chip)
      - name: Build the image
        run: docker build --tag "$IMAGE:sha-${GITHUB_SHA::7}-${{ matrix.arch }}" .

      # 5. Upload it to Docker Hub
      - name: Push the image
        run: docker push "$IMAGE:sha-${GITHUB_SHA::7}-${{ matrix.arch }}"

  # Job 2: after both builds finish, put the two images under one tag,
  # so each computer downloads the one for its chip
  combine:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # Docker image names must be lowercase, so save a lowercase copy as IMAGE
      - name: Make the image name lowercase
        run: echo "IMAGE=$(echo "$IMAGE_NAME" | tr '[:upper:]' '[:lower:]')" >> "$GITHUB_ENV"

      - name: Log in to Docker Hub
        uses: docker/login-action@v4
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      # Make the tags latest and sha-1a2b3c4, each holding both images
      - name: Combine the two images under one tag
        run: |
          docker buildx imagetools create \
            --tag "$IMAGE:latest" \
            --tag "$IMAGE:sha-${GITHUB_SHA::7}" \
            "$IMAGE:sha-${GITHUB_SHA::7}-amd64" \
            "$IMAGE:sha-${GITHUB_SHA::7}-arm64"

  # Job 3: write the new tag into docker-compose.yml and commit it
  # to the branch you pushed, so your team only has to git pull
  update-compose:
    needs: combine
    runs-on: ubuntu-latest
    # lets this job push a commit to your repository
    permissions:
      contents: write
    steps:
      - name: Check out the repository
        uses: actions/checkout@v7

      # Replace the image: line, e.g. image: yourname/your-repo:sha-1a2b3c4
      # (skipped if you have no docker-compose.yml yet)
      - name: Put the new tag in docker-compose.yml
        if: hashFiles('docker-compose.yml') != ''
        run: |
          IMAGE=$(echo "$IMAGE_NAME" | tr '[:upper:]' '[:lower:]')
          sed -i "s|^\( *image:\).*|\1 $IMAGE:sha-${GITHUB_SHA::7}|" docker-compose.yml

      # Commit and push the change (does nothing if the file didn't change)
      - name: Commit and push docker-compose.yml
        if: hashFiles('docker-compose.yml') != ''
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add docker-compose.yml
          git diff --cached --quiet && exit 0
          git commit -m "Use image tag sha-${GITHUB_SHA::7} in docker-compose.yml"
          git pull --rebase
          git push

It runs on its own when a push changes the Dockerfile, a file the Dockerfile copies into the image, or the workflow file. To run it by hand: Actions tab > Publish image to Docker Hub > Run workflow. On Docker Hub you will see four tags: latest, sha-1a2b3c4, and the two halves sha-1a2b3c4-amd64 and sha-1a2b3c4-arm64. Job 3 puts the one without -amd64 or -arm64 in docker-compose.yml for you. Then run git pull to get that commit, and docker compose pull to download the new image.

TipThe docker-compose.yml file (step 5)

Change only the image: line.

docker-compose.yml
# Adapted from docker-uv-renv by Daniel Chen (MIT License)
# https://github.com/chendaniely/docker-uv-renv

services:
  # the service name: `docker compose run analysis-env ...` uses it
  analysis-env:
    # CHANGE THIS LINE once: your Docker Hub username / your GitHub repository's
    # name in lowercase, with the sha- tag your workflow pushed (not latest).
    # After that, the workflow updates the tag for you.
    image: your-docker-hub-username/your-github-repo-name:sha-1a2b3c4
    ports:
      # 2222 on your computer, 22 (ssh) in the container
      - "2222:22"
    volumes:
      # your project folder, at /workspace in the container
      - .:/workspace
      # your ssh public key, so you can log in (ro: read-only)
      - ~/.ssh/id_ed25519.pub:/root/.ssh/authorized_keys:ro
      # your Git name and email, so your commits in the container count as yours
      - ~/.gitconfig:/root/.gitconfig:ro

There is no build: . line: everyone downloads the image your workflow published, instead of building their own.

TipConnect Positron to the container over ssh, step by step (step 6)

Your CONTRIBUTING.md walks your teammates through these same steps (see part 2).

Once, before your first connection:

  1. Install Positron on your computer. Its Remote SSH feature, which connects to the container, comes built in, so you don’t need an extension.
  2. Make an ssh key if you don’t have one. In a terminal on your computer, run ssh-keygen -t ed25519 and press Enter at each question. Check that ~/.ssh/id_ed25519.pub now exists.
  3. Check that Git knows who you are on your computer: git config --global user.email should print the email of your GitHub account. If it prints nothing, set it with git config --global user.name "Your Name" and git config --global user.email "you@example.com". docker-compose.yml shares this with the container, so your commits there count as yours.
  4. Download the image: in your project folder, run docker compose pull.

Each time you work on the project:

  1. In a terminal, in your project folder, start the container in the background:

    docker compose up -d

    docker compose ps should list analysis-env as running.

  2. In Positron, open the Command Palette (Cmd+Shift+P on Mac, Ctrl+Shift+P on Windows).

  3. Type and run Remote SSH: Show Remote Menu, then pick Connect to Host.

  4. Type root@localhost:2222 and press Enter. A new Positron window opens.

    • If it asks for the platform of the remote host, pick Linux.
    • If it asks whether you trust the host (a “fingerprint”), click Continue.
    • The first time, Positron installs its server inside the container. This takes a few minutes (e.g., took > 5 minutes on Sky’s computer).

  5. Open your project folder. You are connected now (the bottom left corner shows SSH: localhost:2222), but the Explorer says No folder opened, and a terminal starts in /root, the container’s home folder, which has no project files. That is normal.

    • Click Open Folder in the Explorer. A path box appears at the top of the window.
    • Delete what is in it, type /workspace, and press Enter (or click OK, you may need to click “ok” a few times before this works).
    • The window reloads. The Explorer now shows WORKSPACE [SSH: LOCALHOST:2222] with your project files. A file you change here changes on your computer too.

  6. Pick the interpreter. Positron may start a different Python than your project’s, so check this every time. Click the interpreter button at the top right of the window (it shows a Python or R version). The menu that opens, Running Interpreter Sessions, only lists sessions that are already running (such as /usr/bin/python3, the container’s system Python: not this one). Click New Console Session…, then:

    • Python: pick the one named Python 3.x (uv: your-project-name) with the path /opt/venv/bin/python, the environment built from your uv.lock. The top right button then shows that name. If it isn’t in the list, open the Command Palette, run Python: Select Interpreter, choose Enter interpreter path… and type /opt/venv/bin/python. Don’t pick /workspace/.venv: that is the environment from your own computer, and it doesn’t run in the container.
    • R: pick the R version in the list. It already uses the packages from your renv.lock.
    • To check, run import sys; print(sys.executable) in the Console. It should print /opt/venv/bin/python.

  7. Work as usual. The Terminal, Console and Render button all run inside the container.

  8. When you are done, close the Positron window, then stop the container in a terminal on your computer:

    docker compose down

If it doesn’t connect:

  • ~/.ssh/id_ed25519.pub is a folder: Docker made it because the key didn’t exist yet. Run docker compose down, delete that folder, make the key (step 2 above), and start again.
  • ~/.gitconfig is a folder, or Git in the container doesn’t know your name: the same thing happened with your Git settings. Run docker compose down, delete that folder, set your name and email (step 3 above), and start again.
  • GitHub asks you to sign in when you push from the container: sign in once in the browser window Positron opens. Positron remembers it.
  • It asks for a password: the container can’t see your key. Check that your key is named id_ed25519.pub, or change the key path in docker-compose.yml.
  • “Remote host identification has changed”: you are using a new image. Run ssh-keygen -R "[localhost]:2222", then connect again.
  • Linux laptops: ssh refuses the key because the file belongs to you, not root. Remove the # from the StrictModes no line in the Dockerfile and push, so the workflow publishes a fixed image.
  • Port 2222 is already in use: change the first 2222 in docker-compose.yml to another number (e.g. 2223), and connect to that port instead.

More detail: Working in a container over ssh with Positron.

TipWhat your CONTRIBUTING.md must include
ImportantReproducibility is worth 20 points

We launch your container and run your analysis by following your README exactly as written. 3. Publish your report on GitHub Pages

Anyone should be able to read your report online without cloning your repository. You publish it by hand: put a self-contained copy of your rendered report at docs/index.html. If you already published your report in Milestone 1, switch to this setup anyway, because later milestones build on it.

  1. Make the rendered report one self-contained HTML file, in its YAML header (skip this if your _quarto.yml already sets it):

    format:
  html:
    embed-resources: true

    If you have only been rendering to PDF, render to HTML as well.

  2. Render your report, then copy it into docs/ as index.html, and add an empty .nojekyll file:

    mkdir -p docs
cp <path-to-your-report>.html docs/index.html
touch docs/.nojekyll
    TipIf you also render a PDF: fix the “Other Formats” link

    When you render more than one format, Quarto adds a link to the others (for example “Typst”) under Other Formats in the HTML report. That link points to a file next to the report, which is not in docs/, so on GitHub Pages it gives a 404. Either remove the link, in your report’s YAML header or your _quarto.yml:

    format:
  html:
    format-links: false

    or point it to the PDF in your repository:

    format:
  html:
    format-links:
      - html   # stops Quarto adding its own link
      - text: PDF
        href: https://github.com/ubc-mds-2026-27/<your-repository>/blob/main/<path-to-your-report>.pdf
        icon: file-pdf

  3. Commit and push docs/. Check that your .gitignore does not ignore docs/ or .html files.

  4. On GitHub.com, go to Settings > Pages > Deploy from a branch, choose the main branch and the /docs folder, and click Save.

  5. After a few minutes, open https://ubc-mds-2026-27.github.io/<your-repository>/ and check that the whole report shows, including its figures.

  6. Put this URL in your README (as the link to your rendered report) and in the About section of your repository.

ImportantKeep the published report up to date

docs/index.html is a copy. Each time you re-render your report, copy it into docs/ again and push. We grade from your 1.0.0 release, and the report on GitHub Pages should match it.

TipWhy this works
  • GitHub Pages can publish the files in a docs/ folder on main, exactly as they are.
  • When someone visits your site’s address, the server shows the file named index.html.
  • With embed-resources: true, the report is one HTML file that holds its figures and styling, so it still works after you copy it.
  • .nojekyll tells GitHub Pages to serve your file as it is (see Turning off Jekyll with .nojekyll).

Copying by hand is easy to forget, so it is not how you would publish a larger site. In DSCI 524 you will use tools that build and publish a website for you.
