Milestone 2

Overall project summary

In this course you will work in assigned teams of three or four (see group assignments on GitHub) to answer a predictive statistical/machine learning question using a publicly available data set that will allow you to answer that question. To answer this question, you will perform a complete data analysis in R and/or Python, from data import to communication of results, while placing significant emphasis on reproducible and trustworthy workflows.

Your data analysis project will evolve throughout the course from a single, monolithic Jupyter notebook, to a fully reproducible and robust data data analysis project, comprised of:

  • a well documented and modularized scripts written in R and/or Python,
  • a data analysis pipeline automated with GNU Make,
  • a reproducible report powered by Quarto,
  • a containerized computational environment created and made shareable by Docker
  • a remote version control repository on GitHub for project collaboration, sharing, and documentation.

An example final project from past years can be seen here: Breast Cancer Predictor

1. Use a container for the computational environment

Write a Dockerfile to create a custom container for the computational environment for your project. Build your container using GitHub Actions, and publish your container image on DockerHub. Once this is done, shift the development of your project from working in a virtual environment to working in a container!

The Dockerfile is the file used to specify and create the Docker image from which containers can be run to create an reproducible computational environment for your analysis. For this project, we recommend using a base Docker image that already has most of the software dependencies needed for your analysis. In particular, the quay.io/jupyter/minimal-notebook image. When you add other software dependencies to this Dockerfile, ensure that you pin the version of the software that you add. You can do this most easily if you use our recommended environment.yml > conda-lock.yml > Dockerfile workflow that you learned about in individual_assignment2.

Note - this document should live in the root of your public GitHub.com repository.

In this milestone, we expect you to add a GitHub Actions workflow to automatically build the image, push it to DockerHub, and version the image (using latest is okay for now) and GitHub repo when changes are pushed to the Dockerfile

You will need to add your DockerHub username and password (naming them DOCKER_USERNAME and DOCKER_PASSWORD, respectively) as GitHub secrets to this repository for this to work. This part is similar to Individual Assignment 3.

Additionally, document how to use and update your container image in your README. This is important to make it easy for you and your team to shift to a container solution for your computational environment. We also expect you will use Docker Compose so that launching your containers is as frictionless as possible (which makes you more likely to use this tool in your workflow)!

ImportantYour README instructions are worth 5 all-or-nothing points

5 points of this milestone are for the reproducibility of your README instructions: whether someone can follow them to launch your container and run your analysis in it. These points are all-or-nothing. If your instructions do not work exactly as you have written them, you will lose all 5 points.

Make sure your instructions work on both Windows and Mac computers. If your team does not have both, work with another team to test them.

2. Publish your report on GitHub Pages

Anyone should be able to read your report online, without cloning your repository. You learned to publish with GitHub Pages in DSCI 521 (Introduction to Quarto and GitHub Pages), where you published a whole Quarto website. Here you apply those skills to publish the HTML version of your report.

NoteAlready published your report in Milestone 1?

Switch to the setup below, even if your current one works. Later milestones build on it.

You publish by hand, with a small workaround. It works because of how GitHub Pages serves files:

  • GitHub Pages can publish the files in a docs/ folder on your main branch, exactly as they are.
  • When someone visits your site’s address, the web server shows the file named index.html.
  • With embed-resources: true, your rendered report is a single HTML file that holds everything it needs, including its figures.

So publishing your report is just putting a copy of that one file at docs/index.html. Copying files by hand is easy to forget, so it is not how you would publish a larger site. Later in the program (in DSCI 524, when you build websites for your packages), you will use tools that build and publish a website for you.

  1. Make your rendered report a single, self-contained HTML file, with embed-resources: true in its HTML options, for example in the report’s YAML header:

    format:
  html:
    embed-resources: true

    If your project’s _quarto.yml already sets this, you don’t need to add it again. A self-contained file holds its figures and styling, so it still works after you copy it somewhere else. If you have only been rendering your report to PDF, render it to HTML as well.

  2. Render your report. Then copy the rendered HTML file into a docs/ folder at the root of your repository, and name the copy index.html:

    mkdir -p docs
cp <path-to-your-report>.html docs/index.html

  3. Add an empty .nojekyll file to docs/, so that GitHub Pages serves your file exactly as it is (see Turning off Jekyll with .nojekyll):

    touch docs/.nojekyll

  4. Commit and push docs/. It is a copy of a generated file, but GitHub Pages can only publish files that are in your repository. Check that your .gitignore does not ignore docs/ or .html files.

  5. In your repository on GitHub.com, go to Settings > Pages. Under Build and deployment, choose Deploy from a branch, then the main branch and the /docs folder, and click Save.

  6. After a few minutes, your report is published at https://ubc-mds-2026-27.github.io/<your-repository>/. Open it and check that the whole report shows, including its figures.

  7. Put this URL in your README (as the link to your rendered report) and in the About section of your repository.

ImportantKeep the published report up to date

docs/index.html is a copy. Each time you re-render your report, copy it into docs/ again and push, or the published version will fall behind. We grade your work from your 1.0.0 release, and the report on GitHub Pages should match it.

Submission Instructions

Just before you submit the milestone 2, create a release on your project repository on GitHub and name it something like 1.0.0 (how to create a release). This release allows us and you to easily jump to the state of your repository at the time of submission for grading purposes, while you continue to work on your project for the next milestone.

Follow the instructions for submission on Gradescope. We only need URLs, entered into Gradescope directly: there is no PDF to make. You will submit:

  1. the URL of your project’s GitHub.com repository
  2. the URL of a GitHub release of your project’s GitHub.com repository
  3. the URL of your report on GitHub Pages

Expectations

  • Everyone should contribute equally to all aspects of the project (e.g., code, writing, project management). This should be evidenced by a roughly equal number of commits, pull request reviews and participation in communication via GitHub issues.
  • Each group member should work in a GitHub flow workflow; where they create branches for each feature or fix, which are reviewed and critiqued by at least one other teammate before the the pull request is accepted.
  • You should be committing to git and pushing to GitHub.com every time you work on this project.
  • Git commit messages should be meaningful. These will be marked. It’s OK if one or two are less meaningful, but most should be.
  • Use GitHub issues to communicate to their team mate (as opposed to email or Slack).
  • Your question, analysis and visualization should make sense. It doesn’t have to be complicated.
  • You should use proper grammar and full sentences in your README. Point form may occur, but should be less than 10% of your written documents.
  • You will not be expected to incorporate Milestone 1 feedback in this submission (of course you can, but likely you will not receive it until the end of the week which might be too late to incorporate it). ```
