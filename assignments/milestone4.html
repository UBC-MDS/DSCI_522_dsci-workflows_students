Milestone 4

NoteThe end-of-course project goal

Your team answers a predictive question with a public data set, in R and/or Python, with a focus on reproducible and trustworthy workflows. By the end of the course, your single Quarto document will have become a project with:

  • well-documented, modular scripts in R and/or Python
  • a pipeline automated with GNU Make
  • a reproducible Quarto report
  • a Docker container for the computational environment
  • a GitHub repository for collaboration and sharing

Milestone 4 summary

This milestone ties your project together: one command runs the whole analysis, your code is tested, your report reads like a finished paper, and you fix what reviewers pointed out.

ImportantSee what a finished Milestone 4 looks like

An example Milestone 4 that corresponds to our expectations is here: Breast Cancer Predictor 3.0.0. Look at its Makefile, src/ and tests/ folders. It uses conda for its environment: ignore that part and keep the uv/renv setup from Milestone 2.

TipReadings for this milestone
  • Data analysis pipelines with GNU Make and the Makefile cheatsheet
  • Testing, then pytest (Python) or testthat (R)
  • Reproducible reports with Quarto and the Quarto cheatsheet (you practised these in Individual Assignment 3)

1. Write a Makefile that runs everything

Put a file named Makefile in the root of your repository, as you did in Individual Assignment 4. It needs:

  • an all target: runs the whole analysis from top to bottom, including publish
  • a clean target: deletes everything the pipeline made, so make all can start fresh
  • a publish target: copies the rendered report to docs/index.html, replacing the steps you did by hand in Milestone 2
  • real file targets for the other steps, with their dependencies (the data and the script), so Make only reruns what changed. Only all, clean, publish and similar group names may be phony.
  • comments that explain each rule, and a README section that says how to run it

Your scripts run in the container, so the commands in the rules start with uv run (Python), for example uv run python scripts/download_data.py ... and uv run quarto render .... Run the pipeline with docker compose run --rm analysis-env make all.

TipExample: the publish target

Change the report’s path to your own:

Makefile
publish: docs/index.html

docs/index.html: reports/<your-report>.html
    mkdir -p docs
    cp reports/<your-report>.html docs/index.html
    touch docs/.nojekyll

Because docs/index.html depends on your rendered report, make publish copies it only when the report has changed. Commit and push docs/ after it runs.

2. Write functions and test them

Look for code that repeats (cleaning several columns the same way, many similar plots, tuning several models) or that you would reuse in another project.

  1. Write at least one function per team member, following the textbook’s workflow for writing functions and tests: write the documentation first, then the tests, then the function body.
  2. Put them in their own files: src/*.py (Python) or R/*.R (R). One function per file, or all in one file, both are fine.
  3. Use them in your scripts with import (Python) or source() (R).
  4. Write tests in tests/ with pytest (Python) or testthat (R). Add the test package to your environment, and say in your README how to run the tests in the container.
TipHow your functions are marked
  • Quality: each function does one thing, and returns a value unless it is meant to write a file or plot.
  • Usability and readability: clear names and arguments; black (Python) or tidyverse (R) style.
  • Documentation: a docstring (Python) or roxygen comment (R) saying what it does, its arguments and what it returns.
  • Tests: they cover expected cases, edge cases and errors.

More functions than the minimum are welcome, but each one is held to these standards.

3. Polish your report

A reader who is not a data scientist should not be able to tell that code made the report. Render it to HTML (that is the version on GitHub Pages); a PDF as well is optional.

4. Address feedback

From the TAs

Fix what the TAs pointed out in earlier milestones. Then submit a regrade request on Gradescope for that question, with links to the pull requests or commits that show the change. If the TA confirms the fix, you get back 50% of the points you lost on that question. Keep the request easy to follow, or we can’t give points back.

From the peer review

Address at least one peer review item per team member (a team of 4 fixes at least 4). List them in a CHANGELOG.md in the root of your repository: for each item, the feedback, what you changed, and a link to the evidence (an issue, pull request, commit or lines of code). Feedback that the TAs also gave can go in too. See keepachangelog.com for an example.

5. Update your README

Your README must take someone from a fresh clone to the rendered report: pull the image, run make all in the container, and how to run the tests. Also say how to run make clean.

Important5 all-or-nothing points for your README instructions

If someone can’t run your whole pipeline by following your instructions exactly as written, you lose all 5 points. Test them on both Windows and Mac. If your team doesn’t have both, ask another team to test them.

Submission instructions

  1. Just before you submit, create a GitHub release named exactly 3.0.0 (how to create a release).
  2. On Gradescope, enter these three URLs (there is no PDF to make):
    • the GitHub release
    • your group project’s repository (general one without GitHub release)
    • your report on GitHub Pages
TipCheck yourself before submitting
TipTeamwork expectations (these are marked)
  • Everyone contributes equally to code, writing and project management, shown by a roughly equal number of commits, pull request reviews and GitHub issue comments.
  • Use the GitHub flow: a branch for each feature or fix, reviewed by at least one teammate before the pull request is merged.
  • Commit and push every time you work on the project, with meaningful commit messages (one or two less meaningful ones are OK).
  • Talk to your teammates in GitHub issues, not email or Slack.
  • Your question, analysis and visualization should make sense. They don’t have to be complicated.
  • Your analysis should be correct and run reproducibly from your README instructions.
  • Follow the black style guide (Python) or the tidyverse style guide (R).
  • Don’t commit generated files, except docs/, which GitHub Pages needs.
  • Write your README in full sentences with proper grammar. Keep point form under 10% of it.
