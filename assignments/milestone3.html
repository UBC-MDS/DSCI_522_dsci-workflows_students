Milestone 3

NoteThe end-of-course project goal

Your team answers a predictive question with a public data set, in R and/or Python, with a focus on reproducible and trustworthy workflows. By the end of the course, your single Quarto document will have become a project with:

  • well-documented, modular scripts in R and/or Python
  • a pipeline automated with GNU Make
  • a reproducible Quarto report
  • a Docker container for the computational environment
  • a GitHub repository for collaboration and sharing

Milestone 3 summary

This milestone is about moving your analysis code out of your report and into scripts, and checking your data before you use it.

ImportantSee what a finished Milestone 3 looks like

An example Milestone 3 that corresponds to our expectations is here: Breast Cancer Predictor 2.0.0. Look at its scripts/ folder and its README. It uses conda for its environment: ignore that part and keep the uv/renv setup from Milestone 2.

TipReadings for this milestone
  • Scripts: writing scripts with command line arguments (click and docopt)
  • Data validation: what to check, and the checklist you must cover
  • Data validation with pandera (Python) or with pointblank (R)

1. Move your code into scripts

  1. Split your analysis into 4 or more scripts (.py or .R) in a scripts/ folder, one script per step of the analysis. The code doesn’t need to be turned into functions yet (that is Milestone 4). A common split:

    • download the data
    • clean and split the data
    • exploratory figures and tables
    • fit the model and evaluate it

  2. Chain them: the files one script writes are the files the next script reads.

  3. Give every script command line arguments for at least its input path and its output path, so nothing is hard-coded. Use click in Python, or docopt in R. Use descriptive file names (data/processed/cancer_train.csv, not data/file.csv).

  4. Save every figure and table to a file (for example in results/), so the report can show it.

TipWhat each script could look like
Script Reads Writes
download a URL data/raw/...
clean and split the raw data cleaned train and test files in data/processed/
EDA the training data figures and tables in results/
model the training and test data the fitted model, plus result figures and tables in results/

Running a Python script in the container looks like this (R: Rscript instead of uv run python):

docker compose run --rm analysis-env \
  uv run python scripts/download_data.py \
  --url https://example.com/data.csv \
  --write-to data/raw/cancer.csv

You can split your code differently, or have more scripts. What matters is having about 4, so you can practise joining them into a pipeline in Milestone 4.

2. Add data validation checks

  1. Write the checks as code in your scripts, for example in the script that cleans or splits the data.
  2. Write at least one check for each item in the textbook’s data validation checklist.
  3. Decide what happens when a check fails (stop with an error, or warn and continue), and make the code do that.
  4. Don’t leak test data: checks that look at relationships between columns (such as correlations) run on the training data only.

3. Make your report show your scripts’ results

  1. If your report is not a .qmd yet, convert it: quarto convert report.ipynb for a Jupyter notebook, or just rename an .Rmd file to .qmd.
  2. Replace the analysis code in the report with code that reads and displays the figures and tables your scripts saved.
  3. Don’t polish its formatting yet (cross-references, citations, hidden code): that is Milestone 4.
  4. After you re-render it, copy it to docs/index.html again and push, so the report on GitHub Pages stays current (see Milestone 2).

4. Update your environment

Your scripts probably use new packages (click or docopt, a validation package). Add each one, pinned, the same way you did in Milestone 2: add it with uv or renv, commit the changed files and push, let GitHub Actions publish a new image and update the tag in docker-compose.yml, then git pull and docker compose pull. (uv recap from DSCI 521)

5. Update your README

Your README must say how to run each script, in order, with the exact command and its arguments, using the container (docker compose run --rm analysis-env ...), then how to render the report.

Important5 all-or-nothing points for your README instructions

If someone can’t run each of your scripts and render your report by following your instructions exactly as written, you lose all 5 points. Test them on both Windows and Mac. If your team doesn’t have both, ask another team to test them.

Submission instructions

  1. Just before you submit, create a GitHub release named exactly 2.0.0 (how to create a release).
  2. On Gradescope, enter these three URLs (there is no PDF to make):
    • the GitHub release
    • your group project’s repository (general one without GitHub release)
    • your report on GitHub Pages
    • your report on GitHub Pages

You don’t need to include Milestone 2 feedback in this submission.

TipCheck yourself before submitting
TipTeamwork expectations (these are marked)
  • Everyone contributes equally to code, writing and project management, shown by a roughly equal number of commits, pull request reviews and GitHub issue comments.
  • Use the GitHub flow: a branch for each feature or fix, reviewed by at least one teammate before the pull request is merged.
  • Commit and push every time you work on the project, with meaningful commit messages (one or two less meaningful ones are OK).
  • Talk to your teammates in GitHub issues, not email or Slack: at least 3 issues per person on average in this milestone.
  • Your question, analysis and visualization should make sense. They don’t have to be complicated.
  • Your analysis should be correct and run reproducibly from your README instructions.
  • Follow the black style guide (Python) or the tidyverse style guide (R).
  • Write your README in full sentences with proper grammar. Keep point form under 10% of it.
