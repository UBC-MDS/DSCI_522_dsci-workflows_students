Milestone 3

Overall project summary

In this course you will work in assigned teams of three or four (see group assignments on GitHub) to answer a predictive statistical/machine learning question using a publicly available data set that will allow you to answer that question. To answer this question, you will perform a complete data analysis in R and/or Python, from data import to communication of results, while placing significant emphasis on reproducible and trustworthy workflows.

Your data analysis project will evolve throughout the course from a single, monolithic Jupyter notebook, to a fully reproducible and robust data data analysis project, comprised of:

  • a well documented and modularized scripts written in R and/or Python,
  • a data analysis pipeline automated with GNU Make,
  • a reproducible report powered by Quarto,
  • a containerized computational environment created and made shareable by Docker
  • a remote version control repository on GitHub for project collaboration, sharing, and documentation.

An example final project from past years can be seen here:Breast Cancer Predictor

1. Abstract code from your literate code document (*.ipynb, *.qmd or *.Rmd) to scripts (e.g., .R or .py).

This code need not be converted to a function, but can simply be files that call the functions needed to run your analysis. You should aim to split the analysis code into 4, or more, R or Python scripts. Where the code in each script is contributing to a related step in your analysis.

Below we list some examples of steps that your current report document can be broken up into. It is not critical you split your code up exaclty as we list below, but you must somehow split your analysis code up into 4, or more, R or Python scripts.

  • Download/extract data
  • Clean/transform data
  • Split and pre-process data
  • Exploratory data analysis
  • Model fitting
  • Model evaluation

The output of the first script must be the input of the second, and so on. All scripts should have command line arguments and we expect you to use the click) Python package for parsing command line arguments for Python projects, and the docopt R package for parsing command line arguments for R projects.

They scripts could be organized something like this:

  • A first script that downloads the data from the internet and saves it locally. This should take at least two arguments:

    • the path to the input file (a URL or a relative local path, such as data/file.csv), as well as
    • a path/filename where to write the file to and what to call it (e.g., data/cleaned_data.csv).

    Note: choose more descriptive filenames than the ones used above. These are general for illustrative purposes.

  • A second script that reads the data from the first script and performs and data cleaning/pre-processing, transforming, and/or partitioning that needs to happen before exploratory data analysis or modeling takes place. This should take at least two arguments:

    • a path/filename pointing to the data to be read in
    • a path/filename pointing to where the cleaned/processed/transformed/partitioned data should live.

  • A third script which creates exploratory data visualization(s) and table(s) that are useful to help the reader/consumer understand that data set. These analysis artifacts should be written to files. This should take at least two arguments:

    • a path/filename pointing to the data,
    • a path/filename prefix where to write the figure to and what to call it (e.g., results/this_eda.png).

  • A fourth script that reads the data from the second script, performs the modeling and summarizes the results as a figure(s) and a table(s). These analysis artifacts should be written to files. This should take at least two arguments:

    • a path/filename pointing to the data
    • a path/filename prefix where to write the figure(s)/table(s) to and what to call it (e.g., results/this_analysis)

  • You are welcome to have any additional scripts as needed, or modify how you organize the splitting up of your code a little differently than suggested. What is important is that you have ~ 4 different scripts so you get practice setting them up in a data analysis pipeline (next milestone).

Important

You must document in your README.md how to call each script, including what arguments you pass each script.

2. If your report literate code document is not already a *.qmd file, convert it so that it is.

You can use quarto convert notebook.ipynb to convert Jupyter notebooks to *.qmd files. If you were using an .Rmd file, you can simply rename the file so that it has a .qmd file extension. Much of the .Rmd syntax is backwards compatible, so this should mostly work.

3. Edit your report literate code document (*.qmd) so that it’s sole job is to narrate your analysis, display your analysis artifacts (i.e., figures and tables), and nicely format the report.

The goal is that non-data scientists would not be able to tell that code was used to perform your analysis or format your report (i.e., no code should be visible in the rendered report).

You should render your report to either html or PDF. Quarto has all the features needed to make your report satisfy our expectations (bibliography, automatic numbering of figures and tables, inline code rendering, etc). In particular, we expect you to:

  • Use markdown headers and Quarto configuration so that a table of contents will be created when the document is rendered.
  • Add correctly formatted inline BibTeX references so that a nicely formatted reference list will be present at the end of the document.
  • Edit the figure formatting so that Quarto:
    • automatically numbers them,
    • has a label for easy cross referencing, and
    • controls the figure sizes so the figures are not too big.
  • Add a table description argument so that they are automatically numbered by Quarto and use cross referencing to link to the table when it is discussed in the text.
  • Edit the narrative so it uses cross-referencing to refer to the figures and tables instead of having their reference hardcode the figure and table numbers.
  • Replace any hard-coded values in the Quarto report narrative text with inline Quarto code, so that the text will be automatically updated with the correct value.
  • Change the code chunk options so that no code is viewable in the rendered report, just the code outputs where needed (e.g., figures and tables).

3. Update your project’s computational environment as you add dependencies to your project

At a minimum, you will be adding either Quarto as a new dependency to your project. Thus, you will need to update your project’s computational environment as you add this (and potentially other) dependencies to your project. This means that your environment specification files will need to have this package added, with the version pinned, and the Docker container image will need to be rebuilt and published to DockerHub.

4. Update any instructions for running your analysis

Do not forget to update your project’s documentation to reflect changes from this week. Update instructions and/or commands in your README.md and documention to run your analysis in your compute environment. You may combine commands within make. But instructions in the README.md file should include how to run the make target and rule. 5% of your project grade this week is going to be dedicated to whether your analysis runs as documented. These points are unrecoverable and all-or-none.
